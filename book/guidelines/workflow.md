# 工作流

## 开发流程——六个阶段，硬关卡

每个功能按顺序走过以下阶段。**不许跳过。**

| 阶段    | 名称             | 产出                   | 关卡                                                             |
| ------- | ---------------- | ---------------------- | ---------------------------------------------------------------- |
| Step 0  | 结构化需求 Brief | 需求简报               | 每个槽位填实                                                     |
| Phase 1 | 分析             | 影响图 + 风险清单      | 不改任何代码                                                     |
| Phase 2 | 设计             | 数据流、文件清单、接口 | 设计完整；只在真缺口处停下——范围冲突、数据形态未定、外部依赖不清 |
| Phase 3 | 实现             | 代码                   | 严格按设计；不越批准范围一步                                     |
| Phase 4 | 测试             | 测试用例               | 全绿；不削弱断言                                                 |
| Phase 5 | Code review      | review 发现清单        | 只记录——不修复                                                   |
| Phase 6 | 收尾             | 文档、经验、问题       | 只记录——不修复                                                   |

Step 0 在任何代码之前。把 brief 填满：背景、范围（影响什么、明确**不**影响什么、边界在哪）、需求本身。空着的"不影响"清单是 Phase 3 越界改动的头号原因——排除项槽位必填。

Phase 2 产出完整设计——数据流、文件清单、接口——然后继续推进；只有出现真缺口时才停下来问用户（范围冲突、数据形态未定、外部依赖不清），绝不为了确认而停。

Phase 4 的硬骨头是关卡，不是顺序：所有相关测试全绿，不许为凑绿削弱断言；覆盖正常路径、边界输入（区间、空值、极端值）、错误路径，并回归确认既有行为没被破坏。测试先行（先写失败的测试 → 最小实现 → 保持绿的 refactor）是默认循环——工作怎么排布都行，关卡必须守住。

Phase 5 和 Phase 6 共享一条纪律：**只记录，不修复。** review 或收尾中发现的问题进 `notes/issue/`——修复是另一件事、另一个任务。顺手修感觉高效，实际上拆了关卡：review 就不再是在 review 刚建好的东西了。

## code ↔ book——两半

```
                 book/  （知识库 + 驱动源）
               ┌─────────────────────────────────────┐
               │  plans/      → 驱动实现              │
               │  guidelines/ → 提供基线              │
               │  learn/      → 提供经验              │
               │  issue/      → 提供方向              │
               │  decisions/  → 提供上下文            │
               └──────────────┬──────────────────────┘
                              │ 驱动
                              ▼
                          code/
                              │ 产出
                              ▼
               ┌─────────────────────────────────────┐
               │  stage/      ← 阶段勾选              │
               │  learn/      ← 新经验                │
               │  issue/      ← 新发现的问题          │
               │  changelogs/ ← 变更记录              │
               │  plans/      ← 完成状态              │
               └─────────────────────────────────────┘
```

## 交互规则

1. **写码前** — 按 tag 搜 `notes/learn/` 找相关经验，只查任务触达的那篇 guideline（`guidelines/README.md` 的路由表负责指路）；不通读。
2. **写码中** — 学到新东西或踩了坑？立即写进 `notes/learn/`；未来的会话（人或 agent）都受益。
3. **写码后** — 同步 book：plan 状态、stage 勾选（附一行结果）、新 issue、索引。
4. **plan 驱动代码** — `book/plans/` 是实现的输入。agent 读 plan，在 `code/` 里施工，再回写 `book/`。
5. **issue 喂代码** — `notes/issue/` 记录问题，成为后续迭代的方向。
6. **book 复利** — 每个功能都应该让 book 比来时更全。book 既是 agent 的上下文，也是人的参考手册。
7. **刷新索引** — book 有任何改动，收尾前跑 `npm run book:index`（仓库根）。新文件必须带 frontmatter `description`，内部链接必须走得通——任何一样不过，构建就失败。
8. **换模型时重新审计** — 脚手架会随模型能力老化。agent 的模型代际变化时，按 ADR-003 的关卡分类法重新审计 AGENTS.md、`guidelines/` 和 skills：留下意图关卡（只记录不修复、范围纪律），拆掉或放宽只因不信任弱模型而存在的关卡。

## 文档路由

| 产出       | 位置                   | 读者                   | 形态                                    |
| ---------- | ---------------------- | ---------------------- | --------------------------------------- |
| 开发阶段   | `book/stage/`          | 人类优先，agent 可勾选 | 概述 + 步骤清单，勾选附一行结果         |
| 学到的经验 | `book/notes/learn/`    | 人类 + agent           | 知识条目：可检索、带 tags、说明适用场景 |
| 潜在问题   | `book/notes/issue/`    | 人类 + agent           | 结构化：问题 + 复现 + 建议方向          |
| 任务跟踪   | `book/notes/task/`     | 人类 + agent           | 检查清单                                |
| 架构决策   | `book/docs/decisions/` | 人类优先               | ADR 格式                                |
| 实现计划   | `book/plans/`          | agent 优先             | 结构化、可直接执行                      |
| 变更记录   | `book/changelogs/`     | 人类优先               | 短、带日期的条目                        |

所有 book 文档都遵守 `guidelines/writing-style.md` 的说人话标准。
