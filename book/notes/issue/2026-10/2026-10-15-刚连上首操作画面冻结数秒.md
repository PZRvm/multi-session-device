# 刚连上后首次操作画面冻结数秒（排查记录，不修复）

## 症状（用户 2026-10-15 报告）

应用刚启动 / 手机刚 Wi-Fi 连上后，**一开始操作手机画面必然不更新**（操控生效），
等几秒自动恢复。死锁修复批（ba726e4）之后从「永久冻结」变为「冻结约 3—6 秒自愈」。

## 排查证据（独立探针，scrcpy 3.3.3 裸流解析）

1. **荣耀编码器不遵守 i-frame-interval=1**：10 秒窗口 252 帧、仅开场 1 个 IDR；
   首滑后 9 秒、162 帧重度运动（38 帧/s、均帧 1.8MB）**零关键帧**。transport.ts 钉的
   1s 关键帧间隔在这台 EBG_AN00 上完全不生效。
2. 主屏并非静默：解锁后持续 ~430KB/s 帧流（桌面动画组件）；首次滑动瞬间 ~4.4MB/s
   尖峰（约 10 倍）。
3. 帧流解析修正记录：scrcpy 3.3 视频口布局 = dummy(1) + 设备名(64) + 编码元数据(12)
   共 77 字节后才 是 pts(u64)+len(u32) 逐帧（此前误按 64 字节 dummy 导致解不出帧）。

## 根因链（两个逻辑盲点叠加）

- **盲点 A（设计前提失效）**：`GopCache` 的 `CACHE_MAX_PTS_SPAN_MS=1500` 注释明写
  「关键帧间隔钉 1s：缓存预算按此设计」——链内 PTS 跨度超 1.5s 即清链等新关键帧。
  该假设依赖编码器守约；实测荣耀 IDR 间隔≈无穷大（仅开场一个），于是开场 1.5s 后
  链被清空且**永远等不到下一个关键帧** → `buildReplay` 恒 null → 缓存恒不可回放。
  （息屏唤醒死锁的「PTS 跨度清链」一环，同根。）
- **盲点 B（悬空即杀流）**：刚连上 + 首次操作 = 重度突发（38 帧/s × 1.8MB 均帧），
  renderer ACK（每 8 包）一轮回来前 `MAX_UNACKED_PACKETS=16` 必然越限 →
  `waitingResync=true` → `sendResync` → replay null → **悬空丢包**（突发吸收本为
  「回放可行」设计；回放不可行时它把好流杀死）。冻结期间控制通道不受影响。
  自愈路径 = 死锁修复批的看门狗：+3s 重试 sendResync 仍 null → nullReplayStalls=2
  → `resetVideo` → 新 configuration → 恢复。「必然冻结几秒」即此链的确定性。

## 修复方向（待用户批复，未动手）

1. **修 A（推荐先做）**：PTS 跨度预算改为只累计「链内相邻帧间隔」（idle gap 不计入），
   或改由字节/包数预算单独约束（内存有界已有这两项；回放时长上限交给 ACK 背压）。
   开场 GOP 得以留存在缓存，突发可回放，盲点 B 的触发条件消失。
2. **修 B（防御性）**：空 replay 的 stall 路径不进悬空丢包——改为「保序暂停发送等
   ACK 追平」或「直接 resetVideo」（一闪换即时恢复），任一都比冻结 3s 好。
3. 组合 1+2 最稳：缓存修复 + 悬空路径防御，两者独立可验。
