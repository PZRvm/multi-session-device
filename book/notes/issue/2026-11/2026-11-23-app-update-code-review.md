# 应用内更新审查：Mac 退出和候选切换

审查范围为本地 `dev` 至应用更新分支 `30c4ded`，涵盖应用更新状态机、IPC、安装准备、Mac 与 Windows 引擎和发布流水线。按项目清单核对权限、并发、事务边界、通知、输入和范围。两项发现均用当前源码及隔离替身验证，本轮只登记。

## R1 · P1 · 取消退出后，后续正常退出可能触发未确认安装

Sparkle 取消第一个更新周期时，主进程将 `quitAllowed` 设为 `true`，再调用 `app.quit()` 进入正常清理。若用户因录屏提示或清理残留选择留在应用，正常退出结束前会复位 `quitPending`，Sparkle 侧的 `quitAllowed` 仍为 `true`。用户之后重新检查并下载，下一次普通退出直接跳过 Sparkle 取消。

隔离替身确认第一次退出调用一次原生取消，退出折返后新周期的第二次退出既未取消也未被更新监听器拦住。Sparkle 2.10.1 的用户驱动合同明确说明：未取消的就绪更新可能在应用自行终止后安装。替身验证了拦截缺失，未在真实包上触发未确认安装。该问题阻塞稳定发布。 [退出监听](../../../../src/main/updates.ts#L133) · [普通退出折返](../../../../src/main/index.ts#L183) · [Sparkle 就绪协议](https://github.com/sparkle-project/Sparkle/blob/2.10.1/Sparkle/SPUUserDriver.h#L193-L208)

修复方向是让退出放行只作用于已取消的那次更新周期，并覆盖「首次退出取消更新 → 用户留在应用 → 重新下载并选择稍后 → 再普通退出」的真实包回归。

## R2 · P2 · 下载失败后若服务端换版，更新会卡在下载中

Mac 适配器在重试时可重新发现候选。控制器当时处于 `downloading`，会忽略候选事件。首次重试发现版本已变时返回下载失败，但适配器已经准备新候选。再次重试会下载新版本；控制器因它和旧候选不一致而丢弃完成事件，按钮停在下载中。

隔离替身验证了 `90.0.2` 下载失败、更新源切换 `90.0.3`、连续重试两次的路径。最后原生层报告 `90.0.3` 就绪，快照仍显示 `90.0.2` 下载中且没有就绪版本。 [Mac 重试入口](../../../../src/main/updates/macSparkle.ts#L199) · [候选与完成校验](../../../../src/main/updateController.ts#L155)

修复方向是在主进程同步换版结果，要求用户重新确认新候选，并给每次下载绑定的版本设定明确的成功或失败终点。
