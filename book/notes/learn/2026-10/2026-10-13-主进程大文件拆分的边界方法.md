# 拆 2600 行 main 单文件：状态归属规则与零契约改动

**场景**：`src/main/devices/index.ts` 长到 2603 行（对账状态机/启停/创建/编辑/IPC 混居），要拆成 emulator 目录那样的「薄 index + 域模块」而不动任何行为与测试断言。plan 见 [2026-10-13-main-devices-emulator-split](../../../plans/2026-10-13-main-devices-emulator-split.md)，架构快照见 [2026-10-13-main-module-split](../../../docs/architecture/2026-10-13-main-module-split.md)。

## 拆分中真正决定边界的三件事

1. **ESM `let` 导出不可外部赋值**——这是拆大文件时最先撞上的硬约束，解法按写方数量分两档：
   - **单写方持有的 `let` 留在持有者文件**（loadPromise→scan、writeQueue→persistence、deleteFlights→lifecycle……）：零额外机制，读方经持有者暴露的函数间接访问。
   - **跨组读写的进 `state.ts` 配访问器**：可重赋值者 `xxxNow()` 读 + `setXxx()` 写（`-Now` 后缀沿文件内已有的 snapshotNow/transientIdsNow 惯例，读者一看即知是内存态快照）；Map/Set 等绑定稳定的直接 const 导出（元素可变、绑定不变，无 TDZ 问题）。
   - 判断口诀：先数写方。一个写方→私有；两个以上→上收 state.ts。别一上来把全部 24 个模块级变量都搬进 state.ts——单写方的搬了反而多一层无意义转发。

2. **`vi.resetModules()` + 动态 `import('..')` 的单例语义靠整图重载保持**：3400 行测试反复 reset 后从 `'..'` 重新 import。拆分后状态分散在多个子模块，但它们全部经 index 依赖图加载，reset 清整个 registry、重载即全新单例——**测试零改动的充要条件是：不许任何子模块被 index 图之外的路径独立 import**。这也是「禁止绕过 index 中转」的实际收益之一。

3. **先列「消费方零改动清单」再动手**：把 index.ts 的 17 个导出符号和四个消费方（ipc/index.ts、main/index.ts、emulator/sdkSourceSwitch.ts、测试）逐一对账，出口契约固定后，内部怎么拆都安全。最终 index.ts 收成 20 行纯 re-export，消费方一行没动。

## 流程上的两个有效做法

- **自底向上逐层抽，每层一个 commit + 全绿门禁**（environment→state→persistence→scan→startup→lifecycle→create→edit→queries/ipc）：每步 typecheck 即时暴露环引用与漏改的调用点；2603 行的拆分全程没有一次「大爆炸」调试。
- **跨模块共用的纯函数下沉到最底层**：parseLegacyCamera 同时被启动仲裁与编辑草稿用，落 environment.ts（与其他载荷守卫同层）；withDeadline/checkTimeoutAvailability 落 startup.ts 导出（lifecycle/create/edit 复用）。

## 踩坑

- 用行号（sed）切块搬运时，任何一步 Edit 都会移动行号——切块与删除必须同一命令内完成，或切块后立刻删（本次 D8 曾因先加了两行 import 导致 ipc.ts 头部混入残留片段）。
- `persistence ↔ scan` 天然互调（首载要扫描、重查要重读库）：把「首载编排（loadAndScan/ensureLoaded）」放进 scan.ts 而不是 persistence.ts，环就消失了——按数据流方向安置编排者，而不是按名词归类。
