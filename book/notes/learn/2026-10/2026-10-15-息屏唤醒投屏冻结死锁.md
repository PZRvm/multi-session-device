# 息屏唤醒投屏冻结死锁（操控有效、画面不动）

2026-10-16 更新：本文记录最初的永久冻结与看门狗兜底。解锁后仍冻结数秒的问题已进一步
修复，见 [PTS 单位与静置 ACK](2026-10-16-投屏PTS单位与静置ACK误判.md)；当前暂停且无回放时立即请求编码器重建，不再等待两轮停滞。

适用场景：scrcpy 投屏在「长息屏 → 唤醒」后画面冻结但触控/输入仍生效；切走画布再
切回即恢复。AVD 与真机共用同一条 main↔renderer 视频管线，本缺陷两端通用（真机
Wi-Fi 场景因息屏常态化而最易触发）。

## 症状与根因链（五步死锁）

1. **流级无恙**：独立 scrcpy 探针实测——深睡 90s 视频 socket 保持打开、零字节；
   唤醒解锁后帧率立即恢复（875 KB/s）。server/设备侧不背锅，问题在 app 管线。
2. **PTS 跨度清链**：GopCache 按「链内 PTS 跨度 ≤1.5s」预算回放延迟；息屏后首帧
   PTS 含整个睡眠间隔（编码时间线连续），跨度瞬间爆表 → clearChain →
   awaitingKeyframe → 唤醒突发的增量帧全部不进缓存（对回放这是正确行为）。
3. **未 ACK 包预算打爆**：唤醒锁屏动画突发 ~875KB/s，MAX_UNACKED_PACKETS=16 很快
   超限 → waitingResync=true → sendResync → buildReplay 为 null（链空）→ 非立即
   路径只 nullReplayStalls=1 被动等关键帧，**waitingResync 保持 true 开始丢包**。
4. **看门狗哑火**：渲染端 ACK 只看「收到」不看「画面」——把冻结前收到的包全部
   ACK → outbox 归零；ACK 停滞看门狗要求 `outbox.length > 0` → 永不再触发。
   没有第二次 sendResync，nullReplayStalls 到不了 2，resetVideo 永不下发。
   控制通道不经 outbox → 操控一直有效。
5. **用户切回画布 = screenActivate → sendResync(immediate) → replay 仍空 →
   resetVideo → 新配置包 → 解锁**——这就是「切走再切回才好」的机制。

## 修复（session.ts 看门狗）

原条件外补并列分支：`waitingResync && lastAckAt 超时 && 画布激活` → 重试
sendResync（链恢复则重放解困；nullReplayStrolls≥2 走 resetVideo 强制编码器出新
配置包），lastAckAt 兼作重试节拍防风暴。冻结自愈窗口 ≈ 2×ACK_STALL_MS(3s)。

## 排查方法论（可复用）

- 「画面冻结但操控有效」= 视频通路断、控制通路活 → 先用**独立探针**（自起
  scrcpy server 数 socket 字节率）切割设备侧与 app 侧责任，再进代码。
- scrcpy 探针坑：server 退出时 **CleanUp 会删掉自己的 jar**，复用旧路径会秒崩
  （Aborted、零日志）——每次重推。
- 恢复路径即线索：用户找到的 workaround（切走切回）对应的代码路径
  （activate → sendResync → resetVideo）就是缺陷的镜像。
