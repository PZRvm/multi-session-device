# 已有模拟器配置编辑功能调研报告

> 范围确认：用户明确只编辑名称和附加配置，内部存储暂不允许修改，不更换机型、系统 API 或系统镜像。

## 1. 需求理解

### 1.1 功能目标

让测试人员修改已有 Android 模拟器的名称及附加设置，复用创建时的字段、选项来源、单位和校验；内部存储在编辑中只读。编辑窗口可显示机型与系统 API 作为只读背景信息；画像选择、系统镜像选择及下载不进入编辑流程。

**名称和普通附加设置可以编辑。** 当前应用只支持重命名；已确认附加设置停机后保存、下次冷启动生效，保存后不自动启动，以保留已有应用、登录状态和文件为设计目标。Quick Boot、跨架构 ABI 等创建时尚未开放的选项，编辑时保持同样的限制。

内部存储保留只读展示。第 3、4 节的实测确认：RAM 扩缩保留了数据样本；直接扩大存储在 API 32 丢失样本、API 34 不生效，调小配置均未真正缩容。用户已确认本期禁止已有设备的内部存储容量变更，扩容和缩容均不开放，即使设备尚未首次启动也保持只读。创建时仍可设置初始容量；普通编辑不安排 AVD 重建、擦除或数据盘迁移。

### 1.2 未知点清单

- [x] 已有模拟器能否编辑名称和附加设置？
  - 名称已有接口；多数附加设置已有配置/启动映射，可补更新流程。见 2.2—2.5。
- [x] 哪些附加设置有特殊生效边界？
  - 普通字段下次启动生效；RAM 扩缩已用临时 AVD 验证。存储直接扩容丢样本或不生效，缩容配置不生效。见 2.5 字段表及 3.4、4.4 实测结果。
- [x] 能否复用创建时的界面与校验？
  - 复用 SettingsForm 和设置契约；编辑直接回填名称与附加设置，不走画像/镜像选择页。见 5.2—5.5。
- [x] 保存怎样避免配置、元数据和运行态不一致？
  - 设备级互斥、配置指纹、跨文件事务及中断恢复；不能只写 devices.json。见 2.5。
- [x] RAM 扩缩会否清数据，填写值是否等于实际内存？
  - 两套镜像均保留测试文件和持久设置；API 34 将 2048 MiB 自动提高到 2560 MiB，运行性能仍受资源影响。见 3.4—3.5。
- [x] 内部存储能否直接无损扩缩，或通过缩容释放宿主空间？
  - 直接扩容丢样本或不生效；调小配置未缩小数据盘，虚拟容量与宿主文件占用不同。见 4.3—4.5。
- [x] 能否在缩容前检查能力，不支持就拦截？
  - 技术上可做保守预检，不能仅凭已用空间或最小容量估算放行。本期已确认不允许存储变更，保存前统一拒绝该字段修改，无需实现缩容探查和迁移。见 4.4—4.5。

### 1.3 拆分判断

分为四个单元：①配置生效与数据保留；②RAM 扩缩；③内部存储扩缩；④名称/附加设置共用界面及 IPC。单元②③独立验证资源与数据边界，落地共用①的停止状态及更新事务；单元④依赖①②③返回有效配置、能力及字段限制。

### 1.4 存储与内存实测环境和方法

实测环境：macOS Apple Silicon，应用 SDK 的 Emulator **37.2.12.0，build 16428233**；新建临时 AVD，画像 `pixel_8`；镜像为 `system-images;android-32;default;arm64-v8a` 与 `system-images;android-34;default;arm64-v8a`，均 revision 2。API 34 另有 extension level 7。版本分别核自 SDK 的 `emulator/package.xml`、启动日志及镜像 `source.properties`。

所有轮次使用独立 `ANDROID_AVD_HOME`、`ANDROID_USER_HOME`、`ANDROID_EMULATOR_HOME`，按本项目设置映射修改配置后以 `-no-window -no-snapshot -gpu host` 冷启动。固定 2 核、heap 256 MiB；等 `sys.boot_completed=1` 后读取 `/proc/meminfo`、`df -k /data`；停机后用 SDK 内 `qemu-img info --output=json` 核对格式和虚拟容量。

数据样本为 `/sdcard/Download/msd-research-marker.txt`、`/data/local/tmp/msd-research-marker.txt`，内容均为 `msd-research-20261008-data-preservation`；另用 SettingsProvider 的自定义 system 键 `msd_research_marker=123456` 检查数据库持久化。每次停机前执行 `sync`。未使用真实账号或安装业务 APK，因此样本保留不等于所有应用和登录状态均已验收。预试的 `screen_off_timeout` 会被模拟器启动属性覆盖，已排除该指标，正式结果使用自定义键。

### 2.3 候选方案

**方案 A：更新原 AVD 的附加配置与元数据**

- 原理：名称只改元数据；附加设置按差异更新白名单配置键和运行设置，下一次启动应用。固定原画像和镜像，内部存储单独校验。
- 来源：[官方 AVD 编辑与属性](https://developer.android.com/studio/run/managing-avds)、[Emulator 配置与启动参数](https://developer.android.com/studio/run/emulator-commandline)、[快照失效规则](https://developer.android.com/studio/run/emulator-snapshots)。
- 适配：复用现有设置映射、store 和 runner；新增编辑事务，无新运行依赖。

**方案 B：每次保存都重新生成 AVD**

- 原理：沿用原机型和镜像，用修改后的名称及设置重新初始化设备。
- 来源：[官方新建命令](https://developer.android.com/tools/avdmanager)、[userdata 初始化与 wipe-data](https://developer.android.com/studio/run/emulator-commandline#avd-data-directory)。
- 适配：能复用创建链路，但修改 RAM 或网络也会丢应用数据，与普通配置编辑的默认目标不符；不采用，不增加 create -f 覆盖路径。

### 2.4 可行性分析

| 维度     | A：原 AVD 更新                                                            | B：全部重建                                         |
| -------- | ------------------------------------------------------------------------- | --------------------------------------------------- |
| 技术匹配 | 覆盖普通附加设置；内部存储保持只读                                        | 能用原画像/镜像重新初始化，但全部修改都清数据       |
| 规则冲突 | 保持独立 AVD 与 IPC 边界，符合用户限定的字段范围；需同步原 PRD 的编辑边界 | 用户没有授权重建清数据；不应把它作为普通保存行为    |
| 成本     | 中：无新包，主要为回填、互斥、跨文件恢复和验证                            | 中：复用创建但需占盘/回滚，用户反复安装和登录成本高 |

RAM 与内部存储的实测环境见 1.4，数据与候选方案分别见第 3、4 节；存储不能直接复用创建时的写配置逻辑。

### 2.5 结论与实施建议

结论：**借鉴思路手写**。采用方案 A：继续使用现有配置映射与 runner，补齐读取、差异校验、更新和事务恢复。固定画像/镜像，不实现更换机型、系统 API 或整台 AVD 重建。

落地建议按以下顺序进入后续 plan：

1. **读取及输入边界。** 在 `src/main/emulator/` 新增配置读取/差异模块，在 `src/shared/types.ts` 定义配置快照与更新输入。业务输入限 deviceId、name、advancedSettings 及配置指纹/能力上下文；不复用包含 profileId/imagePackageName 的完整 CreateDeviceInput。main 从目标设备读取原画像和镜像用于能力校验，不接纳 renderer 修改这些身份。
2. **回填有效值。** 读取可信元数据、原 config 和 runner 默认并保留字段来源；legacy 的 advancedSettings=null 不能直接套今天的新建 defaults。保留未修改旧值；资源或能力变化时定位失效字段，不自动重置全部配置。
3. **保存守卫。** `src/main/devices/index.ts` 新增更新流程，副作用前检查 stopped、文件健康、库可写与配置指纹；设备级互斥覆盖启动、删除和再次保存。复用 `buildEnrichedCapabilities` 校验改动与关联字段；原镜像资源状态变化仍按现有健康/资源守卫拒绝，不变成换镜像流程。
4. **配置事务。** `src/main/emulator/avd.ts` 增加白名单 set/delete，处理 skinRef、orientation 从非空改为空的旧键残留。记录 config 与元数据旧内容及事务进度，失败恢复；中断后恢复或冻结目标设备。备份/事务状态与对账扫描协作，单文件 tmp+rename 不等于跨文件原子提交。只更新允许字段，保持 AVD ini、镜像路径和画像身份；不能照搬创建失败就删除 AVD 的回滚。
5. **快照处理。** 硬件/启动配置变化重置 snapshotReadyAt，确保下次冷启动，保留用户数据盘；名称单独变化不影响快照。[快照规则](https://developer.android.com/studio/run/emulator-snapshots)
6. **存储守卫。** 按 4.5 固定已有设备的容量，main 拒绝 storage 字段变更；更新配置时排除 disk.dataPartition.size，不将旧值或创建默认值重新写入。本期不实现容量探查、扩缩容执行器、重建或擦除。
7. **验证。** 覆盖停机守卫、同设备并发、外部改库、删键、摄像头自引用排除、写盘/回滚/中断恢复、两台设备不串改及身份不变；伪造机型/镜像字段应拒绝。真 AVD 核验 CPU/RAM/heap、摄像头、网络、朝向、皮肤与数据保留。build/typecheck/lint/test 作为实现关卡，本轮仅修订报告。

## 3. 调研单元：RAM 扩容与缩容

### 3.1 该部分要做什么

停机后改变整机 RAM，保留用户数据盘；判断实际生效值与缩小内存后的运行影响。VM heap 为独立关联设置，不把它当成整机内存。

### 3.2 项目现状

- [设置契约](../../../src/shared/settings-contract.ts)把 `ramMiB` 写为 `hw.ramSize`，把 `vmHeapMiB` 写为 `vm.heapSize`，并校验 heap 不超过 RAM 的一半。
- [能力生成](../../../src/main/emulator/settings.ts)当前允许 RAM 2048—32768 MiB。这个表单范围不能证明每个镜像都按原值运行。
- [runner](../../../src/main/emulator/runner.ts)和[启动参数映射](../../../src/shared/settings-contract.ts)已有冷启动路径，无须为了 RAM 修改而重建 AVD。
- [设置表单](../../../src/renderer/src/components/wizard/SettingsForm.tsx)已分别显示“内存（整机 RAM）”及“VM heap”，编辑应共用字段和校验。

### 3.3 候选方案

**方案 A：停机更新 hw.ramSize，下次冷启动**

- 原理：修改虚拟硬件内存，继续使用原数据盘。RAM 增大会增加宿主资源需求；减小后，Android 可更频繁回收内存或终止应用进程。
- 来源：[AVD 内存设置](https://developer.android.com/studio/run/managing-avds)、[Emulator memory 参数](https://developer.android.com/studio/run/emulator-commandline)、[Android 内存回收与 LMK](https://developer.android.com/topic/performance/memory-management)。
- 适配：现有配置映射直接支持；保存前停机，修改硬件后使旧快照失效。[快照规则](https://developer.android.com/studio/run/emulator-snapshots)

**方案 B：修改 RAM 时重建 AVD**

- 原理：按新 RAM 创建空设备，重新安装应用和准备数据。
- 来源：[avdmanager](https://developer.android.com/tools/avdmanager)、[用户数据盘与 wipe-data](https://developer.android.com/studio/run/emulator-commandline#avd-data-directory)。
- 适配：技术上可创建，但增加数据丢失与恢复成本，RAM 调整不需要采用此路径。

### 3.4 可行性分析

| 维度     | A：原盘修改 RAM                          | B：重建                              |
| -------- | ---------------------------------------- | ------------------------------------ |
| 技术匹配 | 两套镜像均能完成扩缩并再次启动，样本保留 | 能设置新 RAM，但原数据不随空设备保留 |
| 规则冲突 | 保持原设备身份与数据隔离；需停机         | 未获清数据授权，不适合作为普通保存   |
| 成本     | 低，无新依赖；补有效值回读和冷启动验证   | 高，用户需重建测试环境               |

正式实测：内部存储全程固定 6144 MiB；`MemTotal` 是来宾 Linux 可用总内存，扣除了部分保留区，不应要求它逐字等于配置数值。

| API 34 | 扩容 |            4096 |        4017052 | 是         | 保留     |
| API 34 | 缩容 |            2048 |        2538144 | 是         | 保留     |

API 34 的 2048 MiB 轮次均记录 `Increasing RAM size to 2560MB`。上游也有按 API/设备形态抬高 RAM、调整 heap，以及 API ≥33 使用 qcow2 userdata 的逻辑；这是解释线索，具体边界仍以已安装二进制验证为准。[main-common.c](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/android-emu/android/main-common.c)

### 3.5 结论与实施建议

结论：**采用现成方案**。使用 Emulator 原有 `hw.ramSize` 能力，配合现有映射，停止后保存并冷启动。

RAM 扩缩本身无需清理持久数据；缩小后可用内存更少，业务应用可能卡顿、被系统终止或因分配失败退出，未落盘的运行内容也不会跨冷启动保留。增大 RAM 也不保证必然更快，过量分配会增加宿主内存压力；本轮未做负载性能测试。

实施时在 `src/main/devices/index.ts` 的配置更新流程加入停止状态、原盘保留及快照失效处理；`src/main/emulator/settings.ts` 与配置读取能力区分输入范围和镜像实际最低值；启动后校验有效 RAM，不能只回显表单值。继续复用 `src/shared/settings-contract.ts` 的 RAM/heap 联动校验，但还需验证 Emulator 对 heap 的调整。现有表单范围上限 32 GiB 未在本轮测试中覆盖。

## 4. 调研单元：内部存储扩容与缩容

### 4.1 该部分要做什么

判断已有 userdata 数据盘是否能改变容量并保留内容，并在保存前检查目标容量，不支持或无法确认时拦截。区分三件事：配置里的目标值、来宾实际容量、宿主文件占用；缩小配置值不代表释放宿主磁盘。

### 4.2 项目现状

- [设置契约](../../../src/shared/settings-contract.ts)只把 `internalStorageMiB` 写为 `disk.dataPartition.size`；没有迁移 qcow2 写入层、调整已有文件系统或验证真实容量的实现。
- [设置能力](../../../src/main/emulator/settings.ts)默认 6144 MiB、允许 2048—65536 MiB；[表单](../../../src/renderer/src/components/wizard/SettingsForm.tsx)称其为“userdata 初始容量”。创建路径不能直接证明编辑路径安全。
- [AVD 配置写入](../../../src/main/emulator/avd.ts)可原子替换单个 config.ini，但不构成数据盘备份或迁移事务。
- 本机停机检测：API 32 的 `userdata-qemu.img` 是 raw、上层为 qcow2；API 34 的基础文件自身是 qcow2，上面还有 qcow2 写入层。两个文件即使名字一样，实际格式也不同。
- 现有容量校验只有范围与整数检查，没有读取目标设备数据盘的缩容能力判断。SDK 工具只读探查核实：qemu-img 为 `2.12.0(v2.12.0-19097-g85fa07f04ef)`，支持 `info --output=json --backing-chain`；resize2fs/e2fsck 为 **1.42.13（17-May-2015）**。工具存在不等于本应用已有无损缩容执行器。

### 4.3 候选方案

**方案 A：只改 disk.dataPartition.size，依赖下次启动扩缩**

- 原理：复用创建字段映射，让 Emulator 自行处理已有数据盘。
- 来源：[AVD 存储设置](https://developer.android.com/studio/run/managing-avds)、[上游 main.cpp 的 resize 分支（首次读取 blob ce784d98404839425c58a29efd7f4d727ea66388）](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android-qemu2-glue/main.cpp)。
- 适配：成本最低，但上游只对识别为 ext4 且目标更大的基础文件调用 resize，成功后删除同名 `.qcow2`。该路径没有通用缩容保证，也未保留所有写入层的最新数据。

**方案 B：备份完整磁盘链后，离线合并、扩容并验证**

- 原理：停止设备，将有效 qcow2 链内容合并到独立副本，正确调整镜像与文件系统；连同密钥等关联文件保留回退副本，验证启动、容量和数据后才切换。扩容与缩容分别设计。
- 来源：[QEMU convert/commit/resize 和离线操作约束](https://www.qemu.org/docs/master/tools/qemu-img.html)、[Android ext4_resize 的 e2fsck/resize2fs 调用](https://android.googlesource.com/platform/external/qemu/+/refs/heads/emu-master-qemu/android/android-emu/android/filesystems/ext4_resize.cpp)。
- 适配：本机有 qemu-img/e2fsck/resize2fs，可作为后续 PoC 起点；qcow2 链、加密分区与文件系统识别使其无法照搬几条命令。本轮没有验证这条无损迁移路线。

**方案 C：清空用户数据后按新容量初始化**

- 原理：用同一机型和镜像生成新 userdata，安装的应用、登录与文件需要重新准备。
- 来源：[Emulator userdata 初始化与 wipe-data](https://developer.android.com/studio/run/emulator-commandline#avd-data-directory)。
- 适配：属于单独的重置功能；用户没有同意清数据，不能藏在“保存配置”里。即使重置，仍需核验镜像最低容量及实际生效值。

### 4.4 可行性分析

| 维度     | A：直接改配置                      | B：离线迁移                                | C：重新初始化                          |
| -------- | ---------------------------------- | ------------------------------------------ | -------------------------------------- |
| 技术匹配 | 实测扩容丢样本或不生效，缩容不生效 | 理论路径存在；加密与格式组合待验证         | 可重新准备空数据盘，受镜像容量规则约束 |
| 规则冲突 | 无法满足默认保留数据的目标         | 必须停机、隔离、可回退；验证前不能宣称无损 | 本期已排除清数据重置                   |
| 成本     | 表面低，数据风险高                 | 高，需要完整备份、空间预检与中断恢复       | 代码成本中，用户恢复测试环境成本高     |

正式实测先保持 RAM 2048 MiB，分别把存储配置从 6144 改为 8192，再改为 4096。表中容量为停机检测的镜像虚拟容量；`df` 总块数受文件系统开销影响。

| 镜像   | 操作/配置（MiB） | 实际虚拟容量（GiB） | df /data 总 1K 块 | 三项样本                        | 结果                        |
| ------ | ---------------- | ------------------: | ----------------: | ------------------------------- | --------------------------- |
| API 32 | 基线 6144        |                   6 |           6094400 | 保留                            | raw 基础盘 + qcow2 写入层   |
| API 32 | 扩容至 8192      |                   8 |           8158648 | 两个文件消失，自定义设置变 null | 扩容生效，数据样本丢失      |
| API 34 | 基线 6144        |                   6 |           6082144 | 保留                            | qcow2 基础盘 + qcow2 写入层 |
| API 34 | 扩容至 8192      |                   6 |           6082144 | 保留                            | 配置改变，容量未改变        |
| API 34 | 缩容配置为 4096  |                   6 |           6082144 | 保留                            | 未缩容                      |

API 32 扩容日志出现 `userdata partition is resized from 6144 M to 8192 M`，与上游 ext4 扩容及删除 qcow2 写入层的逻辑一致；“丢失样本”是本机实测，“写入层丢失解释”由源码推断。API 34 的 qcow2 基础文件不满足上述 ext4 检查，与容量不变的观察一致。两种结果都说明：保存成功或能再次启动，不等于无损修改成功。

API 32 第一次调小配置时，实际仍为 8 GiB；样本已经在前一步扩容时丢失，不能把该轮样本为空归因于缩容。为隔离缩容，另在 8 GiB 状态重新写入三项样本，再仅改为 4096 MiB 复测，结果记录在下方。

独立缩容复测：配置 8192 → 4096 MiB，raw 基础盘与 qcow2 写入层的虚拟容量均仍为 8589934592 字节（8 GiB），`df /data` 总块数仍为 8158648；冷启动成功，两个文件和自定义设置均保留。数据保留的原因包含“实际没有缩容”，不能据此认定真正缩容安全。

QEMU 官方要求实际缩小镜像前先缩文件系统及分区，否则会丢数据。Android 的加密、镜像链和文件系统组合还会增加限制；即便已用空间小于目标值，也不能直接截短镜像。宿主实际占用与虚拟容量也是不同指标。[QEMU resize/info](https://www.qemu.org/docs/master/tools/qemu-img.html)

**后续可研究缩容预检，本期不实现。** 本机 resize2fs 对应的 v1.42.13 上游说明：`-P` 给出最小容量估算，并记有估算可能出错的限制，尤其涉及 1K/2K 块大小；它不是“安全缩容”证明。[resize2fs 1.42.13 手册源码](https://github.com/tytso/e2fsprogs/blob/v1.42.13/resize/resize2fs.8.in)

| 判定方式                                                        | 能否作为放行依据                                 | 成本与用途                                     |
| --------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------------------- |
| 已用空间小于目标容量，或只检查配置值                            | 否；没有证明文件系统、镜像链与缩容执行路径可用   | 低，可用于提前提示，不能保证数据安全           |
| 读取实际数据盘并匹配已验证的版本/格式/文件系统/加密组合及执行器 | 可以作为保守能力门禁；未知组合拦截               | 后续可选；当前没有可放行的存储缩容路径         |
| 在完整隔离副本上实际缩容，检查数据与启动后再迁移                | 是后续建立支持范围的验证方式，仍需切换与恢复事务 | 高，属于离线迁移 PoC，不作为普通保存的试探动作 |

元数据加密可以使 userdata 的文件系统信息只有取得密钥后才能读取；不能因宿主侧读不到 ext4 就误判为空盘，也不能看到来宾挂载 ext4 就断言宿主工具能直接缩它。[Android 元数据加密](https://source.android.com/docs/security/features/encryption/metadata)

### 4.5 结论与实施建议

结论：**借鉴思路手写**。本期只实现已有设备的存储只读与保存守卫，不实现容量调整。第 4.3—4.4 节保留扩缩容候选方案及实测依据，作为后续研究资料，不进入当前实现范围。

用户已确认：已有设备不允许修改内部存储容量，不区分是否已经初始化；扩容、缩容、清数据重置和离线迁移均不在本期。创建时仍可选择初始容量。

| 文件                                                  | 本期实施要求                                                                                                         |
| ----------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `src/renderer/src/components/wizard/SettingsForm.tsx` | 创建时保留容量输入；编辑时显示原存储配置并只读，提示“已有模拟器暂不支持修改内部存储”                                 |
| `src/shared/types.ts`、编辑能力接口                   | 返回存储只读及中文原因；创建能力和编辑能力分别裁定，不因共用表单开放存储修改                                         |
| `src/main/devices/index.ts`                           | 在任何写入前检查容量字段是否实际变更，变更则拒绝；只改名称、RAM 或其他字段时保持原容量                               |
| `src/main/emulator/avd.ts`、编辑配置映射              | 编辑写入白名单排除 `disk.dataPartition.size`；不能直接应用包含该键的完整创建 patch，避免用旧值或新建默认值覆盖原配置 |

存储变更检查以 main 读取的可信原配置快照为依据，不能只依赖前端 disabled。legacy 或外部修改造成值不明时保留旧值，不自动补写创建默认容量；已有配置与真实数据盘容量不一致，也不借普通编辑修正。错误返回具体字段，保留其他编辑草稿。

本期无需新增 qemu-img 容量探查、文件系统最小值估算、缩容支持表或迁移执行器。未来若重新开放存储修改，再验证完整磁盘链、文件系统、加密、目标容量、备份与失败恢复；未初始化参数调整也需届时重新定义范围。不能从 `snapshotReadyAt=null` 推定从未初始化数据盘。

RAM 扩缩继续按第 3 节实施：校验镜像有效最低 RAM 与 heap 联动，停止后保存、下次冷启动。存储只读不影响 RAM 或其他允许字段的编辑。涉及界面布局与视觉时走 impeccable 技能。

## 6. 风险与开放问题

- **内部存储的交付边界。** 用户已确认本期固定已有设备的容量，包含尚未首次启动的设备；存储只读与 main 拒绝变更均需验收。容量探查、扩缩容迁移和清数据重置不在本期。
- **实测边界。** 第 3、4 节覆盖当前 Emulator 与两个 AOSP arm64 镜像；未覆盖 Google APIs/Play、其他 API、文件系统或版本，也未做真实应用及账号登录验收。不能推广为全部镜像保证。
- **RAM 的行为变化。** 缩小内存会改变被测环境，低内存回收可能影响测试；数据盘样本保留不代表运行中的任务、内存缓存和未保存状态保留。
- **事务与迁移恢复。** config 和元数据分别落盘，需要失败/中断恢复；固定机型和镜像后仍不能只改 JSON。配置相关快照不能替代完整数据盘备份；容量迁移失败或中断时，恢复须包含关联写入层与密钥。
- **回填与资源缺失。** legacy、外部 config 修改、已撤走皮肤/摄像头或过期画像须定位说明；旧画像仅用于生成能力，不应触发重新选择机型。回填还需区分配置目标与实际资源，避免 RAM 自动抬高、存储未变化仍显示“已生效”。
- **已有门槛。** Quick Boot 和摄像头取景/签名权限等仍按 [向导验收遗留](../../notes/issue/2026-10/2026-10-06-wizard-plan-remaining-acceptance.md) 跟踪。
- **实施范围。** 后续新 plan 聚焦名称、附加设置、编辑状态及跨文件更新，不包含画像/镜像迁移或整台 AVD 重建。本轮仅合并调研结论，未修改 src、旧 stage 或 plan 状态。
