# 安卓模拟器节省空间与共享 SDK 调研报告

> 创建时间：2026-10-08 11:22:23（Asia/Shanghai，与文件名时间戳一致）
> 需求来源：官方模拟器和 SDK 占盘较大，分析更省空间的第三方软件，以及与 Android Studio 共用模拟器系统的可行性。
> 调研单元：2 个
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

减少测试人员运行本项目所需的硬盘空间，保留多设备、多账号隔离和应用内投屏操控。分别评估更换第三方模拟器，以及复用 Android Studio 已有资源。

**推荐先支持“共用官方 SDK／系统镜像，AVD 数据各自独立”，第三方作为后续可选接入。** 如果希望连设备数据盘也只保留一份，可另做“连接 Studio 已启动设备”，由 Studio 管生命周期。

本机两套 SDK 约为 22 GiB 和 16 GiB，但已装镜像包没有重合。共享可避免今后重复安装；当前不能把项目 SDK 的 16 GiB 全部算成可直接回收的重复空间。第三方是否更省，需要按相同系统需求和设备数实测。

### 1.2 未知点清单

- [x] 空间主要用在哪里？本机系统镜像占 SDK 的大部分，详见 3.2。
- [x] 哪些第三方值得比较？Genymotion、MuMu for Mac 可评估；BlueStacks Air 缺少省盘优势证据，详见 2.3—2.4。
- [x] 第三方能否直接替换？投屏层有复用接缝，AVD 创建、配置、启停和对账需要适配，详见 2.2、2.5。
- [x] 与 Studio 能共用什么？工具、只读系统镜像、ADB 服务均可复用；可写设备数据应保持独立，详见 3.3。
- [x] 能否省掉第二份设备数据盘？连接同一个已运行设备可避免额外新建 AVD，但两处操作会影响同一份登录态，详见方案 C。
- [x] 现在改路径是否就能用？不能，根路径、Java 布局、权限和镜像核验都有现有约束，详见 3.2、3.5。

### 1.3 拆分判断

拆为“第三方替代”和“官方资源共用”两个单元。两者可独立评估；若以后接入第三方，可复用第二单元提出的外部设备连接能力。本次只读盘点和查阅资料，未安装候选产品、启动设备或清理文件。

## 2. 调研单元：第三方模拟器替代

### 2.1 该部分要做什么

比较适合本机 macOS arm64 环境的本地第三方产品，判断硬盘收益、测试覆盖和项目接入成本。厂商公布的最低可用空间、安装包体积、实际安装占用分别看待，不用其中一项替代另一项。

### 2.2 项目现状

| 依据                                                                                                           | 当前行为及影响                                                                                                               |
| -------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| [PRD](../../docs/PRD.md) E/F、4.2                                                                              | 一期要求官方 SDK 引导、独立 SDK 根与独立 AVD。第三方作为新增设备来源，需要修订相应产品契约。                                 |
| [架构规则](../../guidelines/architecture.md)                                                                   | 每会话独占设备数据，跨会话登录态互不影响。更换模拟器仍须保证实例独立。                                                       |
| [avd.ts](../../../src/main/emulator/avd.ts)、[runner.ts](../../../src/main/emulator/runner.ts)                 | 创建依赖 avdmanager；运行依赖官方 emulator、AVD 名及端口分配，停止回收本应用创建的进程组。第三方不能直接填进 emulator 路径。 |
| [settings.ts](../../../src/main/emulator/settings.ts)、[reconcile.ts](../../../src/main/emulator/reconcile.ts) | 设置与核验围绕官方画像、镜像包和 config.ini，第三方需要独立能力和健康检查。                                                  |
| [scrcpy/index.ts](../../../src/main/scrcpy/index.ts)、[transport.ts](../../../src/main/scrcpy/transport.ts)    | 投屏会话接受 deviceId、runId、serial，经 ADB 推送固定 3.3.3 server、转发并建立视频与控制流，是最可复用的部分。               |
| [package.json](../../../package.json)、[类型定义](../../../src/shared/types.ts)                                | Electron 39、React 19、zustand 5；DeviceMeta v2 假定每台设备有官方画像和镜像身份，尚无外部设备来源类型。                     |

因此，“厂商支持 ADB”只证明存在连接入口。能否使用本项目固定的 scrcpy-server、编码器、触控、中文输入、旋转及双设备切换，仍需验证。[scrcpy 官方说明](https://github.com/Genymobile/scrcpy)也将连接与输入权限列为前提；这里不把最新版功能当作本项目 3.3.3 的验收结果。

### 2.3 候选方案

**方案 A：Genymotion Desktop**

- 原理：厂商管理 Android 虚拟机，经 ADB 接入本项目；若需本项目内创建和启停，再适配 GMTool。
- 官方要求：支持 Mac Intel／Apple Silicon；列出的空间门槛为软件 300 MB、每台虚拟设备至少 2 GB。macOS 默认使用内置 QEMU，M 系列还要求 Rosetta。[安装与要求](https://docs.genymotion.com/quickstart/desktop_install/)
- 工具互通：可选择 Studio 的 SDK tools，主要解决 ADB 配套；这不等于复用 Google 的 AVD 或系统镜像。[ADB 设置](https://docs.genymotion.com/usage/desktop/general_settings/)
- 管理入口：GMTool 提供设备创建、列举、启停等命令。[GMTool](https://docs.genymotion.com/tools/desktop/gmtool/)
- 成本：免费版限个人用途，专业／商业环境不能按免费版估算；部分功能和完整 GMTool 命令还受版本授权限制。[产品方案](https://www.genymotion.com/product-desktop/)、[使用条款](https://www.genymotion.com/legal-terms-and-conditions/)
- 适配判断：适合列为测试用途的优先 PoC 候选。其自有 Android 镜像不是本项目精确 Google 镜像包的替身，API、Google 服务、ABI 和 16 KB 页需求要逐项对照。[ABI 说明](https://docs.genymotion.com/usage/desktop/install_apps/)

**方案 B：MuMuPlayer for Mac**

- 原理：用厂商虚拟设备，经 ADB 投屏；完整生命周期可研究其 mumutool。
- 平台：官方 Mac 安装说明面向 Apple Silicon，符合本机架构。[安装说明](https://www.mumuplayer.com/help/mac/install-mumuplayer-pro.html)
- 接口：官方开发者文档提供 mumutool 的设备查询、创建等入口，也有 ADB 和 Studio 调试说明。ADB 端口按设备发现，不把某个示例端口写死。[开发者功能](https://www.mumuplayer.com/tw/help/mac/developer-support-function.html)、[Studio 调试](https://www.mumuplayer.com/help/mac/debug-apps-with-android-studio-and-mumuplayer-pro.html)
- 体积：本次查到的官方资料没有提供可与本机相同测试条件比较的实际占用；不能承诺更省。
- 成本：国际站当前文档说明 Mac 版试用后需会员；地区、版本和购买渠道可能不同，落地时按实际版本确认。[会员说明](https://www.mumuplayer.com/help/mac/free-trial-and-membership.html)
- 适配判断：可作为日常应用功能测试候选；官方 API 组合、设备形态、Google 服务及编码器行为是否满足本项目，需要 PoC。已有 Studio 调试文章含 kill-server 步骤，本项目禁止照搬，会中断其他设备的共享服务。

**方案 C：BlueStacks Air**

- 原理：使用其自有 Android 运行环境，若接入本项目仍需外部设备适配。
- 官方安装要求列出 12 GB 可用空间，产品面向游戏运行。[系统要求](https://support.bluestacks.com/hc/en-us/articles/32272913555597-System-specifications-for-installing-BlueStacks-Air)
- 适配判断：12 GB 是空间要求，不是安装后实测占用。本次没有查到足以证明其在同等测试条件下更省盘、或能直接满足本项目管理能力的资料，因此不列为优先候选。

### 2.4 可行性分析

| 维度     | Genymotion                                   | MuMu for Mac                            | BlueStacks Air                   |
| -------- | -------------------------------------------- | --------------------------------------- | -------------------------------- |
| 技术匹配 | ADB、GMTool 有官方依据；需验本项目投屏链路   | ADB、mumutool 有官方依据；需验具体版本  | 本次未确认完整接入路径           |
| 硬盘收益 | 本体门槛较小，设备仍需 GB 级空间；收益未实测 | 没有同等条件的官方占用数据              | 12 GB 空间要求，缺少省盘优势证据 |
| 测试覆盖 | 自有镜像，需核对所需 API、ABI、服务及页大小  | 不能从能运行 APK 推定完整覆盖原测试矩阵 | 偏游戏场景，覆盖适配另验         |
| 规则冲突 | 新增来源需修订 PRD；独立实例可延续隔离       | 同左；不得照搬 kill-server              | 同左                             |
| 成本     | 商业许可、设备管理和能力映射适配             | 会员／地区版本、CLI 和能力映射适配      | 接口与覆盖证据不足，调研成本更高 |

**省盘成立的条件**是第三方确实满足所需测试矩阵，并能退役原来不再使用的资源。若同时保留 Studio、本项目官方 SDK，再新增第三方，短期总占用会增加。单系统第三方与多个 Android API 的官方安装对比，也不能证明运行引擎本身更省。

### 2.5 结论与实施建议

结论：**借鉴思路手写**。采用厂商已有模拟器与管理接口，自己实现项目适配层；不自研 Android 模拟器。优先做 Genymotion 或 MuMu 的小型 PoC，现阶段不建议仅为省盘更换默认后端。

落地分两步：

1. 先新增外部 ADB 设备连接：在 `src/main/devices/` 增加发现／连接模块；扩展 `src/shared/types.ts`、`src/main/store.ts` 的设备来源和权限，接到现有 scrcpy 会话。preload／IPC 保留白名单；renderer 增加连接入口和外部设备标识。外部来源起初只提供连接、断开，不套用官方 AVD 的删除和进程组停止逻辑。
2. PoC 通过后，再在 `src/main/` 增加厂商后端适配：查询、创建、启停、能力查询；由来源区分官方镜像与厂商系统身份。既有 avd／reconcile 继续负责官方设备，避免把厂商设备伪装成一个 Google 镜像包。

PoC 使用相同数量设备、相同 APK 和数据量，分别测安装后、首次启动后、安装应用后、多开后的 `du` 占用，并验证 ≥30fps／触摸 ≤150ms、中文输入、旋转、断连恢复与双设备隔离。第三方系统版本不能与原测试目标对应时，应记录覆盖缺口，不能只交一个体积数字。涉及界面时走 impeccable 技能。

## 3. 调研单元：与 Android Studio 共用官方资源

### 3.1 该部分要做什么

区分四层资源：Studio IDE、SDK 工具、系统镜像、每台 AVD 的可写数据。判断哪些可以共享、哪些共享会改变登录态隔离，以及本机当下能节省多少。

### 3.2 项目现状

**本机只读盘点，2026-10-08，macOS arm64。** 以下是 `du -h`／`du -sk` 的近似磁盘分配量，不是下载压缩包大小，也不是设备配置里的虚拟容量；APFS 克隆、快照等会影响最终可释放空间，不能直接相加当作全盘唯一物理占用。

| 位置                                                            | 当前占用 | 主要组成                                                                  |
| --------------------------------------------------------------- | -------: | ------------------------------------------------------------------------- |
| `/Applications/Android Studio.app`                              |  2.8 GiB | IDE 与配套运行时                                                          |
| `~/Library/Android/sdk`                                         |   22 GiB | system-images 约 17.4 GiB、NDK 约 2.8 GiB，另有工具及构建资源             |
| `~/.android/avd`                                                |  6.0 GiB | 当前看到一台 Studio AVD                                                   |
| `~/Library/Application Support/multi-session-device/AndroidSDK` |   16 GiB | system-images 约 14.0 GiB，工具／JRE 等约 1.6 GiB，另有 android-user 数据 |
| `~/Library/Application Support/multi-session-device/avd-home`   |  1.1 GiB | 当前看到两台项目 AVD                                                      |

这些数字说明：IDE 不是主要占盘项。项目 bootstrap 也没有安装完整 Android 开发 SDK：`SDK_PACKAGES` 只列 platform-tools 与 emulator，另装 JRE、cmdline-tools；镜像由向导按需下载。[sdk.ts](../../../src/main/emulator/sdk.ts)

已装镜像从 `system-images/*/*/*/source.properties` 读取，空目录不算已安装：

| SDK    | 镜像身份（均为 arm64-v8a）                                                                                          |
| ------ | ------------------------------------------------------------------------------------------------------------------- |
| Studio | android-36：google_apis、google_apis_playstore、google_apis_ps16k；android-36.1：google_apis、google_apis_playstore |
| 项目   | android-32/default；android-34/default；android-37.2/google_apis_playstore_ps16k                                    |

**两套已装包的路径身份交集为空。** 镜像只有 API、变体、ABI 等身份及修订相容时才谈得上共用；36 和 36.1、普通页和 16 KB 页、AOSP 和带 Play 的镜像不能当作重复项。[镜像身份实现](../../../src/main/emulator/catalog.ts)、[DeviceMeta](../../../src/shared/types.ts)

现有三个 `config.ini` 中，Studio AVD 引用 36.1 Play；两台项目 AVD 均引用 32/default。项目的 37.2 镜像约 8.2 GiB、34/default 约 1.7 GiB，在这两个已检查 AVD 根下未见引用，可列为后续保留需求核对对象。这不代表它们无用，也不排除其他路径的 AVD；本次没有执行卸载。

代码层面的阻力：

- [emulator/index.ts](../../../src/main/emulator/index.ts) 和 [devices/index.ts](../../../src/main/devices/index.ts) 都固定使用应用的 AndroidSDK；部分 SDK IPC 虽接受 root 参数，设备创建／启停等仍走默认根，设置尚未形成统一持久化路径。
- [sdk.ts](../../../src/main/emulator/sdk.ts) 将 Java 固定在 SDK 内的 `jre/Contents/Home`；Studio SDK 通常不含这个布局。本机 Studio JBR 的 Java 存在于 `/Applications/Android Studio.app/Contents/jbr/Contents/Home/bin/java`，但可否匹配所选工具仍须核验。
- [avd.ts](../../../src/main/emulator/avd.ts)、[runner.ts](../../../src/main/emulator/runner.ts) 把 ANDROID_USER_HOME／ANDROID_EMULATOR_HOME 放在 SDK 根下。外部 SDK 模式要改为应用自己的可写配置目录。
- [reconcile.ts](../../../src/main/emulator/reconcile.ts) 会解析真实路径，镜像逃出选定 SDK 根会被拒绝。把某个镜像目录软链接到 Studio SDK 不是现有代码支持的切换方案；命令行工具软链接还出现过根推断问题，见[历史记录](../issue/2026-10/2026-10-04-avdmanager-sdk-root-null.md)。
- [adb.ts](../../../src/main/emulator/adb.ts) 已优先选择用户 adb，复用 5037；它只覆盖运行时总线，不会自动合并两套 SDK。

### 3.3 候选方案

**方案 A：继续独立 SDK，精简资源，不安装 Studio IDE**

- 原理：保留当前官方引擎，只安装运行／创建设备所需工具和目标镜像。只运行现成设备时对工具的需求还可更少；本项目动态创建和画像读取目前仍需 cmdline-tools 与 Java。
- 官方 SDK 工具可独立安装，不要求完整 IDE。[SDK 管理文档](https://developer.android.com/tools/sdkmanager)
- 收益：没装 Studio 的用户不会被要求额外装 IDE、NDK、CMake、build-tools；有 Studio 且仍需开发的用户不因此省掉这些开发资源。当前项目已经采用精简安装，进一步收益主要来自减少不再需要的镜像、设备数据和快照。
- 适配：最贴合现有 PRD。可以增加资源占用与引用展示；已经初始化的数据盘不能靠调小容量配置保证缩小，见[存储调整实测](./20261008104140-已有模拟器配置编辑.md#44-可行性分析)。

**方案 B：共用 SDK／系统镜像，保留项目独立 AVD——推荐**

- 原理：本项目引用 `~/Library/Android/sdk` 的 emulator、tools 和已装系统镜像，仍将每台设备的可写数据放在自己的 avd-home。
- 官方依据：同类 AVD 的系统文件是共享只读资源，用户数据目录独立；SDK 根与 AVD 根可以分别指定。[系统与数据目录](https://developer.android.com/studio/run/emulator-commandline#understand-the-default-directories-and-files)、[环境变量](https://developer.android.com/tools/variables)
- 预期效果：Studio Device Manager 仍不纳管项目设备定义；运行中的项目设备经共享 ADB 成为部署目标。账号隔离依靠独立数据盘，不要求系统镜像各复制一份。
- 成本边界：只读使用外部 SDK 包；缺包时让用户在 Studio 安装，或切回应用托管模式。项目不自动升级、下载覆盖或卸载外部 SDK，避免删除 Studio 仍在使用的资源。
- 收益计算：可退役的重复工具 + 真正重合且可迁移的镜像；每个独立账号所需的可写数据盘继续保留。把两边不同镜像搬进一个目录只改变位置，不会减少镜像总量。

本机工具／JRE 合计约 1.6 GiB，全部满足复用条件、旧资源不再被引用且安全退役后，才是这一部分的大致节省上限。不能将它当成立即可删除量：Studio emulator 为 **36.1.9**，项目为 **37.2.12**；项目 37.2 镜像的 source.properties 声明 `Pkg.Dependencies=emulator#36.5.11`，Studio 当前版本低于其声明要求。cmdline-tools 两边均为 23.0，platform-tools 分别为 36.0.0／37.0.1。切换前需核验或由用户升级共享工具，不静默升级。

还可设计“应用自有工具 + 外部镜像根”，通过官方 `-sysdir` 引用系统镜像，但创建、包扫描、对账和来源记录都要拆开工具根与镜像根，比整套外部 SDK 模式更复杂。本机镜像目前无重合，首批不建议为此增加混合模式。

**方案 C：连接 Studio 已启动的同一台设备**

- 原理：由 Studio 启动和停止 AVD，本项目按 ADB serial 连接并投屏，不另创一份设备。现有 scrcpy 会话接口支持以 serial 建立连接，但设备发现与外部来源编排尚未实现。[scrcpy 会话入口](../../../src/main/scrcpy/index.ts)、[共享 ADB 实现](../../../src/main/emulator/adb.ts)
- 收益：省掉为同一测试用途额外创建的设备数据盘；若完全采用外部设备，本应用可以进入仅 ADB／投屏模式，无需额外下载自己的模拟器和系统镜像。现有资源仍需确认不再使用后才能退役。
- 代价：两边操作影响同一台设备、同一份账号和应用数据，不能把一个 serial 当成两个隔离账号会话。项目退出只断开自己的投屏和转发；初期不给外部设备创建、删除、改配置和停止权限。
- 变体判断：让两边都直接管理同一个可写 AVD 目录，虽然可以研究串行使用，但会引入启动锁、配置、快照及误删责任，并违背“Studio 不能改删项目设备”的现有约定。首批优先连接既有进程，不采用双边共同管理目录。

### 3.4 可行性分析

| 维度         | A：独立精简                      | B：共用 SDK，独立 AVD                                         | C：连接已启动设备                                               |
| ------------ | -------------------------------- | ------------------------------------------------------------- | --------------------------------------------------------------- |
| 技术匹配     | 已有主体能力                     | 官方资源布局支持，需要统一路径和 Java 解析                    | 投屏可复用，需要设备发现、来源及连接状态                        |
| 节省来源     | 减少不需要的镜像／设备／快照     | 去掉重复工具和真正重合镜像，避免后续重复安装                  | 避免额外 SDK／镜像下载和第二份同用途设备数据盘                  |
| 当前实际限制 | 已经精简，不能再承诺大幅缩小工具 | 本机无重合镜像，且 emulator 版本不同                          | 不能提供两份独立账号环境；外部关闭会断连                        |
| 规则冲突     | 无新增冲突                       | 需调整“独立 SDK 根”；AVD 隔离可保留，镜像可用性由外部共同影响 | 需增加外部设备契约，不能把外部设备纳入项目 AVD 的删除／隔离承诺 |
| 相对改动量   | 小；若新增占用展示，需实现统计   | 中，覆盖路径、配置、核验和写权限                              | 中，覆盖来源模型、发现、连接与工具条行为                        |

对本机，优先核对大镜像的保留需求，比只省几十 MB 的 adb 更有价值。路径迁到外置盘可以释放内置盘压力，但总占用不减少；下载镜像时也仍需压缩包与解压临时空间。[下载实现](../../../src/main/emulator/downloader.ts)

### 3.5 结论与实施建议

结论：**采用现成方案**。使用官方 SDK、系统镜像与独立 AVD 的资源模型，以方案 B 作为首选产品方向；项目负责路径、权限和迁移配置。方案 A 保留为无 Studio 用户的默认模式，方案 C 作为可选外部设备能力。

建议按以下顺序落地：

1. **明确契约。** PRD 的“独立 SDK”改为默认应用托管、可显式选择外部 SDK；每台项目设备的可写数据仍独立。外部 SDK 模式标注镜像增删／升级由外部管理，外部删镜像可能使项目设备不可用。
2. **统一路径来源。** 在 `src/main/emulator/` 新增运行环境解析模块，统一返回 SDK 根、Java、avdmanager、emulator、adb、应用配置根和 AVD 根。替换 index、devices、avd、runner、profiles／profileMetadata 中的固定拼接；Java 独立解析，检测 JBR 或已安装的兼容运行时，缺 cmdline-tools 给出明确原因。
3. **持久化模式与权限。** 扩展 `src/shared/types.ts` 和 SDK 设置 IPC／preload，保存 managed／external 模式及已核验路径。外部模式在 main 层禁止包安装、卸载、升级和许可文件写入；android-user、缓存等写到 userData。镜像核验允许选定的可信 SDK 根，继续保留 realpath 与越界检查。
4. **先服务新设备，既有设备显式迁移。** 给设备保存运行环境绑定，不能全局切一个路径就把旧 AVD 指向不存在的包。迁移时停机、核对精确包及 revision、关联镜像链与配置，备份后更新引用、冷启动验证应用数据；新模式验收前保留原资源和回退入口。不能把 API 32 数据盘直接改挂到 API 36 当作迁移。
5. **验证共存与收益。** 覆盖外部 SDK 缺 Java／cmdline-tools、版本不匹配、被升级／移除、只读目录、重启恢复、两边同时运行各自 AVD、删除项目设备不影响 Studio、外部 SDK 无包变更。迁移完成再用同口径 `du` 量收益；未过验收不自动清理旧 SDK。

方案 C 和第三方可以共用一套外部设备来源模型，避免两次改造。设置及向导 UI 涉及布局时走 impeccable 技能。本报告未修改 PRD、stage、plan 或业务代码，实施时另立计划。

## 4. 风险与开放问题

- **第三方体积尚无同机实测。** 最低空间要求不能当作真实安装量，也不能把测试矩阵缩水所得的空间当成无代价优化。PoC 应先定所需 API、Google 服务、ABI、页大小和设备数。
- **共用会扩大可用性依赖。** 独立 AVD 能保住账号数据边界；Studio 升级工具或删除共享镜像仍可能影响项目启动，需要版本诊断、启动前检查和回退。
- **已有数据迁移不能只改 SDK 根。** 数据盘可能包含镜像链和路径引用；保留登录态要做独立迁移验证，不用 wipe-data 充当修复。此前存储扩缩的实测也不能代替本次路径迁移验收。
- **省盘与虚拟容量不同。** 不通过降低 RAM 解决硬盘问题；不假设调小 dataPartition 配置会回收已用空间。快照策略还要尊重当前 Quick Boot 未完成的验收门槛。[运行快照](../../docs/architecture/2026-10-08-android-runtime.md)
- **外部设备连接有操作语义差异。** 断开投屏不等于关机；同一个外部 serial 只能绑定一份会话身份，并处理外部停机、重连和控制冲突。
- **资料与版本边界。** 第三方文档、会员方案和官方工具接口可能更新。实现时以实际安装版本核验；MuMu 部分开发者文章较早，不能仅凭文章推定当前版本接口完全一致。本次不自动升级任何工具。
