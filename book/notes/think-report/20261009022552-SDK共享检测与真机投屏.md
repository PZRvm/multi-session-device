# SDK 共享检测与真机投屏 功能调研报告

> 创建时间：2026-10-09 02:25:52（Asia/Shanghai，与文件名时间戳一致）
> 需求来源：设置里检测本机 Android Studio/SDK，能拿到则共享、拿不到则选路径（带默认值）；另立 stage06 集成 QtScrcpy 式投屏（免安装依赖、USB + 无线调试、局域网扫描 + 配对码）。
> 调研单元：2 个
> 状态：调研完成，假设全部批复（2026-10-09），可衔接 write-plan（未实施）

## 1. 需求理解

### 1.1 功能目标

**单元一（stage05 设置增强）**：设置窗单独一条「SDK 来源」，三态：应用托管（默认）/ 共享 Studio SDK（检测到才出现，只读使用）/ 自选路径（应用全权管理的可写根，如 Windows D 盘，恒可选；输入框预填平台默认路径）。测试人员借此省一份 SDK 磁盘、复用已装镜像。产品方向与 [2026-10-08 共享 SDK 调研](./20261008112223-安卓模拟器节省空间与共享SDK.md) 单元三方案 B 一致，本次补齐它缺的「自动检测」。

**单元二（stage06 真机接入）**：物理设备作为新设备来源——USB 插入即见、可投屏操控；无线调试支持扫描同网段设备、选 IP 填端口（未配对加配对码）、已配对直连。**QtScrcpy 不需要引入**：项目已内置 scrcpy-server 3.3.3（随包分发 + SHA-256 校验）与 @yume-chan 投屏栈，画面 + 控制已在应用内；真实增量只是「设备来源 + adb 无线发现/配对/连接」这一层。

### 1.2 未知点清单

- [x] macOS/Windows 能否检测 Studio 与其 SDK？→ 能，见 2.3 方案 A。
- [x] 改过路径的 Studio SDK 能否自动识别、路径归属如何判定？→ 能：Studio 配置文件记录它实际在用的路径（首选线索）→ 环境变量 → 默认目录 → PATH 反推 → 手选，逐级核验；SDK 目录自身无归属印记，归属＝实际路径与选中路径 realpath 对比。见 2.3 方案 B、2.5。
- [x] 自选非 Studio 路径（如 D 盘）能否操作包？→ 能，该模式是应用可写根。见假设 3。
- [x] 共享后哪些固定路径要松绑？→ SDK 根、Java 布局、avd-user 目录、reconcile realpath、adb 候选五处，见 2.2。
- [x] 要不要 QtScrcpy？→ 不要，投屏栈现成。见 3.2。
- [x] 无线扫描怎么做、已配对怎么判？→ `adb mdns services` 列 `_adb-tls-connect`（已配对直连）/`_adb-tls-pairing`（待配对）+ 手动 IP 兜底；platform-tools 34–36 的 mDNS 回归是已知风险。见 3.3—3.4。
- [x] USB 要多少额外工作？→ `adb devices` 即可复用投屏，大头是设备来源模型与未授权态 UX。见 3.5。

### 1.3 拆分判断

拆为两个无代码依赖、可并行的单元：**单元一「Studio/SDK 检测与共享设置」**、**单元二「真机接入与投屏」**。单元一有阶段内依赖：设置窗本体（stage05 `[suggested]` 步骤，plan 待写）必须先行。

## 2. 调研单元：Android Studio SDK 检测与共享设置

### 2.1 该部分要做什么

检测（Studio 安装 + SDK 定位）、设置项（三态 + 默认值预填）、路径解析接入（运行环境按所选根统一解析）。**不做**：既有设备数据迁移（前报告 §3.5 步骤 4 另立任务）；对 Studio SDK 写任何东西（共享模式恒只读；自选路径是应用自有可写根，不在此限）。

### 2.2 项目现状

- [PRD](../../docs/PRD.md) §2 E「SDK 独立引导」、§4「独立 SDK 根 + 独立 AVD 目录」——共享模式需先修订 PRD；§2.3 已规划设置窗「SDK 路径（高级项）」，本单元是它的具体化。
- [stage/05-功能完善.md](../../notes/summary/2026-10/2026-10-16-功能完善.md)：设置窗步骤 `[suggested]`、plan 待写——本单元排在其后。
- [sdk.ts](../../../src/main/emulator/sdk.ts)：`sdkPaths()` 把 Java 固定在 `<root>/jre/Contents/Home`（mac 布局），JRE/cmdline-tools 钉版 mac_arm64 下载——外部根没有这个布局，Java 需独立解析（Studio JBR 在 `<Studio.app>/Contents/jbr/Contents/Home`）。
- [adb.ts:118-131](../../../src/main/emulator/adb.ts)：`candidateAdbPaths()` 已含 `~/Library/Android/sdk/platform-tools/adb` 标准候选——共享模式下外部 platform-tools 天然进候选，但 Windows 分隔符与路径缺失。
- [devices/index.ts:105](../../../src/main/devices/index.ts)：SDK 根固定 `userData/AndroidSDK`；[reconcile.ts](../../../src/main/emulator/reconcile.ts) 对镜像做 realpath 越界检查——外部根须成为「选定可信根」才放行。
- 前报告 §3.2 的本机事实：Studio emulator **36.1.9** 落后项目 **37.2.12**，项目 37.2 镜像声明依赖 emulator#36.5.11——共享时部分镜像不可用，需版本诊断而非静默失败。

### 2.3 候选方案

**方案 A：借鉴 flutter_tools 检测思路自写（推荐）**

- 原理：Studio 检测——macOS 扫 `/Applications`、`~/Applications` 的 `Android Studio*.app`（3 秒超时 `mdfind 'kMDItemCFBundleIdentifier="com.google.android.studio*"'` 兜底）；Windows `reg query HKLM\SOFTWARE\Android Studio /v Path` + `%ProgramFiles%\Android\Android Studio`、`%LOCALAPPDATA%\Programs\Android Studio` 目录 + `%LOCALAPPDATA%\Google\AndroidStudio*\.home` 文件。SDK 定位——`ANDROID_HOME`/`ANDROID_SDK_ROOT` → 平台默认目录（macOS `~/Library/Android/sdk`；Windows `%LOCALAPPDATA%\Android\Sdk`）→「存在 platform-tools 或 licenses」核验。
- 来源：[flutter_tools android_studio.dart](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/android/android_studio.dart)、[android_sdk.dart](https://github.com/flutter/flutter/blob/master/packages/flutter_tools/lib/src/android/android_sdk.dart)、[Windows 注册表 Path 值](https://stackoverflow.com/questions/39381797/change-installation-directory-android-sdk)
- 适配点：纯 Node（fs 扫描 + reg query 子进程），main 新模块 + 注入接缝可单测，无新依赖。

**方案 B：解析 Studio 配置文件（并入 A 的检测链，作首选线索）**

- 原理：Studio 在设置里改过的 SDK 路径记录在配置目录 `options/other.xml` 类文件（Windows `%APPDATA%\Google\AndroidStudio<版本>\options\`，macOS `~/Library/Application Support/Google/AndroidStudio<版本>/options/`）——读到的就是「Studio 实际在用哪个 SDK」，安装向导里改的非默认路径同样在此。
- 来源：[Studio 配置目录官方文档](https://developer.android.com/studio/intro/studio-config)
- 边界：配置目录带版本号（多版本并存/残留时取最近使用或最高版本）、文件不保证存在、字段随版本漂移，不能单独依赖——失败逐级回落到环境变量 → 默认目录 → PATH 上 adb 反推 → 手选。

**方案 C：第三方「检测 SDK」npm 包**

- 看过不采用：普遍维护弱、只覆盖默认目录；自写百余行纯函数更便宜可测。

### 2.4 可行性分析

| 维度 | 方案 A（自写检测） | 方案 B（并入 A 检测链） |
| --- | --- | --- |
| 技术匹配 | 纯 Node + reg query；检测与核验分层，覆盖 Studio 未装/SDK 缺失/自定义路径 | 单独依赖易漂移；入链后负责「改过路径」与「归属判定」 |
| 规则冲突 | 共享 SDK 只读、自选可写，符合前报告约束；需修订 PRD「独立 SDK」 | 同左 |
| 成本 | 一个新模块 + 设置项；无依赖 | 少量解析代码，可靠性风险已由回落链兜住 |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**。检测/核验自写（flutter_tools 思路）；资源模型沿用前报告 §3.5——共享根只读、自选根为应用可写、AVD 数据恒独立。
- 落地路径（设置窗本体落地后）：
  1. 新增 `src/main/emulator/studioDetect.ts`：`detectStudioAndSdk(deps)` 返回 `{ studioFound, sdkCandidate|null, 默认路径 }`（fs/reg 接缝注入，macOS/Windows 两套候选表）；SDK 候选链：Studio 配置文件路径 → `ANDROID_HOME`/`ANDROID_SDK_ROOT` → 平台默认目录 → PATH 上 adb 反推 → 手选，每级核验后才采纳。另提供 `isStudioSdk(path)`：选中路径与 Studio 实际路径 realpath 对比，相等即按共享只读处理——归属由应用判定，用户无需分辨。
  2. 运行环境解析模块：统一返回 SDK 根、Java（内置 JRE ↔ Studio JBR 独立解析，缺失给中文可操作错误）、avdmanager/emulator/adb、avd-user 根。
  3. 设置持久化扩展（`src/shared/types.ts` + store + IPC）：`sdkMode: 'managed' | 'shared-studio' | 'custom'` + 已核验路径；新增 `sdk:detect-studio` 查询通道。
  4. 设置窗「SDK 来源」单独一条（走 impeccable 技能）：三态恒可选（默认托管）；检测到 Studio+SDK 时共享项一键采纳并展示核验结果（工具/镜像/emulator 版本差异）；自选路径预填默认值 + 目录选择器；手选路径若与 Studio 实际路径一致，自动提示并按只读共享处理。
  5. reconcile/镜像扫描接受「选定可信根」；共享模式禁用一切包安装/卸载/升级入口（向导只用已装镜像，下载项禁用并说明缺包去 Studio 装）；托管/自选保留完整包操作。

## 3. 调研单元：真机接入与投屏（stage06）

### 3.1 该部分要做什么

物理设备作为新设备来源：USB（插入即见）与无线（扫描/手动 IP + 端口 [+ 配对码]）连接、连接管理、复用现有投屏操控链路。**不做**：测试辅助四件套对真机的逐项适配（后续批次）、iOS、账号隔离承诺。

### 3.2 项目现状

- [package.json:30-36](../../../package.json)：`@yume-chan/adb`、`adb-scrcpy`、`scrcpy`、`scrcpy-decoder-webcodecs` 已在依赖——投屏栈现成，QtScrcpy（Qt/C++）与 Electron/TS 架构不匹配且能力重复，不引入。
- [scrcpy/index.ts:421-459](../../../src/main/scrcpy/index.ts)：`ensureSession({id, runId, serial})` 只认 serial；[transport.ts:122-163](../../../src/main/scrcpy/transport.ts) 走 `adb -s <serial> push/forward/app_process`——serial 为 `ip:port` 语义不变，无线设备无需改投屏层。
- [adb.ts](../../../src/main/emulator/adb.ts)：`probeServer`/`ensureSharedServer`（复用共享 5037 server，绝不 kill-server）/`listAdbSerials`（只收 `device` 态）——pair/connect/mdns 直接加命令封装；`unauthorized`/`offline` 态解析需新增。
- [ipc/index.ts:43-51](../../../src/main/ipc/index.ts)：流会话桥绑 emulator runner 事件——外部设备没有 runner，需要「激活即建会话」的第二条桥。
- [PRD](../../docs/PRD.md) §2.4 Non-Goals 明列「真机（USB 物理设备）支持」——stage06 立项需先修订 PRD。
- 设备模型（[types.ts](../../../src/shared/types.ts) DeviceMeta v2）假定官方画像与镜像身份——外部设备需要独立的来源/状态类型。

### 3.3 候选方案

**方案 A：复用共享 adb server，adb CLI 实现 pair/connect/mdns（推荐）**

- 原理：USB 插入即出现在 `adb devices`；无线走官方 Android 11+ 流程：设备开「无线调试」→ `adb mdns services` 列出 `_adb-tls-connect._tcp`（已配对，直接 `adb connect ip:port`）或 `_adb-tls-pairing._tcp`（设备正显示配对码）→ 未配对 `adb pair ip:port <配对码>`（配对码可作参数免交互）。连接端口动态，从 mDNS 或设备界面读取。老设备（≤10）无配对流程，仅支持已处 `tcpip 5555` 的直连。投屏复用现有 scrcpy 管理器，serial 直接可用。
- 来源：[官方 adb 文档（Wi-Fi 连接与 mdns）](https://developer.android.com/tools/adb)、[platform-tools 发行注记（37 删 openscreen、改 LIBADBMDNS 后端）](https://developer.android.com/tools/releases/platform-tools)、[mDNS 空结果回归 issue 330179635](https://issuetracker.google.com/issues/330179635)
- 适配点：全部经现有 `runAdb()` 封装；不碰 kill-server 红线；无新依赖。

**方案 B：@yume-chan Tango 纯 TS 直连 adbd**

- 来源：[ya-webadb](https://github.com/yume-chan/ya-webadb)、[Tango TCP 指南](https://tangoadb.dev/tango/daemon/tcp/enable)
- 看过不采用：与「共享 5037、绝不重启」架构相悖、形成双 adb 栈；无线配对（SPAKE2/TLS）支持未见文档证实；现有链路已验证。

**方案 C：捆绑 scrcpy 桌面版二进制**

- 看过不采用：原生窗口游离于应用画布外，无法复用设备画布、GopCache 后台恢复、应用内输入注入与剪贴板；server 侧已钉版内置（Apache-2.0）。

### 3.4 可行性分析

| 维度 | 方案 A（adb CLI + 现有栈） | 方案 B（Tango 直连） | 方案 C（捆绑桌面版） |
| --- | --- | --- | --- |
| 技术匹配 | 发现/配对/连接/投屏全链路有官方依据与现成实现 | 配对支持未证实；桌面端 USB 本就绕不开 adb | 覆盖投屏但形态不符 |
| 规则冲突 | 无（不碰共享 server 红线） | 与共享 server 架构冲突 | 无 |
| 成本 | 只加设备来源层与 IPC；风险集中在 mDNS 兼容 | 双栈维护 + 协议自研 | 三平台二进制分发维护 |

### 3.5 结论与实施建议

- 结论：**采用现成方案**（adb CLI 三件套 + 既有投屏栈），手写只有「外部设备来源」薄层。
- 落地路径：
  1. PRD 修订（移除真机 Non-Goal，注明无账号隔离承诺）+ stage06 阶段文档由用户建立（stage 人主导）。
  2. `src/shared/types.ts`：外部设备来源类型（serial、usb/wireless、device/unauthorized/offline/connecting）。
  3. `src/main/devices/external.ts`：`listExternal`（解析 `adb devices -l` 全状态）、`pairDevice(ip, port, code)`、`connectDevice(ip, port)`（错误分类：拒绝＝端口/开关不对，认证失败＝需配对）、`disconnectDevice`、`scanWireless`（解析 `adb mdns services`）；接缝注入可单测。
  4. IPC 新增 `devices:external-*` 通道 + preload 白名单；scrcpy 桥加「激活即 ensureSession」第二条路（runId 用连接代次）。
  5. renderer 设备列表加「真机」区：USB 列表 + 未授权引导；无线连接器（扫描列表 / 手动 IP+端口 / 配对码表单，走 impeccable 技能）；外部设备只有连接、断开与投屏，无创建/删除/改配置。
  6. 验收：USB 插拔、未授权态、Android 11+ 配对→连接、已配对直连、≤10 tcpip 直连、投屏触控/中文输入/旋转、Wi-Fi 断连恢复、与模拟器并行互不干扰。

## 4. 风险与开放问题

- **mDNS 发现是最大不确定性**：platform-tools 34–36 的 openscreen 后端有广泛报告的「`adb mdns services` 空结果」回归，37 起修复；宿主 PATH 里的 adb 版本不可控，而应用不重启共享 server——手动 IP+端口必须是一等兜底，验收覆盖多版本 adb。
- **网络环境**：AP 隔离/访客网挡组播，扫描天然失效；连接端口动态变化，重连可能要重查。
- **共享 SDK 版本差异**：外部 emulator 可能低于项目镜像要求（37.2 镜像需 ≥36.5.11，Studio 36.1.9 不满足）——设置页亮出核验结果，不静默降级。
- **真机是共享状态**：无账号隔离；应用关闭只断投屏不关机，停止语义与模拟器不同，UI 文案要区分。
- **Windows 检测先行、验证滞后**：检测代码可先写（含单测），但应用一期 macOS only，Windows 真机验证依赖应用本身的 Windows 支持。

## 5. 已确认假设

> 2026-10-09 用户批复全部确认；二、三轮追问的结论（自选路径可写、归属自动判定、不做群控）已并入正文。

- [x] 假设 1：单元一排在设置窗本体落地之后（同一 plan 或紧随），不单独抢跑。
- [x] 假设 2：修订 PRD——「独立 SDK 根」改为默认托管、可显式共享/自选；「真机支持」移出 Non-Goals（macOS 先行）。

- [x] 假设 6：默认路径预填 macOS `~/Library/Android/sdk`、Windows `%LOCALAPPDATA%\Android\Sdk`（Studio 官方默认 SDK 位置，SDK 不随 Studio 装进 /Applications）；改过路径经检测链识别（2.3 方案 B）。
- [x] 假设 7：stage06 阶段文档由用户主导建立；本报告确认后我以 `[suggested]` 供步骤草稿。
