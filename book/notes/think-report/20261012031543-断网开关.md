### 2.3 候选方案

**方案 A（采用）：adb 命令组 + 定时读回轮询**

命令集（全部实测通过，API 36.1 模拟器）：

| 开关 | 下发 | 读回 |
| --- | --- | --- |
| 飞行模式 | `cmd connectivity airplane-mode enable\|disable` | 同命令无参 → `enabled`/`disabled` |
| Wi-Fi | `svc wifi enable\|disable` | `settings get global wifi_on` → `0`/`1`（瞬态 `2`） |
| 移动数据 | `svc data enable\|disable` | `settings get global mobile_data` → `0`/`1` |

原理：主进程对运行中设备每 1s 读三个值，值变化才推 renderer。三个读可合并进一次 `adb shell`（分号连接）——20ms×1 与 ×3 差别可忽略，实现批定。

来源：AOSP `ConnectivityService.java` 命令注册（android-9/10/11 三版源码 grep 确认，见 2.4）；本机两轮实测（见 2.4）。

**方案 B：svc 双刀替代飞行模式**——第一轮作为独立候选看过；第二轮实测语义后**并入方案 A 成为开关组**（svc 从「替代方案」变「组成部分」）：svc 双关也能断网，但飞行模式一条命令、设备 UI 概念一致、radio 恢复语义系统托管，仍是总开关首选。

**方案 C：emulator console 流量整形（`gsm data off` / `network speed`）**——只影响蜂窝模拟不切 WiFi 流量，不满足「真断网」，还需 console auth token 管理，**否**。

**同步机制候选（「能不能监听」的正面回答）**

- **轮询读回（定案）**：实测单发 20ms（本机 adb server 常驻，开销在进程 spawn）；**1s 间隔**（2026-10-12 用户定）——单设备占空比约 2%，并行上限数设备也就每秒 N × 20ms 量级，摊在主进程异步 I/O 上无感；值变化才推、稳态零消息零渲染。体验为「变化后 ≤1s 跟随」。轮询在途时不叠发（上一发未返回跳过本轮），设备高负载下命令变慢只会让当轮延后，不堆积。
- **logcat 流「监听」（实测排除）**：wifi 切换有 `WifiService: setWifiEnabled package=… enable=false` 可识别行，但飞行模式切换**没有任何稳定锚点行**（第二轮实测：清缓冲→切飞行→全量 grep 仅命中一条蓝牙侧日志）；且日志文案跨版本/厂商可变、需长驻流管理（挂断重连、设备停止清理）。为一个布尔值守这渠道不值。
- **设备端广播接收 app（原则排除）**：`AIRPLANE_MODE_CHANGED` 广播在设备上注册接收器可真监听，但要往被测设备装 APK——违背本项目对设备零侵入的原则，且模拟器/真机通吃的维护成本翻倍。
- **结论：adb 体系内不存在设置变化的订阅通道，轮询是标准且正确的做法**——不是性能妥协。

### 2.4 可行性分析

**第一轮实测记录**（本机 Medium_Phone_API_36.1 模拟器 emulator-5554，2026-10-12 凌晨，adb + UI 自动化全程留痕）：

1. 基线：`cmd connectivity airplane-mode` → `disabled`；`settings get global airplane_mode_on` → `0`；`ping 8.8.8.8` 通（rtt 184ms）。
2. `cmd connectivity airplane-mode enable` 后：读回 `enabled` / `1`；`ping 8.8.8.8` **100% 丢包——真断网**；期间 adb 读回与设备 UI 自动化照常（控制通道不受飞行模式影响）；设备快速设置面板与状态栏均显示飞行模式已开（UI 与命令态一致）。
3. `cmd connectivity airplane-mode disable` 可恢复（含网络恢复）。
4. **设备内（快速设置磁贴）手动关闭飞行模式后**：宿主侧两条读回命令即时变 `disabled` / `0`，ping 恢复——**设备内切换 → 宿主读回的同步实测成立**，延迟量级即轮询间隔。
5. 读命令延迟：3 次 `settings get` 均 20ms（本机 adb server 常驻）。

**第二轮实测记录**（同机重启后，2026-10-12 03:25–03:50，应监听追问与分 radio 扩容）：

1. `svc wifi disable` / `svc data disable` 均成功，分别置 `wifi_on=0` / `mobile_data=0`，读回即时；恢复命令对称有效。
2. **单关 wifi（数据开，等足 10s）→ ping 8.8.8.8 仍通（180ms）**——模拟器蜂窝真实路由流量；wifi→蜂窝 failover 有数秒瞬态（首发实验 2s 时曾读到 unreachable，为切换未完成的假象）。
3. **单关数据（wifi 开）→ ping 通**；**双 radio 全关 → `Network is unreachable`**。结合第一轮结论：飞行模式与双关是唯二真断网路径——飞行模式作为「断网」总开关的定位被实测强化，分 radio 开关定位为场景测试而非断网。
4. **设备内（Internet 面板 Wi-Fi 开关）手动切换 → 宿主 `settings get global wifi_on` 即时跟随**——分 radio 的双向同步同样成立。
5. **飞行模式开启时 svc 命令不被拒**：推 `svc wifi enable` 后 `wifi_on` 瞬时读 `2`（enabling 态），关飞行后按意愿恢复 `1`；关飞行模式本身把 radio 恢复到进入前状态（本轮 wifi 进入前已关故保持关、数据恢复开）——**恢复语义系统托管，应用读回为准即可，不自己建模**。
6. logcat 评估：清缓冲 → adb 切飞行模式 → 全量 grep `airplane` 仅一条蓝牙侧日志，无 ConnectivityService 稳定锚点行——logcat 监听通道正式排除。

**版本兼容（AOSP 源码证实）**：`services/core/java/com/android/server/ConnectivityService.java` 中 `case "airplane-mode"`（enable/disable/无参 get）在 [android-9.0.0_r1（约 5967 行）](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-9.0.0_r1/services/core/java/com/android/server/ConnectivityService.java)、[android-10.0.0_r1（约 7035 行）](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-10.0.0_r1/services/core/java/com/android/server/ConnectivityService.java)、[android-11.0.0_r1（约 7649 行）](https://github.com/aosp-mirror/platform_frameworks_base/blob/android-11.0.0_r1/services/core/java/com/android/server/ConnectivityService.java)三版源码 grep 均在（help 文本明确含「airplane-mode / Get airplane mode.」）；API 36.1 实测通过。`svc` 命令族历史更古老，不构成新约束。本项目设备范围（模拟器 android-3x、真机 API 32+）全覆盖，无需旧版兜底。

| 维度 | A 命令组 + 轮询 | C console 整形 |
| --- | --- | --- |
| 技术匹配 | Android 9+ 全覆盖；断网语义真（飞行/双关）；场景语义真（单 radio）；双向同步两轮实证 | 不真断网（WiFi 不切），**直接否** |

### 2.5 结论与实施建议

- **结论：采用现成方案（A）**——三组官方 shell 命令 + 轮询读回，零新依赖，PRD 预埋口径经两轮实测双向成立。
- **落地路径**（粒度到文件与接口，建议成 plan 开工）：
  1. `src/main/network/index.ts`（新域模块，镜像 screenshot 域结构）：`registerNetworkIpc(deps)`——`networkSet`（payload 携带 `target: 'airplane'|'wifi'|'data'` 与 `enabled`，**成功后立即读回并以读回值推送**，不做本地乐观态）、轮询器（`Map<deviceId, timer>`，仅运行中设备，1s 间隔，三个读合并一次 adb shell，在途不叠发，值变化才推）、设备启动时读一次初值、`clearNetworkWatch(deviceId)` 清理钩子；同设备下发互斥（镜像 `captures` Set 先例）。
  2. `src/shared/ipc-channels.ts`：`networkSet` / `networkChanged`（main → 主窗，载荷含三开关态）两通道。
  3. `src/shared/types.ts` + `src/preload/api/network.ts`：`NetworkTarget` 联合类型、`NetworkState`（三布尔）、结果类型；`index.d.ts` 同步。
  4. `src/main/ipc/index.ts`：设备停止/清理路径挂 `clearNetworkWatch`（88/93 行 clearScreenshotCache 同位）。
  5. `DeviceToolbar.tsx` 开关组：断网总开关显眼（飞行模式），Wi-Fi/数据为伴随小开关；**飞行模式开启时分开关仍可点**（意愿排队语义系统托管，实测记录 5），显示设备真实态；点击至读回确认期间 busy。`deviceStore` 增网络态切片与 `networkChanged` 跟随；三语词条落 `src/shared/i18n/mainWindow.ts`。
  6. **读回解析**：`cmd connectivity airplane-mode` 行 trim 后全等匹配 `enabled`/`disabled`；`wifi_on` 容忍瞬态 `2`（视为「开启中」，UI 态按开显示或置 pending，plan 定）；`mobile_data` 0/1。
  7. **状态语义**：设备是唯一事实源——应用下发、设备内手动切换、飞行模式前后的 radio 恢复、设备重启残留态（settings global 落 userdata，AVD 持久），一律以读回为准，天然消解全部 desync。
  8. 界面涉及布局与视觉，实现时走 impeccable 技能。
- **分步建议**：① main 域 + IPC + 轮询（单测：三命令解析含 `wifi_on=2`、互斥、退订）→ ② preload/renderer 接线 → ③ toolbar 开关组 + 三语 → ④ 真机验收清单（三开关双向同步、飞行/双关真断网 ping、单关场景与 failover 瞬态、停止退订、重启初值、连点竞态、飞行模式下点 radio 的意愿恢复）。

## 3. 风险与开放问题

- **wifi-adb 真机**：tcpip 模式连接的真机开飞行模式会切断自身连接通道。一期模拟器（虚拟总线）无此问题；stage 06 真机接入时开关需限定 USB 连接或在文档标注。
- **模拟器蜂窝语义**：模拟器蜂窝为仿真接入宿主网络（真实路由但非运营商链路）；真机上单关数据 = 真断蜂窝。分 radio 开关在两类设备上「网络场景」含义一致，带宽/延迟特性不同——测试人员理解即可，不做特殊处理。
- **failover 瞬态**：单关 wifi 后数秒内设备可能短暂失网再走蜂窝——应用不探测连通性、不承诺「关 wifi 后立即联网/断网」，一切以开关读回为准，避免越界。
- **竞态**：用户快速连点与轮询并发——下发串行化（互斥先例）+ 以下发后读回为准可覆盖。
- **读回瞬态值**：`wifi_on=2` 见 2.4 第二轮记录 5，解析方案已覆盖。
