# 真机 USB/无线接入与 APK 拖装 功能调研报告

> 创建时间：2026-10-13 01:37:55（Asia/Shanghai，与文件名时间戳一致）
> 需求来源：分析 stage06 真机接入与投屏的可行性，准备先做 USB 调试、再做 WiFi 调试；另研究能否把 APK 拖入（真机）安装。
> 调研单元：3 个
> 状态：调研完成，待用户确认（未实施）

## 1. 需求理解

### 1.1 功能目标

物理设备接入现有设备列表与投屏操控（stage06 立项、PRD I 组已批复，定位不变：真机是「操控同一台设备的窗口」——无账号隔离承诺、断开不关机、只连接/断开/投屏）。本次调研做两件事：①把既有批复方案（[think-report 20261009022552](./20261009022552-SDK共享检测与真机投屏.md) 单元二）按用户定的「先 USB、后 WiFi」批次切分复核——重点是逐条核对其代码引用在 2026-10-13 模块拆分重构后是否仍成立；②新增调研 APK 拖装到真机（测试辅助域对真机适配的第一个提前项，用户点名）。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 既有批复结论（复用 adb CLI + 内置 scrcpy 栈、不引入 QtScrcpy、不碰共享 server 红线）在重构后代码里是否仍成立？→ 成立，引用已逐条核对到新位置，见 2.2。
- [x] USB 插拔怎么检测？→ 两个候选：轮询 `adb devices -l`（推荐先行）vs `host:track-devices-l` 长连接推送（后续优化），见 2.3。
- [x] 内置 scrcpy-server 3.3.3 对真机的版本要求？→ API 21+（Android 5.0）；Android 12 需 scrcpy ≥1.18，3.3.3 满足；server 是 DEX 与设备 arch 无关，见 2.3/2.4。
- [x] WiFi 批的技术要点有无新变化？→ `adb pair` 按参数式（配对码作第三参）实现并实测；新 mDNS 栈已修复老回归但服务名可能带空格（`adb-SERIAL (2)._adb-tls-connect._tcp`），解析器不能按空白切；新版 adb「mdns 自动连接默认关闭」不影响我们的显式 connect，见 3.3。
- [x] APK 拖入真机能做吗、增量在哪？→ 能：安装域只吃 serial 与真机无关；增量是 serialOf 第二通路、真机特有失败签名、（待批复）bypass 旗标交互，见 4.3—4.5。

### 1.3 拆分判断

拆 3 个调研单元，与实施批次对齐：**单元 A「USB 真机接入（第一批）」**、**单元 B「WiFi 无线调试（第二批）」**——A/B 的总体方案已在 2026-10-09 报告批复，本次是批次切分与增量验证；**单元 C「APK 拖装到真机」**——新增能力点，依赖单元 A 的外部设备模型（connected 态 + serial），不依赖单元 B，可随第一批交付。

## 2. 调研单元：USB 真机接入（第一批）

### 2.1 该部分要做什么

USB 物理设备出现在设备列表（含未授权态引导）、点击激活即投屏操控、插拔即时跟随。**不做**：配对/无线扫描/连接（第二批）、测试辅助域适配（APK 拖装除外，见单元 C）、iOS。

### 2.2 项目现状（既有批复引用逐条复核，2026-10-13 重构后）

- [adb.ts](../../../src/main/emulator/adb.ts)：`probeServer`/`ensureSharedServer`（共享 5037，绝不 kill-server——红线不变，且 [ipc 装配](../../../src/main/ipc/index.ts) 未动）、`listAdbSerials` 只收 `device` 态——外部设备需要解析 `adb devices -l` 的 `device/unauthorized/offline` 全状态与 `-l` 的型号/usb 信息，此函数不动、解析逻辑放新模块。
- [scrcpy/index.ts:519-532](../../../src/main/scrcpy/index.ts)：`ensureSession({id, runId, serial})` 只认 serial——复核成立；[transport.ts](../../../src/main/scrcpy/transport.ts) 走 `adb -s <serial> push/forward/app_process`，serial 为 USB 硬件号语义不变，投屏层零改动。
- [ipc/index.ts:106-125](../../../src/main/ipc/index.ts)：流会话桥绑 emulator runner 事件——外部设备没有 runner，需要「激活即建会话」第二条通路（runId 用连接代次），与既有批复一致。
- [stage/06](../../stage/06-真机接入与投屏.md) 步骤 1 已定落点 `src/main/devices/external.ts`（2026-10-13 拆分后 devices 目录已是多模块结构，external.ts 作为新域模块加入，遵循「域模块不经 index 中转、跨域消费走注入」的分层约定——见[拆分快照](../../docs/architecture/2026-10-13-main-module-split.md)）。
- [types.ts](../../../src/shared/types.ts) DeviceMeta v2 假定官方画像与镜像身份——外部设备独立类型（serial、usb/wireless、连接态），不动 DeviceMeta。

### 2.3 候选方案（本次新决策点：USB 插拔检测）

**方案 A1：轮询 `adb devices -l`（推荐先行）**

- 原理：应用激活外部设备标签页/主窗在场时按 2s 间隔轮询，diff 后广播变化；复用现有 `runAdb()`，形态与 network 域 1s 轮询先例一致。
- 来源：[adb 官方文档（devices 列表与状态）](https://developer.android.com/tools/adb)
- 适配点：纯封装级改动，无长连接维护；轮询窗口外的插拔在下一拍收敛，列表场景足够。

**方案 A2：`host:track-devices-l` 长连接推送（后续优化）**

- 原理：smart socket 持久连接，server 在设备集变化时推全量列表；[adb.ts](../../../src/main/emulator/adb.ts) 已实现同协议（`encodeAdbRequest`/probeServer 的 OKAY+长度帧解析），加一个持续 socket 客户端即可。
- 来源：[adb SERVICES.TXT（host:track-devices）](https://android.googlesource.com/platform/system/core/+/jb-dev/adb/SERVICES.TXT)、[dotnet/android#12073（track-devices-l push 语义，2026-03）](https://github.com/dotnet/android/issues/12073)
- 适配点：零轮询延迟、无忙轮询；代价是断线重连与 socket 生命周期管理，第一批不值得先付。

**投屏/控制通路（无新候选，沿用既有批复）**：内置 scrcpy-server 3.3.3 随包分发，server 是 DEX 由 app_process 执行、与设备 arch 无关；版本要求 API 21+（Android 5.0），Android 12 需 scrcpy ≥1.18——3.3.3 均满足。来源：[Genymobile/scrcpy#3095](https://github.com/Genymobile/scrcpy/issues/3095)、[scrcpy#98（API 21 下限）](https://github.com/Genymobile/scrcpy/issues/98)。

### 2.4 可行性分析

| 维度 | 方案 A1（轮询） | 方案 A2（track-devices-l） |
| --- | --- | --- |
| 技术匹配 | runAdb 现成；2s 粒度满足列表跟随 | 协议已在库内可实现；断线重连自维护 |
| 规则冲突 | 无（只读命令、不碰 server 生命周期） | 无 |
| 成本 | 一个定时器 + diff 广播 | 长连接客户端 + 生命周期挂接（激活/退出/断线） |

### 2.5 结论与实施建议

- 结论：**采用现成方案**（adb CLI + 既有投屏栈，既有批复维持）；插拔检测选 **A1 轮询先行**，A2 作为后续优化不进第一批。
- 落地路径：
  1. `src/shared/types.ts`：外部设备类型（serial、`transport: 'usb' | 'wireless'`——serial 含 `:` 判 wireless、`state: 'device' | 'unauthorized' | 'offline' | 'connecting'`、型号名）+ 设备列表快照扩展（外部区与 AVD 区并列）。
  2. `src/main/devices/external.ts`：`listExternal()`（解析 `adb devices -l` 全状态，接缝注入可单测）+ 2s 轮询器（主窗在场时启停）+ 变化广播通道；不经 devices/index 中转，ipc 装配层接线。
  3. scrcpy 第二桥：外部设备「激活即 `ensureSession({id, runId: 连接代次, serial})`」，断开/失联销毁会话（挂 destroySession）。
  4. IPC：`devices:external-list`（拉取）+ `devices:external-changed`（推送）+ preload 白名单。
  5. renderer 设备列表「真机」区 + 未授权引导（提示在手机上授权；撤销重授权路径：开发者选项 → 撤销 USB 调试授权 → 重插）——界面走 impeccable 技能。
  6. 验收：插拔 2s 内跟随、未授权态展示与转正、投屏触控/中文输入/旋转、与模拟器并行互不干扰（stage06 步骤 4 的 USB 子集）。

## 3. 调研单元：WiFi 无线调试（第二批）

### 3.1 该部分要做什么

Android 11+ 无线调试：mDNS 扫描 + 手动 IP+端口 + 配对码配对、已配对直连；Android ≤10 仅支持已处 tcpip 5555 模式的直连。**不做**：「USB 转无线」自动化（既有批复假设 5）。

### 3.2 项目现状

- 既有批复方案 A（`adb mdns services` 为主、手动 IP 一等兜底、`adb pair`/`adb connect` 经 runAdb 封装）不变；风险记录（platform-tools 34–36 mDNS 空结果回归、AP 隔离、动态端口）仍有效。
- [PRD I 组](../../docs/PRD.md) AC 已按此口径写入（116—121 行）。

### 3.3 候选方案（本次增量验证的三处实现要点）

**`adb pair` 配对码传参**：官方文档展示交互式（`adb pair ipaddr:port` 后提示输入配对码）——子进程无 tty，实现必须用参数式 `adb pair <ip:port> <code>`。来源：[adb 官方文档](https://developer.android.com/tools/adb)、[SO 71221039（配对流程）](https://stackoverflow.com/questions/71221039/wi-fi-debug-adb-there-was-an-error-pairing-the-device)。参数式在社区广泛使用，落地时以真机实测为准（失败分类：拒绝＝端口/开关不对、认证失败＝需重新配对）。

**mDNS 解析防空白**：新 platform-tools 的 mDNS 栈（LIBADBMDNS 后端，替换 openscreen）修复了空结果回归与 Windows 崩溃；但 mDNS 名冲突时服务名含空格（`adb-SERIAL (2)._adb-tls-connect._tcp`），Flutter 解析器曾因此误判——`scanWireless` 解析不能按空白切分，需按 `\_adb-tls-\*` 后缀锚定。来源：[platform-tools 发行注记](https://developer.android.com/tools/releases/platform-tools)、[Medium（新 mDNS 栈修复记）](https://medium.com/@sijus/google-just-fixed-wireless-debugging-over-adb-4fc897ef8b2a)、[flutter#187092（空格服务名，2026-05）](https://github.com/flutter/flutter/issues/187092)。

**mdns 自动连接默认关闭**：新版 adb 把「发现即自动 connect」改为默认关闭——我们的方案本就是显式 `adb connect`，不受影响；反而消除了「设备被自动连上导致列表突增」的干扰。来源：[platform-tools 发行注记](https://developer.android.com/tools/releases/platform-tools)。

### 3.4 可行性分析

| 维度 | 结论 |
| --- | --- |
| 技术匹配 | pair/connect/mdns 全部是 adb CLI 现成命令；解析层有真实坑（空格服务名）已在候选节给出对策 |
| 规则冲突 | 无（显式 connect、不碰 server 生命周期） |
| 成本 | external.ts 增四个函数 + 连接器 UI；风险集中在宿主 adb 版本差异（老 adb 无新 mDNS 栈 → 空结果 → 手动 IP 兜底路径保命） |

### 3.5 结论与实施建议

- 结论：**采用现成方案**（既有批复维持），第二批增量是三处实现要点（参数式 pair、解析防空白、错误分类）。
- 落地路径：`external.ts` 补 `scanWireless()`/`pairDevice(ip, port, code)`/`connectDevice(ip, port)`/`disconnectDevice(serial)`；IPC `devices:external-scan/pair/connect/disconnect`；renderer 无线连接器（扫描列表 / 手动 IP+端口 / 配对码表单，手动 IP 一等入口）走 impeccable；验收按 stage06 步骤 4 无线子集（配对→连接、已配对直连、≤10 tcpip 直连、Wi-Fi 断连恢复）。

## 4. 调研单元：APK 拖装到真机（新增）

### 4.1 该部分要做什么

把 `.apk` 拖到真机画布即安装，交互与模拟器一致（拖入高亮 → 安装中 → 结果卡）。**不做**：批量拖入、进度百分比（adb 不产出）、非 apk 文件。

### 4.2 项目现状

- [apkInstall/index.ts](../../../src/main/apkInstall/index.ts)：核心是 `adb -s <serial> install -r <file>` + 每设备串行互斥 + 失败签名→词条映射——**与设备是真机还是模拟器无关，只吃 serial**，域本体可整体复用。
- [ipc/index.ts:57-61](../../../src/main/ipc/index.ts)：注入 `serialOf: runningDeviceSerial`——[devices/queries.ts](../../../src/main/devices/queries.ts) 的该函数断言 `status === 'running'`（模拟器生命周期态），真机没有这个状态，是唯一结构性门槛。
- renderer：[useApkInstall.ts](../../../src/renderer/src/hooks/useApkInstall.ts) + `InstallDropOverlay` 已按 deviceId 键控（模块级状态机，重挂载恢复），画布门槛条件需从「running」扩到「running 或 connected」。

### 4.3 候选方案（真机特有失败面的处置）

**签名扩充（无争议，直接做）**：

- `INSTALL_FAILED_USER_RESTRICTED`：MIUI/HyperOS 默认拦「USB 安装」，需手机侧开开发者选项里的「USB 安装」（可能要求登录小米账号/SIM 在网）。无法从 adb 侧绕过，只能词条引导。来源：[SO 47239251](https://stackoverflow.com/questions/47239251/install-failed-user-restricted-android-studio-using-redmi-4-device)、[android.stackexchange 185116](https://android.stackexchange.com/questions/185116/enable-install-via-usb-without-creating-mi-account)。
- `INSTALL_FAILED_DEPRECATED_SDK_VERSION`：Android 14+ 拒装 targetSdk < 23 的旧 APK；`adb install --bypass-low-target-sdk-block` 可越过（需 platform-tools 34+；宿主共享 adb 是老版本时不认此旗标，报 unknown option——原文上报兜底）。来源：[bayton.org](https://bayton.org/android/android-14-minimum-sdk/)、[XDA（旗标用法）](https://xdaforums.com/t/installing-apps-with-an-outdated-sdk-on-android-14.4632567/)。

**bypass 旗标交互（两选一，见假设 3）**：失败命中 deprecatedSdk 后，A：失败卡加「仍要安装」按钮，确认后带旗标重装；B：静默自动带旗标重装一次。倾向 A——测试工具应把「绕过系统安全门槛」的决定留给用户。

### 4.4 可行性分析

| 维度 | 结论 |
| --- | --- |
| 技术匹配 | 安装命令、串行互斥、renderer 状态机全部现成；serial 对真机语义不变 |
| 规则冲突 | 无——install 是设备侧操作，不碰共享 server 生命周期 |
| 成本 | 三处小增量：serialOf 组合、签名词条 ×2、旗标重试交互；无新依赖 |

### 4.5 结论与实施建议

- 结论：**采用现成方案**（apkInstall 域整体复用），增量集中在「谁能给 serial」与「真机失败面」。
- 落地路径：
  1. devices 域新增组合查询（如 `serialOfDeviceId(id)`：先查外部设备表 connected → serial，miss 落 `runningDeviceSerial`），[ipc/index.ts](../../../src/main/ipc/index.ts) 的 apkInstall 注入换它——安装域自身零改动。
  2. `FAILURE_SIGNATURES` 增两条（userRestricted → 开「USB 安装」引导词条；deprecatedSdk → 旧安装包提示词条）+ i18n 三语。
  3. 输入扩展 `allowLowTargetSdk?: boolean`，命中 deprecatedSdk 时失败卡出「仍要安装」（若假设 3 批复 A 案）。
  4. renderer 画布 droppable 条件扩到外部设备 connected 态；overlay 文案复用。
  5. 验收：真机拖装成功/失败各一、MIUI 拦截词条、Android 14+ 旧 APK「仍要安装」链路、模拟器拖装回归不变。

## 5. 风险与开放问题

- **宿主 adb 版本不可控**（共享 server 架构的既有约束）：老 adb 无 `--bypass-low-target-sdk-block`、mDNS 可能空结果——两条都有兜底（原文上报 / 手动 IP 一等入口）。
- **mDNS 服务名含空格**：解析按后缀锚定，不按空白切（flutter#187092 在案）。
- **配对端口动态变化**：重连可能要重查 mDNS 或让用户重看手机端口（既有风险，无线批验收覆盖）。
- **未授权态无法推进任何操作**：投屏/安装对 unauthorized 设备直接失败；不 kill-server 重弹（红线），引导走手机侧撤销重授权。
- **USER_RESTRICTED 无法自动绕过**：小米账号门槛是设备侧策略，只做词条引导。

## 6. 待确认假设

- [ ] 假设 1（批次划分）：第一批 = USB 接入（列表/未授权引导/投屏第二桥）+ APK 拖装（依赖外部设备模型即可）；第二批 = WiFi（扫描/配对/连接/直连）。APK 拖装不等到第二批。
- [ ] 假设 2（插拔检测）：第一批用 2s 轮询 `adb devices -l`；`host:track-devices-l` 长连接推送作为后续优化，不进第一批。
- [ ] 假设 3（旧 APK 交互）：`INSTALL_FAILED_DEPRECATED_SDK_VERSION` 失败卡提供「仍要安装」按钮、用户确认后带 `--bypass-low-target-sdk-block` 重试（不静默自动绕过）。
- [ ] 假设 4（USER_RESTRICTED）：只做中文引导词条（指向手机「USB 安装」开关），不尝试任何自动绕过。
- [ ] 假设 5（辅助域边界）：截屏/断网/日志三域对真机的适配仍按 PRD「后续批次」处理，本次只提前 APK 拖装（用户点名）；它们的注入点同为 running 态断言，真机接入时需要与 serialOf 同款的第二通路，届时另立任务。
