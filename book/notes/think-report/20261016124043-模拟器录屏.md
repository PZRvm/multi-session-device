# 模拟器与真机录屏功能调研报告

> 创建时间：2026-10-16 12:40:43（Asia/Shanghai）
> 需求来源：用本程序录屏；用户随后明确模拟器与真机、MP4、设备声音、暂停续录、切设备不中断。
> 调研单元：3 个（视频封装 → 音频采集 → 任务与暂停时间轴）
> 状态：需求与待确认假设已获用户确认；[开发 plan](../../plans/2026-10-16-device-recording.md) 的 Step 0 / Phase 1 / Phase 2 已完成，Phase 3 已进入 P0。[实测](../../docs/poc/2026-10-16-recording-p0.md) 发现原始 AAC PTS 长录偏差；采样时钟候选已用 AVD 复验，用户已批准将真机音频验收后移。正式录制域、IPC、独立媒体页和工具条/任务区已接入，开发验证进行中，尚未交付。下文调研时期“未实测”表述保留为当时状态，当前证据以 P0 报告为准。
> 修订：保留首次报告文件名与创建时间；本版取代先前“优先 Emulator WebM”的推荐。

## 1. 需求理解

### 1.1 功能目标

在应用内录制 Android 模拟器、USB/无线真机的屏幕和设备声音，输出 MP4，不包含机身皮肤。支持开始、暂停、继续、停止；选中其他设备后，原任务继续录制原设备的实时状态，不把新选设备接进旧文件。多个设备分别录成各自的视频，不把多个设备拼入同一个视频。用户已确认录制中跟随设备横竖屏变化，前后内容仍保存为同一完整视频。剪辑、GIF 等功能暂不纳入。

用户已确认暂停续录语义：暂停内容不进入文件，继续后接在同一 MP4 中，播放时没有暂停造成的长空白；采音失败时明确提示，由用户选择是否无声继续。设备声音已明确要求，不再作为“先无声”的假设。

### 1.2 未知点清单

- [x] 模拟器与真机如何共用录屏？复用两者已接入的 scrcpy 视频源，见第 2 节。
- [x] 如何生成 MP4？使用成熟封装库，不能把 H.264 字节改后缀；优先评估 Mediabunny，见 2.3。
- [x] 能否录设备声音？scrcpy 3.3.3 有音频能力，但项目目前关闭，Android 版本与采集方式存在边界，见第 3 节。
- [x] 能否暂停续录且切设备不中断？可设计独立主进程任务与统一时间轴，仍需验证关键帧与同步，见第 4 节。
- [x] 是否已证明最终文件可用？没有。本轮完成代码和官方 API 调研，未录制设备、未安装依赖、未修改实现；验证门槛见第 5 节。

### 1.3 拆分判断

拆为三个单元：视频封装、音频采集、任务与暂停时间轴。前两项可独立验证，第三项依赖前两项的包格式与时间戳结论；最终联合验收。

## 2. 调研单元：视频采集与 MP4 封装

### 2.1 该部分要做什么

获取设备屏幕编码包并写成 MP4，覆盖模拟器与真机，避免额外捕获宿主 UI。

### 2.2 项目现状

- [PRD](../../docs/PRD.md) D 组已有开始/停止录屏要求；暂停续录和真机范围来自本轮用户补充，不能说已在旧 PRD 中批准。[stage05](../../stage/05-功能完善.md) 的组合步骤虽勾选，注记仍明确录屏未实现。
- [transport.ts](../../../src/main/scrcpy/transport.ts) 固定 server 3.3.3；[session.ts](../../../src/main/scrcpy/session.ts) 在 main 读取编码包；[media.ts](../../../src/main/scrcpy/media.ts) 处理配置、微秒 PTS 和投屏回放。后台会话继续收包，只有 renderer 发送依赖当前视图。
- [external.ts](../../../src/main/devices/external.ts) 和 [IPC 装配](../../../src/main/ipc/index.ts) 已将真机接入 scrcpy。录制任务应绑定 deviceId/runId/streamId，不以当前 active view 为归属。
- [package.json](../../../package.json) 为 Electron ^39.2.6、React ^19.2.1、Tango scrcpy ^2.3.0 / adb-scrcpy ^2.3.2；[打包配置](../../../electron-builder.yml) 仅带 server，未声明完整 scrcpy CLI、FFmpeg 或 MP4 封装库。
- [架构规则](../../guidelines/architecture.md) 要求 main 编排、renderer 解码；直接封装编码包不需要解码，可放在独立 main 录制域。沿用三语字典，不套用技能中的浏览器 partition、WebContentsView 或 antd 背景。

### 2.3 候选方案

**A：scrcpy 原始视频包 + Mediabunny 封装（推荐）**

[固定 3.3.3 录屏文档](https://github.com/Genymobile/scrcpy/blob/v3.3.3/doc/recording.md) 说明设备编码、客户端封装。[EncodedVideoPacketSource](https://mediabunny.dev/api/EncodedVideoPacketSource) 接收编码包；[AVC 注册规范](https://mediabunny.dev/codec-registry/avc) 支持 Annex B 与长度前缀格式，但对关键帧参数集有要求。项目要整理 scrcpy 独立配置包与数据包，不能假设原样逐包 add 就可用。

[文件写入文档](https://mediabunny.dev/guide/writing-media-files) 提供 Node 的 FilePathTarget 和 finalize；无需为了直接封装引入编解码扩展。当前 `npm view mediabunny version license dist.unpackedSize --json` 查得 1.61.5、MPL-2.0、10,881,949 bytes；这是 npm 解包体积，不等于应用新增体积。版本核对来源：[上游 package.json](https://github.com/Vanilagy/mediabunny/blob/main/package.json)。实施验证时锁定 1.61.5，并核对该版本实际导出 API，在线文档可能继续变化。

**B：scrcpy 编码流 + FFmpeg 封装**

[FFmpeg 容器文档](https://ffmpeg.org/ffmpeg-formats.html) 提供 MP4 封装；能力成熟，但直接通过 stdin 喂裸 H.264 会丢掉 scrcpy 包的 PTS 信息，需要有时间戳的输入协议或中间容器。暂停仍由应用裁剪时间轴，不能仅冻结子进程。新增原生产物、平台架构和分发许可核对，见 [官方许可说明](https://ffmpeg.org/legal.html)。作为 A 验证不通过或确需转码时的备选。

**C：设备/模拟器自带录屏后合并**

[Emulator 原生输出 WebM](https://developer.android.com/studio/run/emulator-record-screen) 不覆盖真机与 MP4；[Android screenrecord](https://developer.android.com/tools/adb#screenrecord) 不录音，官方还记录时长与旋转限制。暂停需分段再拼接，音频另采、再做同步。与本轮统一需求不匹配，不推荐。

### 2.4 可行性分析

| 维度 | A：Mediabunny | B：FFmpeg | C：内建录屏 |
| --- | --- | --- | --- |
| 技术匹配 | 两类设备共用流，直接 MP4 | 能力强，需保留原始时间戳 | 不能独立满足真机+MP4+声音+暂停 |
| 规则冲突 | main 独立封装符合分层；不得阻塞投屏 | 可隔离 main 子进程，需严格进程归属 | 可按 serial 隔离，但链路分叉 |
| 成本 | 新增 TS 包与包适配，需附第三方许可 | 新增二进制、打包与协议适配 | 看似无依赖，完整需求下需再合并/转码 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**。采用 Mediabunny 现成封装能力，项目自己实现 scrcpy 包适配和任务逻辑，不手写 MP4 容器。用户确认动态横竖屏后，完整推荐增加固定画布的视频重编码，见第 5 节；本节的直接封装是固定尺寸时的低成本候选，不能单独宣称覆盖全部需求。

在 `src/main/recording/` 新建封装适配器；从 session 原始 reader 处分发给录制订阅，再走现有投屏逻辑。不能从 `sendPacket` 录制，否则 active view、回放和 ACK 会影响文件。录制写入使用有界串行队列，磁盘过慢时终止并报告录制错误，不能无界攒内存或拖住投屏。先验证普通 MP4 + 文件流；fMP4 只是崩溃恢复的候选，需要比较播放器兼容性，见 [输出格式](https://mediabunny.dev/guide/output-formats)。

## 3. 调研单元：设备声音采集

### 3.1 该部分要做什么

把设备声音与屏幕写入同一 MP4；不录宿主麦克风。是否同时在设备或电脑播放声音是另一个产品选择，不能与“文件含声音”混为一谈。

### 3.2 项目现状

[transport.ts](../../../src/main/scrcpy/transport.ts) 明确 `audio: false`，只按视频→控制的顺序建 socket；`Transport` 没有音频字段。[types.ts](../../../src/main/scrcpy/types.ts) 和 [session.ts](../../../src/main/scrcpy/session.ts) 也没有音频 reader。只改为 true 会改变 socket 握手顺序，不能视作完整接入。

本地 Tango 源码 `node_modules/@yume-chan/scrcpy/src/2_0/impl/parse-audio-stream-metadata.ts` 已有音频状态与 AAC 等 codec 解析，可复用而非自造协议。

### 3.3 候选方案

**A：当前 scrcpy 会话增加音频 socket**

复用同一 server，但当前视频会话建立时关闭音频，开始录制时动态启用不能凭空成立：需要会话重建，或预先长期开音频。前者可能打断投屏，后者扩大持续采音范围，不直接推荐作为默认策略。

**B：录制任务按需启动独立 audio-only scrcpy 会话（优先验证）**

保留已有视频会话，另以独立 scid 建音频会话，录制结束只清自身 socket、forward 和进程。AAC 编码优先匹配 MP4；[AAC 注册规范](https://mediabunny.dev/codec-registry/aac) 规定配置与包格式，封装层须校验 AudioSpecificConfig、采样率与声道。使用 EncodedAudioPacketSource，无需在电脑再次编码。

两种方式均基于 [scrcpy 3.3.3 音频说明](https://github.com/Genymobile/scrcpy/blob/v3.3.3/doc/audio.md)：Android 11+ 支持；11 启动采集需解锁；10 及以下不支持。默认 output 采集会改变设备本地播放；Android 13+ 的 playback/dup 可保留设备出声，但应用可以拒绝采集。音频 codec 可选 AAC。不能承诺所有应用都有可录声音。

### 3.4 可行性分析

| 维度 | A：同会话音频 | B：独立音频会话 |
| --- | --- | --- |
| 技术匹配 | 时钟归属清晰，但开始录制可能要求重建 | 按需启动，不需要为音频重启既有视频 |
| 规则冲突 | 改动现有三通道握手及会话行为 | 需独立 scid、独立清理，禁止全局杀 server |
| 成本 | 会话改造大，长期采音策略需要明确 | 多一个 server；独立会话时间基准、并存稳定性需实测 |

### 3.5 结论与实施建议

结论：**借鉴思路手写**。优先验证独立 audio-only 会话，并复用 Tango 协议解析与 Mediabunny AAC 封装。它是推荐的验证方向，尚未证明与当前视频会话在各厂商设备上稳定并存。

新增 `recording/audioTransport.ts`，复用二进制校验、ADB 环境与版本固定策略；支持超时、取消和幂等 teardown。先证明设备音视频 PTS 的时钟关系，不允许各自归零而掩盖启动偏移。音频配置未就绪前不可把任务报告为“音视频录制成功”；采集失败时明确显示无音频，不静默输出成功。用户已同意提示后选择无声继续。

## 4. 调研单元：暂停续录与后台任务

### 4.1 该部分要做什么

录制任务独立于画布挂载和设备选择；暂停去掉对应音视频片段，继续写同一 MP4，停止后统一完成文件。

### 4.2 项目现状

[useDeviceScreen.ts](../../../src/renderer/src/hooks/useDeviceScreen.ts) 随选择 activate/deactivate，不能让录制跟随其 effect。[media.ts](../../../src/main/scrcpy/media.ts) 在每次配置包重置 generation/PTS 基点；录制必须持有自己的时间映射。[recovery.ts](../../../src/main/scrcpy/recovery.ts) 的 resetVideo 与 active view 绑定，不能把它原样当后台录制续录工具。

[DeviceToolbar.tsx](../../../src/renderer/src/components/DeviceToolbar.tsx) 和 [ExternalCanvas.tsx](../../../src/renderer/src/components/ExternalCanvas.tsx) 是两类设备入口；[截屏域](../../../src/main/screenshot/index.ts) 可借鉴受控落盘，不沿用全量 Buffer 保存长视频。

### 4.3 候选方案

**A：应用维护录制状态、关键帧边界与统一时间轴（推荐）**

暂停时继续读取设备流，停止向文件添加媒体；续录等待独立可解码的关键帧，使用同一裁剪映射处理音视频，扣除暂停区间及续录等待区间。不能仅丢弃暂停期间的视频、却保留音频或原 PTS。静止画面尾部时长要由录制边界补齐，不能只靠“下一帧的 PTS”。

依据：[编码包 API](https://mediabunny.dev/api/EncodedPacket) 可明确指定秒单位 timestamp/duration；[视频包输入 API](https://mediabunny.dev/api/EncodedVideoPacketSource) 要求按解码顺序添加并遵守背压。这里的暂停算法是项目设计推论，不是封装库自动提供的能力。scrcpy 的微秒 PTS 必须显式换算。

**B：每次暂停结束文件，续录新段，停止时拼接**

对用户可表现为一个任务，但拼接仍需正确的时间戳、音轨边界和一致编解码参数；旋转造成尺寸变化时不能保证无损直接合并。依赖第 2 节的封装/转码方案，额外临时文件、等待和失败恢复成本更高，暂不推荐。

### 4.4 可行性分析

| 维度 | A：统一时间轴 | B：分段再拼接 |
| --- | --- | --- |
| 技术匹配 | 满足同一文件、暂停片段被移除 | 可达到效果，最终还需合并 |
| 规则冲突 | main 持有任务即可；与视图解绑 | 同样可放 main，但产物生命周期更复杂 |
| 成本 | 要处理关键帧、帧时长、音视频共同边界 | 除上述边界，还增加合并与临时磁盘成本 |

### 4.5 结论与实施建议

结论：**借鉴思路手写**。任务层自行实现暂停和时间映射，封装层交给库。

- 新建 main `recording/manager.ts`、时间轴模块及状态；身份至少包含 taskId/deviceId/runId/streamId。任务不属于选中行或画布，切设备不得自动停止；暂停不停止设备或投屏。
- 状态建议 starting/recording/pausing/paused/resuming/stopping/saved/error；增加 `recording:start/pause/resume/stop/get/changed`，在 shared 定义并同步 preload 类型、sender 守卫及 main/ipc 装配。
- 主窗展示录制任务入口与原设备名；当前设备工具条提供控制，切到其他设备后仍可操作原任务。UI 实现走 impeccable，沿用三语。用户补充多设备分别生成视频：任务与输出路径均按设备分开，不能随选择切换而混入另一设备。并发数量上限仍需按实际资源验证确定。
- `stop` 与 `pause/resume` 串行；音频和视频共享暂停区间，续录首关键帧之前的音频需丢弃或按帧边界处理，接受 AAC 帧粒度误差需有实测指标。暂停状态停止也必须补齐最后有效帧并 finalize。
- 热拔线、模拟器停止、进程崩溃与 streamId 换代要结束/标错旧任务，不把重连流静默拼进去。文件 finalize 后才发布为最终 MP4，重名不覆盖；失败保留可恢复材料和原因。

## 5. 风险与开放问题

1. **旋转/分辨率变化**：当前 scrcpy 会重配编码器；单 MP4 不保证跨播放器正确处理动态尺寸。用户已明确要跟随设备横竖屏变化，仍保存一个完整视频，推荐固定输出画布重编码，见下文。不能把整轨旋转元数据当作动态尺寸兼容方案。
2. **音频兼容性与出声位置**：Android 10 以下不具备本方案的设备声音采集能力；Android 11 解锁条件、13+ duplication 与应用拒录需显示清晰结果。用户已明确仅录模拟器/真机自身声音，不采电脑系统声或麦克风。默认 output 可能让设备静音；用户已要求保持设备本地出声，采集方式必须满足此约束。Android 13+ playback/dup 是候选，较旧版本或应用拒录需在 PoC 验证并明确提示，不得静默改变播放行为。电脑实时监听不是本轮需求。
3. **同物理设备双 transport**：USB 与无线可能指向同一手机。多录制任务会争用音频采集，不能以不同 deviceId 就认定完全独立；本轮先保证选择切换不中断，物理设备并发另设策略。
4. **关键帧与静止段**：一秒关键帧参数不代表静止屏幕一定按秒产帧。后台开始/续录应有超时和受控请求关键帧方案；resetVideo 可能影响投屏，需验证而非承诺无感。
5. **长录与异常收尾**：队列、音视频交错、磁盘满、finalize 与应用退出需要测试；不承诺崩溃时完整保留所有内容。

落地前验证门槛：在独立验证目录或后续 PoC plan 中，锁定 Mediabunny 1.61.5，用真实模拟器及 USB/无线手机验证 H.264+AAC MP4；至少检查多次暂停后无长空白与音画漂移、静止段时长、切设备、暂停后直接停止、音频缺失、旋转与热拔线。以 QuickTime/Chromium 等实际播放器检查播放、拖动及音轨，并比较投屏性能。当前没有这些实测结果，报告只确认技术路径可行。

### 旋转补充调研

[固定 3.3.3 的方向说明](https://github.com/Genymobile/scrcpy/blob/v3.3.3/doc/video.md) 区分设备旋转、采集方向和录制方向；录制方向可写为容器显示变换。[Mediabunny VideoTrackMetadata](https://mediabunny.dev/api/VideoTrackMetadata) 也提供整轨 rotation 元数据。由此可行的是：同一视频轨整体旋转 90°/180°/270°，前后所有内容都受影响；它不会只旋转录制中途之后的部分，也不能自动解决前后编码尺寸不同的问题。

用户已确认“设备横过来后，后半段也正常横屏，继续同一个文件”。推荐的兼容路线是统一输出画布尺寸：每段按当前方向等比放入画布，必要时留黑边，不裁掉设备内容，再编码为固定尺寸 MP4。这个方案是本项目的技术推论，不是已经实测的能力。它需要视频解码、合成、重编码，原先纯封装方案不再覆盖全部工作；必须选用独立 renderer/worker 或正式平台适配器，遵守现有解码渲染分层，不能直接往 main 塞解码逻辑。

[转换文档](https://mediabunny.dev/guide/converting-media-files) 可用于后续核对缩放、适配及旋转能力，但动态实时输入与多段处理仍需 PoC。用户已选择逐段随方向适配，整段统一旋转不再作为本需求的解决方案。

### 本轮澄清后的最终推荐

用户指定并在示例解释后再次确认输出规则：未切换横竖屏时，按该设备当前屏幕大小输出；切换后，输出宽度取录制有效画面中最大宽度，高度取最大高度，画面居中。以 1080×2400 与 2400×1080 为例，最终 MP4 为 2400×2400，竖屏左右留边，横屏上下留边；先前片段也要按最终画布居中。不同设备各算自己的尺寸，不能跨设备取最大值。

**推荐采集原始音视频并按配置变化保留临时片段和时间轴，停止后按最终尺寸生成单一 MP4。** 录制时持续统计有效画面尺寸，避免提前猜测用户之后是否旋转。未旋转且编码配置一致时，优先验证直接封装路径；发生旋转时，统一解码各段，按最大宽高画布居中适配并重编码 H.264，再与同一裁剪时间轴上的 AAC 封装。音频尽量直接封装。该路线是依据前述封装/转换 API 的设计推论，尚未实测。

不能只在旋转时增大后续视频尺寸，就宣称整个文件符合固定最终画布；此前已经写出的画面也需要整理。因此停止后显示“正在生成视频”，完成后才发布到下载目录。用户在解释后已确认停止录制后整理视频、完成后再提示保存成功的流程。会有额外临时磁盘占用与生成等待；转码失败要保留临时片段以便重试，不把半成品当成功文件。不要将分段编码后的 MP4 文件字节直接拼接。

当前已用 scrcpy 默认采集尺寸可能因编码器能力回退，不能把它无条件称为手机原生分辨率；PoC 要核对实际屏幕、采集和输出尺寸。最大画布也可能超过本机 H.264 编码能力，例如高分辨率设备旋转后得到大正方形；遇到时明确报告，不静默缩小。用户已允许明确提示后按编码器上限等比缩小作为兜底，实际编码上限通过验证获取。

解码合成与编码放在独立 renderer/worker 或正式平台适配器，不复用随当前选择销毁的可见画布；main 管理任务、临时文件和最终落盘。阶段状态增加 processing，stop 不等于 saved。音频只取指定设备输出，不采电脑声音、设备麦克风或宿主麦克风；后者未在需求中授权。

验证必须加入未旋转原尺寸、竖→横→竖最大画布居中、暂停期间方向变化、多次暂停与旋转交错、切设备后继续原任务、最终音画同步、两个独立设备各自产生文件，以及高分辨率编码上限和生成失败重试。暂停区间内无保留画面的方向变化不应单独迫使最终画布扩大，这一边界是建议语义，后续设计写清。

### 保存位置与完成后的操作

默认系统下载目录已获用户确认。它指系统配置的 Downloads 路径，通常是 `~/Downloads`，实现通过 Electron 的系统路径查询获取，不写死用户名或路径。该路径无需每次弹出“另存为”；可生成“设备名-时间戳.mp4”，重名递增不覆盖。

“完成后的打开方式”指保存成功后是否自动启动播放器，以及是否提供手动操作；它不影响保存位置。用户已确认：不自动播放，也不在应用内提供“播放”操作；成功提示显示文件名，只提供“在文件夹中显示”，在 Finder/文件管理器定位文件，由用户自行在文件夹打开视频播放。
