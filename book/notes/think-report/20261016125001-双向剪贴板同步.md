# 双向剪贴板同步功能调研报告

> 创建时间：2026-10-16 12:50:01（Asia/Shanghai）
> 需求来源：电脑复制后设备能粘贴；设备内复制后，电脑剪贴板也自动获得内容。
> 调研单元：1 个
> 状态：已实现、用户人工验收通过；2026-10-16 review P2/P3 均修复并复审关闭，开发计划 completed

## 1. 需求理解

### 1.1 功能目标

测试人员在电脑与当前选中的 Android 设备之间复制纯文本，无需点击“同步”按钮。
设备中长按复制后，切到电脑编辑器即可粘贴；电脑复制后，设备内长按粘贴和电脑快捷键粘贴都能使用新内容。

用户已确认：只同步右侧当前选中的设备；本批仅做纯文本，包含中文、英文、换行和表情。后台设备不参与同步。图片和文件留后续需求。

### 1.2 未知点清单

- [x] 设备能否主动通知复制事件？能。scrcpy 3.3.3 注册剪贴板变化监听，并推送文本；项目已经接收但丢弃。见 2.2、2.3。
- [x] 电脑是否能写入系统剪贴板？能。Electron 39.2.6 提供主进程 `clipboard.writeText`。见 2.3。
- [x] 电脑复制后能否自动更新设备，而不自动粘进输入框？能。检测宿主变化后使用 `setClipboard`，指定 `paste: false`。见 2.5。
- [x] 能否直接照搬官方 scrcpy 客户端？不能完整满足本次目标。其电脑到设备方向主要在快捷键粘贴时同步，项目还需要宿主变化检测与多设备归属。见 2.3。
- [x] 能否保证任意格式、任意长度、每次变化都无损同步？不能。现有通道仅文本，设备返回存在长度截断，宿主轮询也无法观察两个采样点之间所有变化。见第 3 节。

### 1.3 拆分判断

作为一个调研单元：两向传输及同步策略共用现有主进程 scrcpy 会话，无需为 preload 或 renderer 新造数据通道；按传输方向分开说明即可。

## 2. 调研单元：当前设备与电脑的纯文本双向同步

### 2.1 该部分要做什么

补齐设备→电脑自动写入，并将电脑→设备从“主动粘贴时发送”扩展为自动同步。
保持设备切换、断开和会话重建时的归属正确，避免后台设备、输入法中间文本和过期任务改写电脑剪贴板。

### 2.3 候选方案

**方案 A：复用现有 scrcpy 控制通道 + Electron 剪贴板，补同步协调器**

- 原理：设备文本从已有 clipboard 流进入主进程，经当前设备及会话检查后 `clipboard.writeText`；宿主用单个定时器检测 `readText` 变化，经既有 writer 写设备，`paste: false`。
- 来源：[scrcpy 3.3.3 控制说明](https://github.com/Genymobile/scrcpy/blob/v3.3.3/doc/control.md)、[同版本 Controller](https://github.com/Genymobile/scrcpy/blob/v3.3.3/server/src/main/java/com/genymobile/scrcpy/control/Controller.java)、[Electron 39.2.6 clipboard API](https://github.com/electron/electron/blob/v39.2.6/docs/api/clipboard.md)、[Tango 控制 API](https://tangoadb.dev/scrcpy/control/)。Tango 网站描述较新版本，实际调用能力以本地 2.3.0 源码核对为准。
- 适配：全在现有主进程链路；不换 server、不新增 npm 包。Electron 39.2.6 clipboard API 没有列出变化事件，定时检查是本报告提出的项目策略。

**方案 B：额外启动官方 scrcpy 桌面客户端**

- 原理：利用完整客户端现成的设备→电脑剪贴板处理与快捷键粘贴行为。
- 来源：[官方控制说明](https://github.com/Genymobile/scrcpy/blob/v3.3.3/doc/control.md)、[3.3.3 客户端 input_manager.c](https://github.com/Genymobile/scrcpy/blob/v3.3.3/app/src/input_manager.c)。后者在处理 Ctrl+V 时读取宿主剪贴板并发送 `setClipboard`，不能据“autosync”名称推断它已监听每次宿主变化。
- 适配：需额外分发客户端并维护第二套控制会话，当前 Electron 的 active 归属无法直接约束其写宿主行为；仍需补宿主自动变化同步。因此不选。

### 2.4 可行性分析

| 维度     | 方案 A                                                                 | 方案 B                                                                                             |
| -------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 技术匹配 | 现有协议和 Electron 39 API 覆盖文本读写；补宿主检测与策略即可          | 官方具备基本复制粘贴，但不直接满足应用内当前设备和双向自动同步要求                                 |
| 规则冲突 | 用 active 单目标可保持设备分区隔离；宿主中转内容属于用户批准的共享边界 | 不加额外协调时，多个客户端可能竞争唯一宿主剪贴板，不符合本次已确认范围                             |
| 成本     | 无新增依赖；已有 Tango 包 MIT，主要成本为同步竞态与硬件验收            | 增加原生可执行文件、分发与进程清理；scrcpy 为 Apache-2.0，许可证本身不构成阻碍，但整套引入成本更高 |

许可依据：本地 `node_modules/@yume-chan/scrcpy/package.json`；[scrcpy 3.3.3 LICENSE](https://github.com/Genymobile/scrcpy/blob/v3.3.3/LICENSE)。

### 2.5 结论与实施建议

**结论：借鉴思路手写。** 采用现有 scrcpy/Tango 与 Electron API，借鉴官方 clipboard 消息处理，手写本项目的变化检测、设备归属和竞态协调。可行性来自协议与源码核查，本轮没有完成真设备同步原型验证。

建议行为如下；未获用户确认的细节列在第 4 节：

1. **设备→电脑：** 持续消费所有会话的流，但只有当前选中且仍有效的会话可写宿主。写前检查 session 对象仍在 map、runId/streamId 与绑定仍有效、abort 未触发。失焦到电脑编辑器后仍可接收当前设备复制，不能简单用主窗焦点禁用同步。
2. **电脑→设备：** 一个管理器级定时器，建议间隔 300ms；只有存在选中且 ready 的目标才运行。宿主纯文本变化后，`paste: false` 写入设备；不向后台设备广播。首次连接只建立检测基线，不初始化两端原有内容；切换设备的基线策略在开发计划中明确。
3. **切换策略：** 首次连接不改原有内容（用户已确认，取代初稿的电脑内容初始化建议）。设备切换是否同样只建立基线，在开发计划中明确；不回放后台期间的设备旧剪贴板到电脑。归属撤销时清空待发送任务；已在 socket 发出的旧写入不能撤回，后续回包不得写宿主。
4. **防循环与防乱序：** 协调器记录最新观察值、来源、目标代次与单调修订号；同步写宿主后更新轮询基线，设备侧回声不能再次反向发送。仅保留最新待同步文本，限制在途写入；两个方向进入同一协调流程。设备事件到达时先检查宿主是否已有未采样变化，按明确的观察顺序裁决；协议没有跨端复制时间戳，不能保证真实时间上的最后复制者必胜。
5. **与 IME/主动粘贴协调：** 中文输入也调用 `setClipboard`，不能把这些内部中间值当成用户复制写回电脑。自动同步不得插入 IME 的设置剪贴板→粘贴序列；保留 `paste: true` 主动操作路径，并让它与 `paste: false` 的同步共用调度。服务端有自身写入抑制，但项目仍需代次及来源检查，不能只靠内容相等或服务端抑制。
6. **错误与生命周期：** 写宿主失败不阻断 clipboard 流消费或 ACK 解析；写设备失败显示同步不可用并遵循既有控制通道故障处理。停止/断开/关闭应用撤销计时器与任务，重连仅绑定新会话。ACK 只证明协议确认，服务端即使设置失败也可能回复 ACK，不能展示为“目标应用已成功粘贴”。

文件与接口落点：

| 文件                                               | 建议改动                                                                                                            |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| 新增 `src/main/scrcpy/clipboardSync.ts`            | 管理器级同步协调器；注入 readText/writeText/availableFormats/时钟供测试，提供设备消息、目标切换、会话就绪、停止入口 |
| `clipboard.ts`                                     | 提取可选择 paste 标志的公共写入口；保持既有 `clipboardPaste` 语义；复用 ACK 与队列控制                              |
| `controlChannel.ts`                                | 消费文本后送协调器；继续消费非当前设备消息，不让背压阻塞 ACK                                                        |
| `types.ts`、`context.ts`                           | 注入协调器和必要状态，按当前模块依赖方向接线，避免循环依赖                                                          |
| `ipc.ts`、`session.ts`、`lifecycle.ts`、`index.ts` | active 更新、ready、断开与 destroyAll 时通知协调器；不与视频恢复计时器混用                                          |
| 相关 `__tests__/`                                  | 协议/调度/切换回归，使用假 clipboard，不改测试机真实剪贴板                                                          |

核心数据在 main 内流转，无需新增传输剪贴板正文的共享类型或 IPC，也无需 renderer 获得读取系统剪贴板的通用能力。若后续决定增加开关或状态提示，再同步增加 shared/preload 契约与三语词条，界面实现走 impeccable。

实施顺序：先写同步策略与边界测试，再打通设备→电脑，然后补宿主轮询和统一写调度，最后做模拟器及 USB/无线真机验收。正常负载建议验收为复制后 1 秒内另一端可粘贴；该时间为建议指标，尚无实测数据。

关键验收：中英/换行/表情、连续快速复制、电脑编辑器中复制与粘贴、设备长按粘贴、IME 不覆盖电脑剪贴板、A/B 切换与后台复制隔离、断连和旧回包、同手机 USB/无线双条目、截图图片不清空文本、长度边界及 ACK/写失败无死循环。两端同时复制需单独核对冲突策略。

## 3. 风险与开放问题

- **文本长度并非无限。** scrcpy 3.3.3 的设备→电脑 writer 会按 UTF-8 边界截断至 `262139` 字节（256KiB 减 5）；电脑→设备 reader 声明文本预算 `262130` 字节（减 14），但其读取路径没有在此强制校验。应在项目发送前设明确上限，超限给出提示；不能宣称大文本无损同步。设备返回值没有“已截断”标记，原文是否更长无法仅凭收到的文本确定。来源：[DeviceMessageWriter](https://github.com/Genymobile/scrcpy/blob/v3.3.3/server/src/main/java/com/genymobile/scrcpy/control/DeviceMessageWriter.java)、[ControlMessageReader](https://github.com/Genymobile/scrcpy/blob/v3.3.3/server/src/main/java/com/genymobile/scrcpy/control/ControlMessageReader.java)。
- **清空不能直接等同空串。** 宿主只有图片时 `readText` 也可能读不到文本，应先检查格式；设备没有文本时服务端可返回 null 且不发送消息，所以现有通道不能可靠区分图片复制、显式清空与自动清空。建议首批只保证新文本复制，不承诺清空动作跨端镜像。依据：[Electron clipboard](https://github.com/electron/electron/blob/v39.2.6/docs/api/clipboard.md)、[Controller](https://github.com/Genymobile/scrcpy/blob/v3.3.3/server/src/main/java/com/genymobile/scrcpy/control/Controller.java)、[Device](https://github.com/Genymobile/scrcpy/blob/v3.3.3/server/src/main/java/com/genymobile/scrcpy/device/Device.java)。
- **“完全同步”有并发边界。** 轮询可同步最终观察到的文本，不能保留每次瞬时变化；跨端无全局时间戳，极近的同时复制需要项目定义裁决顺序。若将来要求每次复制事件无遗漏，需另调研系统原生监听与扩展协议。
- **运行环境需验证。** 模拟器、不同 Android 厂商和系统版本仍需实际复制测试，不能把服务端存在监听当成所有 ROM 已验收。当前架构覆盖 USB 与无线；是否纳入本批真机验收见第 4 节。
- **共享范围会扩大。** 相比当前按粘贴发送，自动同步会把宿主的新文本自动写入选中设备。此次目标明确要求自动同步；是否提供暂停入口可在实现设计时决定，不在调研中自行增加操作步骤。正文不落日志或磁盘。

- [x] 首次连接不初始化两端内容（用户 2026-10-16 确认）。开发计划将切换与重连也设计为只建基线，避免额外覆盖；这是设计延伸，不冒称用户逐项批复。
- [x] 失焦到其他电脑应用仍与最后选中设备同步；无目标或未 ready 时停止宿主轮询（随方案确认）。
- [x] 只同步新复制的非空纯文本；空串、没有文本格式时均不清空另一端（用户 2026-10-16 确认）。空格、换行不做 trim。
- [x] 复用同一协议同时支持模拟器与真机；本批至少模拟器实测，USB/无线真机按可用硬件补验（用户 2026-10-16 确认）。

## 5. 不轮询方案补充（2026-10-16）

设备→电脑已有 scrcpy 变化推送，无需轮询。需要选择的是电脑→设备的变化检测。

| 方案                                    | 是否真正不轮询                       | 适用性                                                                       |
| --------------------------------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| Windows 原生 AddClipboardFormatListener | 是，收到 WM_CLIPBOARDUPDATE 后读文本 | Windows 可用，不能用于当前 macOS                                             |
| macOS 原生 changeCount 检测             | 否，定时检查计数，变化后才读正文     | 减少重复读取正文，但需要原生桥或辅助程序                                     |
| 粘贴或返回应用时读取                    | 是，不定时检查                       | 保持设备→电脑自动；电脑→设备变成按需，不能保证电脑复制后设备长按粘贴立即可用 |
| 监听 Cmd+C 等键盘事件                   | 只能观察部分复制意图                 | 漏右键复制、菜单复制和程序写剪贴板，且按键发生时内容可能尚未更新，不推荐     |

macOS 公开的 NSPasteboard 接口提供 changeCount，未找到覆盖任意应用写入的公开通用变化通知；不把 iOS 的 UIPasteboard 通知误用于 macOS。第三方库声称“监听”也必须核对内部是否定时检查。Electron 的 clipboardchange 重构 RFC 属于方案文档，不能据此断言当前 Electron 39 已可用。

结论：本次核查没有找到能在当前 macOS/Electron 39 下可靠覆盖所有复制来源的纯事件替代方案。若坚持不轮询，建议采用按需读取，但需接受电脑→设备不再是实时自动同步；若保持原目标，仍推荐有当前目标时才检查。用户在了解性能预期后已于 2026-10-16 确认采用轮询；尚未开始实现，也没有性能实测结论。
