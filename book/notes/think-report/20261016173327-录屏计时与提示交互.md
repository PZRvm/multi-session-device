# 录屏计时与提示交互功能调研报告

> 创建时间：2026-10-16 17:33（Asia/Shanghai）
> 需求来源：录制时需要在底部栏以外查看用时；两个录屏提示希望支持下次不再提示；完成结果条与 Logcat 图标重叠，需要重新安排。
> 调研单元：2 个
> 状态：技术调研与两轮 grill-me 访谈完成，全部待确认项已获用户确认；用户随后指示开始执行，已按 [交互 plan](../../plans/2026-10-16-recording-interactions.md) 实施。

## 1. 需求理解

### 1.1 功能目标

测试人员录制设备时能看见有效录制用时，暂停不累计，也不恢复此前已移除的整条活动任务栏。减少同一条件下重复的尺寸/无声确认，并允许以后恢复询问。停止后的生成和保存结果仍可找到，操作不被 Logcat 按钮遮挡。

已明确底部栏不放计时、每台设备独立录像、切设备不中断原任务。用户确认：左侧列表只展示录制状态，不要求同时显示多台计时；当前设备计时放在 Logcat 左侧，垂直居中并留出间距；提示按设备和条件记住且跨重启有效。停止后同一位置显示正在生成，文件真正保存后弹原生 dialog，失败提供重试或稍后处理并保留素材；设置通用里用一个按钮同时恢复两类提示。下文保留候选比较，并标明最终选择。

### 1.2 未知点清单

- [x] 现有原生提示框能否放复选框：Electron 39.8.10 API 和 macOS 实现均支持，见 3.3。
- [x] 是否自动记住勾选：API 只返回按钮和勾选状态，应用需要自己存储和决定是否跳过，见 3.5。
- [x] 计时是否需要新时间源：不需要，已有 main 的有效 durationMs，见 2.2。
- [x] 重叠是否来自弹窗或系统图标：来自 App 内 Logcat 的绝对定位与结果列表共享画布外层，见 2.2。
- [x] 哪种布局和记忆范围更符合用户使用习惯：首轮回答已收敛，见 2.3 方案 C 与第 5 节。
- [x] 停止后的生成/失败反馈、恢复提示入口：用户第二轮已确认完整反馈流程，以及通用设置内的统一恢复按钮。

### 1.3 拆分判断

分为「计时与工作区布局」「原生确认与偏好记忆」两个单元。前者只改变 renderer 展示，后者涉及 main 的选择语义和持久化，可分别确认；都不改变采集/编码时间轴与原有媒体验收目标。

## 2. 调研单元：计时与工作区布局

### 2.1 该部分要做什么

给活动任务一个紧凑、持续可见的计时位置；完成结果与日志入口各有自己的布局空间。不增加录屏历史库，不自动播放，不在设备画面里绘制会进入成片的内容。

### 2.2 项目现状

- `src/main/recording/manager.ts` 每秒发布活动任务的有效 `durationMs`；`src/renderer/src/stores/recordingStore.ts` 已有全局快照，不必在 UI 重新用 Date.now 累计。
- `src/renderer/src/components/RecordingTasks.tsx` 按用户上一轮要求隐藏 isRecordingActive 的任务，停止后才呈现排队、生成、结果等行；活动命令保留在 RecordingControls。
- 模拟器行在 `src/renderer/src/components/DeviceRow.tsx`，真机行是 `DeviceListPane.tsx` 内的 ExternalRow。两者已有设备名、副行和动作；新增计时应明确留出位置，不把时间放在可能被省略的副行末尾。
- `src/renderer/src/App.tsx` 中 RecordingTasks 在 canvas-content 之前；Logcat 按钮却相对整个 canvas-area 绝对定位 top/right 10px，因此不会随结果列表占用高度向下移动。截图中的重叠与此实现一致。
- DESIGN.md 要求沿用 token、发丝线、紧凑行式结构；main 是任务事实源，renderer 只镜像。新计时必须覆盖暂停和后台设备，并沿用三语可访问文案。

### 2.3 候选方案

**方案 A：设备行计时，Logcat 归属投屏区（首轮推荐，用户未选）**

- 原理：左侧对应设备行出现「录制 00:10」或「已暂停 00:10」，停止后撤下活动计时；时间保留独立可见槽位。切设备后仍能看见其他设备计时。完成结果留在上方，把 Logcat 的定位容器移到其下方 canvas-content；结果和投屏工具不共享定位原点。
- 来源：现有 [DeviceRow](../../../src/renderer/src/components/DeviceRow.tsx)、[DeviceListPane](../../../src/renderer/src/components/DeviceListPane.tsx)、[App](../../../src/renderer/src/App.tsx) 与 recordingStore；这是针对本项目结构的设计推断，不是框架规定。
- 适配：无需新依赖；单录与双录均对应明确设备。需要照顾列表窄宽、选中反白、真机分组折叠和后台录制。

**方案 B：当前投屏角落计时，结果与日志共用工作区顶栏**

- 原理：计时仅跟当前投屏设备；顶部工具区给结果和 Logcat 固定独立位置，内容按正常布局避让。
- 来源：同一 App/RecordingTasks 的现有布局，可借鉴 [CSS 正常布局与绝对定位](https://www.w3.org/TR/css-position-3/#absolute-positioning) 的区别安排空间。
- 适配：盯着投屏时更容易看见，但切到未录制设备就看不到后台任务时长。新顶栏也可能接近用户刚移除的顶部占位，需要明确接受。

**方案 C：设备行只标状态，Logcat 左侧计时，原生完成 dialog（用户选定）**

- 原理：模拟器行与真机行只显示录制中/已暂停等状态。当前选中设备才在 Logcat 左侧显示有效用时；两者归入同一工具组，垂直居中、间隔清楚，未录制的当前设备不冒用后台设备计时。完成后移除上方结果条，保存结果改为原生 dialog。
- 来源：用户首轮回答；技术基于已有全局快照、App 的日志入口和 [Electron 原生 MessageBox](https://www.electronjs.org/docs/latest/api/dialog#dialogshowmessageboxwindow-options)。
- 适配：不同时铺开多台计时，切换设备后即时反映该设备状态。用同一容器排工具位置，移除结果条后也消除本次结果与图标抢空间的问题。

独立「录屏结果」入口也可消除大列表占位，但需多点一次才能找到文件；本轮用户明确选择原生 dialog，不采用独立历史入口。

### 2.4 可行性分析

| 维度     | 方案 A                                       | 方案 B                                   |
| -------- | -------------------------------------------- | ---------------------------------------- |
| 技术匹配 | 复用全局任务快照，后台/多设备可见            | 复用同一快照，仅显示选中设备             |
| 规则冲突 | 不恢复活动顶部任务条，保留列表行式结构       | 需确认用户是否接受新的工作区顶栏         |
| 成本     | 两类设备行各接一处状态；调整 Logcat 定位容器 | 新计时位置及顶栏响应式组合，布局改动更广 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**。沿用现有组件和任务状态，按用户选择实施 C；完成通知复用 Electron 原生 MessageBox。生成和失败反馈流程也已确认。

落地文件为 DeviceRow、DeviceListPane、App、录屏三语文案和共用时长/状态展示组件；计时读 main 的 durationMs，录制推进、暂停冻结、准备/续录等待显示真实状态。不每秒重载设备列表，不新增媒体 reader。App 将时间与 Logcat 放进同一横向工具组，不再独立设定两者的绝对位置；RecordingTasks 不再作为顶部结果列表挂载，但任务快照订阅仍需有稳定所有者。

完成通知在 main 管理：只在最终 MP4 发布成功后才可称保存成功，按 taskId 去重，并提供「在文件夹中显示 / 关闭」，不自动播放。用户已确认停止后在 Logcat 左侧显示「正在生成…」；失败弹原生 dialog，提供「重新生成 / 稍后处理」，素材保留。推荐用可见主窗作为原生 dialog 的父窗；主窗关闭期间先保留待提示结果，重开再展示，不能因显示通知而终止后台任务。多结果需串行避免叠窗。实施时使用 impeccable 对照宽窄窗、当前设备切换、暂停和日志展开态。

## 3. 调研单元：原生确认与偏好记忆

### 3.1 该部分要做什么

在「采集尺寸不同」和「无法录设备声音」两种原生确认里提供明确的记住选择交互。记住继续使用实际采集尺寸，或记住本条件下无声继续；取消不生成偏好。清理材料、放弃任务和真正退出等确认不在本次免提示范围。

### 3.2 项目现状

- `src/main/recording/index.ts` 的 recordingConfirm 直接调用 dialog.showMessageBox，目前只返回 `response === 0`，未使用 checkbox。
- `manager.ts` 在开始前对照 wm size 与采集尺寸；截图为 1080×2340 对 1080×2336，仅差 4px。代码目前只判断尺寸不同；本调研不推断这 4px 的唯一原因，也不擅自放宽提示阈值。
- 音频每次尝试采集，不可用时才问 silent；现有 Android SDK 31 会进入该分支。记住选择不应跳过未来的音频能力检查，更不能把恢复正常的设备永久改为无声录制。
- `src/main/theme/store.ts` 有 userData JSON、版本校验、内存镜像、串行 tmp+rename 的持久化先例，可复用模式，不把录屏偏好混进设备元数据或主题文件。
- 通用 dialog IPC 已返回 checkboxChecked，但 `src/shared/types.ts` 的 DialogOptions 未声明复选框。录屏当前直接在 main 调用，所以本次不必扩大通用 renderer dialog 权限。

### 3.3 候选方案

**方案 A：Electron 原生复选框 + 应用持久化（推荐）**

- 原理：给 showMessageBox 设置 checkboxLabel / checkboxChecked，读取返回的 response / checkboxChecked；在有效肯定答复后由 main 写入独立偏好。
- 来源：[Electron 官方 dialog API](https://www.electronjs.org/docs/latest/api/dialog#dialogshowmessageboxwindow-options)、[本项目实际版本 39.8.10 的 macOS 实现](https://github.com/electron/electron/blob/v39.8.10/shell/browser/ui/message_box_mac.mm)。后者用 NSAlert.showsSuppressionButton 呈现复选框并返回其状态；本地 electron.d.ts 亦包含这些字段。
- 适配：保持截图中的原生样式与已有主进程职责，无新增依赖。系统负责复选框外观，不承诺任意自绘布局或准确像素位置。

**方案 B：只在本次应用会话记住**

- 原理：仍用同一原生复选框，选择存 main 的内存 Map，重启后再次询问。
- 来源：同一 Electron API；存储时长是应用策略。
- 适配：实现较少，易撤销；但每次打开仍重复，文案应写「本次运行不再提示」，不能暗示永久生效。

**方案 C：自绘确认面板**

- 原理：自定义组件提供复选框与更复杂选项。
- 来源：项目已有 renderer 组件栈；无需外部库，但违反当前 DESIGN.md 的原生短确认约定且本需求用现成 API 即可。
- 适配：不推荐；为单个复选框替换整套原生确认没有必要。

### 3.4 可行性分析

| 维度     | 方案 A                                     | 方案 B                     | 方案 C                        |
| -------- | ------------------------------------------ | -------------------------- | ----------------------------- |
| 技术匹配 | 已安装版本和 macOS 源码支持                | 同左                       | 可以自绘，但需新面板/窗口流程 |
| 规则冲突 | 符合 main 原生短确认                       | 符合，但需准确说明生效时长 | 与现有原生确认约定冲突        |
| 成本     | 小型偏好模块、恢复提示入口、三语和边界校验 | 仅内存状态，维护最少       | 布局/键盘/窗口/外观维护较多   |

### 3.5 结论与实施建议

结论：**采用现成方案**。复选框使用 Electron 原生能力，偏好策略由本项目实现。用户已选 A 的按设备/条件记忆，跨重启有效。

推荐交互文案分别为「此设备遇到相同尺寸时不再提示」「此设备遇到相同情况时自动无声录制」，初始不勾选。只有勾选且点击继续才记录；取消、关闭或任务已停止的迟到答复均不记录。尺寸与音频选择各自独立；非首次错误不会因为曾记住另一个原因就无条件放行。

按已确认的设备/条件记忆，尺寸条件使用方向归一后的原尺寸/采集尺寸组合；音频条件使用稳定的原因类别与 SDK 等能力信息，不直接拿整段易变异常字符串作键。真机 USB/无线尽量用 main 可验证实体身份，无法证明同一实体时不跨连接套用。每次录制仍重新判断实际能力，音频恢复后正常录音。暂不免掉停止后编码降采样的 resize 提示，避免把采集尺寸接受误用为任意降质接受。

建议在 `main/recording/` 新增独立偏好模块，调整 index.ts 的原生返回数据和 manager.ts 的确认上下文：必须在确认答复仍属于有效任务后才能落盘。并发任务通过串行写队列合并，不让两个复选选择互相覆盖。用户已确认在设置「通用」中提供一个「恢复录屏提示」按钮，同时清除尺寸与无声提示的记忆，不新增整个录屏设置分类；恢复操作不删除视频、录制材料或改变进行中的任务。持久化失败时不得宣称重启后仍有效。

## 4. 风险与开放问题

- 左侧只显示录制状态，不显示多设备计时。计时跟当前设备，切到没有任务的设备应隐藏；窄窗需保留时间与 Logcat 的对齐和间距，不能把按钮挤出画布。
- 已选按设备/条件记忆，尺寸或故障条件变化重新询问；不能泛化为所有设备永远无声。
- 恢复询问入口需要可找到，不能只靠删配置文件；偏好损坏按默认重新提示，不影响已录材料。
- 结果条/Logcat 重叠已有明确布局原因，见 [issue](../issue/2026-10/2026-10-16-recording-result-logcat-overlap.md)。已移除结果条并采用原生结果 dialog，issue 已按构建界面验证关闭。
- 本轮 UI/偏好设计不等于解决十分钟 112/106ms 同步与真机音频待验问题，父 plan 状态保持原样。
