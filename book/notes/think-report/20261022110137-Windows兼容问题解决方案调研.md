## 1. 需求理解

### 1.1 功能目标

本项目一期宿主为 macOS（`PRODUCT.md:9`），Windows 支持未排期（`PRODUCT.md:34`）。此前会话已逐文件核实出一份 Windows 兼容性问题清单（16 项实质问题 + 2 项编解码验证项）。本次调研为清单中除编解码（原 17/18 项）外的每个问题寻找**有官方出处或成熟实践背书的解决方案**，形成可直接进 plan 的选型结论，服务于将来「Windows 支持」立项。本报告只做方案选型，不写实现代码，不修改 `src/`。

## 2. 调研单元 A：进程管理

### 2.1 该部分要做什么

Windows 上等价实现四个能力：进程树终止（问题 1）、优雅退出（问题 2）、「关窗不停设备」的宿主方案（问题 3）、消除子进程黑框（问题 4）。不做：模拟器功能本身的任何改动。

### 2.2 项目现状

- `src/main/emulator/runner.ts:282-284`：spawn `detached: true` 建独立进程组，macOS 上「真身 qemu 与启动器同组」按组整杀。
- `runner.ts:424-429`：`killGroup` 先 `process.kill(-pid, signal)`（负 PID 进程组杀，POSIX 专属），catch 回退 `child.kill(signal)`——回退只杀直接子进程，Windows 上会留孤儿 qemu。
- `runner.ts:406`：stop/cancel 走 SIGTERM → 3s → SIGKILL 梯子。
- `src/main/index.ts:46-50`：`window-all-closed` 非 darwin 即 `app.quit()`（Windows 惯例分支，有意为之）。
- `src/main/index.ts:56-101`：`before-quit` → `prepareAppShutdown()`（`src/main/devices/lifecycle.ts:301`，`runner.disposeAll()`）→ 停不掉才弹对话框。
- 全仓库 spawn 均未传 `windowsHide`（grep 为零）。

### 2.3 候选方案

**方案 A1：`taskkill /T` 树杀（借鉴 tree-kill 思路手写平台分支）**

- 原理：Windows 官方命令 `taskkill /PID <pid> /T /F` 递归终止进程树；npm 包 tree-kill 在 Windows 上就是这条命令的封装（Unix 上递归杀 ppid 链）。自写平台分支约 20 行，可按项目风格接缝注入做单测。
- 来源：taskkill 官方文档 <https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/taskkill>；tree-kill 封装事实 <https://stackoverflow.com/questions/32705857/cant-kill-child-process-on-windows>；Node 官方确认负 PID 组杀在 Windows 抛错 <https://nodejs.org/api/process.html>
- 适配点：`runner.ts` 的 `killGroup` 增加 win32 分支；`detached: true` 在 Windows 不再需要（无进程组语义，且与 windowsHide 有冲突，见 A4）。
- 看过不选：直接引入 tree-kill 包——功能就是一条命令封装，引包不如自写可控（项目无此依赖，接缝风格自写更贴合）。

**方案 A2：emulator console `kill` 命令做优雅退出（采用官方通路）**

- 原理：模拟器控制台（console 端口 5554+）支持 `auth <token>` 认证后发 `kill` 命令，emulator 自行收尾（存状态、清锁）——这才是跨平台的「优雅」，SIGTERM 梯子在 Windows 本就退化为硬杀。项目已持有 console 端口分配（`ports.ts`）与 auth token 落盘口径（PRD 4.2「控制台 auth token 落应用自有目录」）。
- 来源：官方文档 <https://developer.android.com/studio/run/emulator-console>；实践佐证 <http://vaughandroid.me/2016/05/27/killing-the-android-emulator/>
- 适配点：`runner.ts` 停止路径先走 console kill（带超时），超时再树杀兜底。**注意这是新增通路**（现状直接杀进程），是否纳入需拍板——不纳入则 Windows 接受硬杀 + 依赖既有的 AVD 锁残留拦截（`runner.ts:172`）。

**方案 A3：Electron Tray 实现「关窗到托盘、后台继续」（采用现成 API）**

- 原理：主窗 `close` 事件 `preventDefault()` + `hide()`，托盘图标负责显示/退出；`before-quit` 清理链复用现状不动。这是 Signal 等成熟 Electron 应用的标准形态。
- 来源：Electron 官方 Tray 教程 <https://electronjs.org/docs/latest/tutorial/tray>；close-to-tray 模式 <https://stackoverflow.com/questions/37828758/electron-js-how-to-minimize-close-window-to-system-tray-and-restore-window-back>
- 适配点：新增 `src/main/tray.ts`；`window/index.ts` 主窗 close 分支；退出菜单项显式走 `app.quit()`（绕过 preventDefault）。macOS 行为不变（现状本就后台）。

**方案 A4：`windowsHide: true` 消除黑框（采用现成选项）**

- 原理：Node 官方 spawn 选项，Windows 上不创建子进程控制台窗口，默认 `false`。
- 来源：Node 官方文档 <https://nodejs.org/api/child_process.html>（同页还有官方段落：`.bat`/`.cmd` 必须经 `cmd.exe /c` 或 shell 执行——与硬阻塞 2 的修复直接相关）
- 适配点：全仓 spawn 调用点（`sdk.ts`/`avd.ts`/`runner.ts`/`cameras.ts`/`adb.ts`/`downloader.ts`）补 `windowsHide: true`。**坑**：`nodejs/node#21825` 报告 `detached: true` 与 windowsHide 组合在部分场景仍弹框（<https://github.com/nodejs/node/issues/21825>）——A1 落地后 Windows 分支去掉 detached，正好绕开。

### 2.4 可行性分析

| 维度 | A1 taskkill 树杀 | A2 console kill | A3 Tray | A4 windowsHide |
| --- | --- | --- | --- | --- |
| 技术匹配 | 官方命令，覆盖 qemu 子进程；Node 负 PID 在 win 抛错已被官方文档确认 | 官方通路；项目已持有端口与 token 两大前提 | Electron 39 完整支持 | Electron 内置 Node 完整支持 |
| 规则冲突 | 无 | 无（PRD 4.2 token 口径已预留） | 无；产品行为变化需拍板 | 无 |
| 成本 | 约 20 行 + 单测，零依赖 | 新增 client 小模块（TCP + auth + 超时） | 新增 tray 模块 + 图标资源（.ico 已有） | 每个调用点一行 |

### 2.5 结论与实施建议

- 结论：**借鉴思路手写**（A1 树杀平台分支）+ **采用现成方案**（A2 官方 console kill、A4 windowsHide 选项）；A3 托盘**已拍板不做（2026-10-22）**——Windows 关窗即退出，但退出前若本工具启动的设备在跑，先弹确认框（「有 N 台设备正在运行，退出将停止它们」：确认=继续退出并优雅停全部；取消=留在应用）。注意与现状的差异：现有 `before-quit` 对话框只在实例**停不掉**时出现，新决策把「确认」提前到停机之前，落点在 `before-quit` 入口按平台+运行态加一道确认。
- 落地路径：① `runner.ts` killGroup 加 win32 分支（taskkill `/T`，先不带 `/F` 试优雅、带 `/F` 兜底）并去掉 Windows 的 detached；② 全部 spawn 点补 `windowsHide: true`；③ `before-quit` 序列头部（`prepareAppShutdown` 之前）加「有设备在跑 → 确认退出」对话框（win32；mac 无关窗退出路径，维持现状）；④ A2 console kill 优雅退出作为独立小阶段另行排期。

## 3. 调研单元 B：文件系统

### 3.1 该部分要做什么

Windows 上等价实现：占用锁下的 rm/rename 容错（问题 5）、跨卷目录移动（问题 6）、路径比较大小写（问题 7）、长路径防御（问题 8）、临时文件可见性（问题 9）。

### 3.2 项目现状

- `src/main/emulator/downloader.ts:116`：`moveDir` 即 `fs.rename`，无 EXDEV 回退；`:99` 解压用系统 `unzip`（Windows 无此命令，属硬阻塞）。
- `src/main/emulator/sdk.ts:411-413,434,436`：JRE/cmdline-tools 归位全靠 `rename`。
- `src/main/emulator/sdkMigration.ts` / `sdkSourceSwitch.ts`：SDK 切换迁移的 `rm(recursive)`/`rename`——Windows 上撞模拟器占用或杀软扫描句柄时报 EBUSY/EPERM。
- `src/main/emulator/studioDetect.ts:246-262`：`isStudioSdk` 用 realpath 后字符串全等判定 SDK 归属——Windows 大小写漂移会误判。
- 临时名 `.tmp-jre`/`.archive.bin`/`.downloading.zip`（`sdk.ts`/`downloader.ts`）在 Windows 资源管理器可见。

### 3.3 候选方案

**方案 B1：rename/move 带重试 + EXDEV 回退（借鉴 graceful-fs 与 fs-extra 思路手写）**

- 原理：graceful-fs 官方 README 明言——Windows 上杀软短暂锁目录导致 rename 报 EPERM/EACCES，它对 rename 做「最长 1 秒的重试」；fs-extra 的 `move` 则在 rename 报 EXDEV 时回退为 copy + delete（其仓库自带 `CROSS_DEVICE_PATH` 跨设备测试钩佐证成熟度）。自写一个小工具函数：rename → EPERM/EBUSY/EACCES 退避重试（如 100ms×10）→ EXDEV 回退 `fs.cp(recursive)` + `rm`。
- 来源：graceful-fs <https://www.npmjs.com/package/graceful-fs>；fs-extra move <https://github.com/jprichardson/node-fs-extra>；EXDEV 场景 <https://stackoverflow.com/questions/4568689/how-do-i-move-file-a-to-a-different-partition-or-device-in-node-js>
- 补充事实：Node 官方 fs.rm 对 EBUSY/EMFILE/ENOTEMPTY/EPERM **已自带线性退避重试**（<https://nodejs.org/api/fs.html>）——重试工具只需覆盖 rename/move，rm 可依赖内建。
- 看过不选：直接引入 graceful-fs（全局 monkey-patch fs，侵入性强）/ fs-extra（整个库只用一个 move）——与项目「接缝注入、可单测」风格不符，借思路即可。

**方案 B2：路径比较大小写规范化（手写，几行）**

- 原理：NTFS 大小写不敏感，realpath/环境变量返回的盘符与大小写不稳定；比较前对 win32 路径做 `toLowerCase()`（分隔符 `path.join` 产物已统一）。
- 来源：现象与讨论见 <https://stackoverflow.com/questions/1880321/why-does-the-260-character-path-length-limit-exist-in-windows> 同批 Windows 路径语义问答；核心是平台事实，无第三方库需求
- 适配点：`studioDetect.ts` 的 `isStudioSdk` 与 `looksLikeSdkRoot` 类字符串比较处加平台分支。

**方案 B3：长路径双轨防御（策略优先，longPathAware 为辅）**

- 原理：Windows 解除 260 限制需**注册表 + 应用清单 longPathAware 双条件**（微软官方），且清单逐 exe 生效、注册表在用户机器上不可控。第一道防线应是缩短根路径（应用自管 SDK 根已固定在 `%APPDATA%` 下，实测前缀约 70-90 字符，正常用户名下 system-images 深路径 < 260）；第二道才是给打包产物注入 longPathAware 清单（electron-builder 的 manifest 注入依赖底层 electron-packager 的 `application-manifest` 支持）。
- 来源：微软官方双条件说明 <https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation>；逐 exe 清单生效实例（jq 仓库） <https://github.com/jqlang/jq/issues/3658>；electron-builder manifest 讨论 <https://github.com/electron-userland/electron-builder/issues/1649>
- 适配点：一期只做「路径长度检测 + 超限时提示用户换短路径 SDK 根」（设置页已有 SDK 根切换能力）；清单注入挂到 Windows 适配的打包阶段再说。

**方案 B4：`attrib +h` 隐藏临时文件（手写，一行命令）**

- 原理：Windows 隐藏靠文件属性而非点前缀；`spawn('attrib', ['+h', path])` 即可。注意 Node 官方文档坑：隐藏文件不能用 `w` flag 直接打开写（要 `r+`），本项目临时文件是先写后隐藏、用完即删，不踩此坑。
- 来源：<https://stackoverflow.com/questions/22053335/node-js-create-hidden-directory-windows>；`w` flag 坑 <https://nodejs.org/api/fs.html>
- 适配点：可选；或干脆接受可见（临时文件生命周期秒级，Windows 用户常见 `.tmp` 文件）。

### 3.4 可行性分析

| 维度 | B1 重试+回退 | B2 大小写规范化 | B3 长路径双轨 | B4 attrib |
| --- | --- | --- | --- | --- |
| 技术匹配 | 覆盖 5/6 两问题；mac 上无害（重试永不触发、EXDEV 不存在） | 覆盖问题 7 | 覆盖问题 8 且承认注册表不可控的现实 | 覆盖问题 9 |
| 规则冲突 | 无 | 无 | 无 | 无 |
| 成本 | 一个 ~40 行工具函数 + 单测 | 几行 | 一期仅检测+提示，近零成本 | 一行，可选 |

### 3.5 结论与实施建议

- 结论：**借鉴思路手写**（B1 核心工具）+ **完全手写**（B2/B4）+ **策略优先**（B3 一期只做检测提示，清单注入缓行）。
- 落地路径：新增 `src/main/emulator/fsWin.ts`（或并入现有工具层）：`moveDirWithFallback` / `renameWithRetry`；替换 `downloader.ts:116`、`sdk.ts` 归位、`sdkMigration`/`sdkSourceSwitch` 的裸 rename；`studioDetect.ts` 比较处加 win32 大小写分支。全部接缝注入可单测，mac 行为零变化（回归保障）。

## 4. 调研单元 C：打包与安全

### 4.1 该部分要做什么

解决：未签名产物触发 SmartScreen（问题 10）；Defender 实时扫描拖慢下载-校验-解压与模拟器冷启动（问题 11）。

### 4.2 项目现状

- `electron-builder.yml`：win/nsis 段齐全（icon.ico、NSIS 配置在），**无任何签名配置**；`build:win` 脚本在（`package.json:23`）。
- 下载链路：`downloader.ts` 下载 2GB+ 镜像 zip → 落盘 → 整文件重读算 sha1（`:84-91`）→ 系统 `unzip` 解压（`:99`）。
- 依赖全纯 JS 无原生模块（mac/win 交叉打包可行）。

### 4.3 候选方案

**方案 C1：Azure Trusted Signing（采用现成方案，electron-builder 26 内置）**

- 原理：微软云签名服务，个人开发者低价档（产品页口径），electron-builder 自 25.1.0 起原生支持 `win.sign.type: "azure"` 配置（本项目 electron-builder ^26.0.12 满足）。Electron 官方教程称其为「Windows 上最便宜的签名选项，可消除 SmartScreen 警告」。
- 来源：electron-builder Win 签名文档（含完整配置示例） <https://www.electron.build/docs/features/code-signing/code-signing-win/>；Electron 官方教程 <https://electronjs.org/docs/latest/tutorial/code-signing>；Azure 产品页 <https://azure.microsoft.com/en-us/products/artifact-signing>
- **如实说明反面证据**：electron-builder 签名总览明确「EV 证书 2024 年起不再有即时 SmartScreen 信任，OV 与 EV 一致、信誉随下载量积累」（<https://www.electron.build/docs/features/code-signing/>）；MS Learn Q&A 2026-04 仍有 Azure 签名后见警告的案例（<https://learn.microsoft.com/en-us/answers/questions/5861538/azure-trusted-signing-still-seeing-smartscreen-war>）。预期应设为「显示发布者名 + 信誉随分发逐步建立」，不是签约即无警告。
- 看过不选：OV/EV 传统证书（年费高、EV 需硬件令牌且 2024 后无即时信任优势）；不签名（SmartScreen 全量拦截 + 企业环境直接被封）。

**方案 C2：设置页 Defender 排除引导（借鉴 Android 官方建议手写）**

- 原理：Android 官方文档确认杀软实时扫描会显著拖慢构建/模拟器（「forces the build process to halt each time a file is created while it scans that file」），并给出排除目录建议表（Gradle 缓存、SDK 目录、IDE 系统目录），同时警告**不要整体关闭实时扫描**。等价到本项目：引导用户把**自管 SDK 根**（下载/解压）与 **AVD 数据目录**（冷启动）加入 Defender 排除；「一键添加」用官方 `Add-MpPreference -ExclusionPath` cmdlet 经 UAC 提权执行，绝不静默。
- 来源：Android 官方 studio-config（含目录表与 Caution 原文，已核对） <https://developer.android.com/studio/intro/studio-config>；Add-MpPreference 官方文档 <https://learn.microsoft.com/en-us/powershell/module/defender/add-mppreference>
- 适配点：设置页 Windows 专属「性能建议」卡片 + `shell.openExternal('ms-settings:windowsdefender')` 引导；第三方杀软（火绒/360）只给通用指引文案。
- 顺带受益（此前已论证，属硬阻塞修复时一并做）：sha1 校验并入下载流（省一次 2GB 重读）、解压改 Windows 自带 `tar.exe`（Win10 1809+ 内置 bsdtar，与 mac 同命令）并给逐条目进度——两者让「感知慢」直接减半。

### 4.4 可行性分析

| 维度 | C1 Azure Trusted Signing | C2 Defender 引导 |
| --- | --- | --- |
| 技术匹配 | electron-builder 26 原生支持；需 Azure 账号 + 身份验证（个人 3 年身份核验流程） | 纯官方 cmdlet + 官方建议背书 |
| 规则冲突 | 无（凭据走 CI secrets，不入仓库） | 无（UAC 显式确认，符合安全纪律） |
| 成本 | 月费低价档 + 一次性身份验证流程 | 一个设置页卡片 + 引导文案 |

### 4.5 结论与实施建议

- 结论：C1 签名**已拍板不做（2026-10-22，自用场景）**——接受首次运行 SmartScreen「更多信息 → 仍要运行」提示，本节方案留档备将来分发时启用；C2 **借鉴思路手写**（Defender 排除引导保留，自用同样受益于下载/解压提速）。
- 落地路径：① 仅做 C2：设置页新增 Windows 性能卡片（i18n 三语字典同步）；② sha1 流式化与 tar.exe 解压替换已并入主体工程报告（20261022125639 §3/风险节）。

## 5. 调研单元 D：模拟器运行环境

### 5.1 该部分要做什么

解决：Windows 硬件加速体系差异（问题 12）、镜像 ABI 与宿主架构绑定（问题 13）、摄像头隐私模型差异（问题 14）。

### 5.2 项目现状

- `src/main/emulator/runner.ts`：启动参数未含 `-accel` 相关分支（mac 上 Hypervisor.Framework 零配置）。
- `src/main/emulator/catalog.ts`：镜像目录按 manifest 列出，`abi` 是数据字段；`src/shared/i18n/errors.ts:435` 的跨架构提示只写了 macOS Apple Silicon 场景。
- `src/main/emulator/cameras.ts:65-70`：非 darwin 权限直接 `granted`/`true`；`sdkIpcSkins.ts:75` 的「去系统开权限」深链只有 darwin 分支（`x-apple.systempreferences:`）。

### 5.3 候选方案

**方案 D1：WHPX 为唯一推荐加速方案（采用官方路径）**

- 原理：Google 官方在 Windows 推荐 Windows Hypervisor Platform（Win10 1803+，系统功能里开启）；备选 AEHD 要求关闭 Hyper-V 系功能且**将于 2026-12-31 停用**，官方已引导用户迁移 WHPX——新项目没有理由选 AEHD。应用侧做法：启动失败时识别 WHPX 缺失错误，引导用户开启（`ms-settings:windows-optionalfeatures` 可直达系统功能页）。
- 来源：官方加速配置页 <https://developer.android.com/studio/run/emulator-acceleration>；AEHD 停用公告（emulator 37.1.11 release notes） <https://developer.android.com/studio/releases/emulator>

**方案 D2：镜像目录按宿主架构过滤 x86_64（采用官方事实约束）**

- 原理：x86_64 Windows 宿主只能跑 x86_64 系统镜像（API 21+ 全版本覆盖）；arm64 镜像在 Windows 不可用（ARM 宿主支持目前是 Linux 方向）。应用侧：Windows 下目录与本地扫描（`catalog.ts` 的 abi 字段）过滤为 x86_64，跨架构提示文案补 Windows 场景。
- 来源：x86_64 镜像覆盖事实 <https://github.com/ReactiveCircus/android-emulator-runner/issues/235>；ARM 宿主支持现状（emulator release notes） <https://developer.android.com/studio/releases/emulator>；x86 镜像跑 ARM 应用的官方说明 <https://android-developers.googleblog.com/2020/03/run-arm-apps-on-android-emulator.html>

**方案 D3：摄像头空列表 → 官方深链引导（采用官方通路）**

- 原理：Windows 摄像头隐私设置（设置 > 隐私和安全性 > 相机）的「相机访问」总开关会拦掉桌面应用；`ms-settings:privacy-webcam` 是微软官方 URI scheme，Electron `shell.openExternal` 可直达。应用侧：Windows 上 `-webcam-list` 结果为空时，给出该深链入口（补齐 `sdkIpcSkins.ts:75` 缺的分支）。
- 来源：微软官方相机权限页 <https://support.microsoft.com/en-us/windows/privacy/manage-app-permissions-for-a-camera-in-windows>；ms-settings URI 官方文档 <https://learn.microsoft.com/en-us/windows/apps/develop/launch/launch-settings>；Electron 内实践 <https://www.bigbinary.com/blog/request-camera-micophone-permission-electron>

### 5.4 可行性分析

| 维度 | D1 WHPX | D2 ABI 过滤 | D3 深链 |
| --- | --- | --- | --- |
| 技术匹配 | 官方推荐 + AEHD 停用使然；错误识别需真机采样错误输出 | catalog 已有 abi 字段，过滤是纯数据层改动 | 官方 URI + Electron 现成 API |
| 规则冲突 | 无 | 无（与 errors.ts 既有跨架构提示同体系） | 无 |
| 成本 | 失败识别 + 引导 UI；真机回归量在 WHPX 与 Hyper-V 系功能/第三方虚拟机冲突场景 | 小 | 小 |

### 5.5 结论与实施建议

- 结论：三个子问题全部**采用现成方案/官方通路**。
- 落地路径：① `catalog.ts` 目录与本地扫描加宿主架构过滤（win32 → x86_64）；② `errors.ts` 跨架构文案补 Windows 措辞；③ runner 启动失败的错误分类里加 WHPX 缺失识别 + `ms-settings:windows-optionalfeatures` 引导；④ `sdkIpcSkins.ts:75` 补 `ms-settings:privacy-webcam` 分支。全部为 Windows 分支新增，mac 零改动。

## 7. 风险与开放问题

- **SmartScreen 信誉证据冲突**：Electron 官方称 Azure Trusted Signing 可消除警告，但 electron-builder 文档与 MS Learn 2026-04 案例均指向「信誉随下载积累、过渡期仍可能弹警告」——对外预期要按后者管理。
- **windowsHide 与 detached 冲突**（`nodejs/node#21825`）：树杀方案落地时必须同步去掉 Windows 分支的 detached，需真机验证。
- **WHPX 环境冲突面大**：与 Hyper-V 系功能（含内核隔离/基于虚拟化的安全）、VMware/VirtualBox/Docker Desktop 的组合冲突需真机回归矩阵，无法在 mac 侧预判。
- **长路径注册表不可控**：longPathAware 双条件依赖用户机器注册表，方案只能「检测 + 提示」，不能承诺根治。
- **console kill 是新增通路**（A2）：现状 runner 不走 console，引入它是行为变化（停止耗时增加一个 console 往返），需产品拍板是否纳入。
