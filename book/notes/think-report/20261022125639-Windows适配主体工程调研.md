## 1. 需求理解

### 1.1 功能目标

前一份调研解决了 Windows 兼容的「外围问题」（进程、文件系统、打包、环境、UI），本报告解决**适配主体工程**的四个硬阻塞：SDK 引导钉死 macOS ARM64 二进制与 macOS 布局（`sdk.ts`）、二进制路径无 `.exe`/`.bat`、镜像下载依赖系统 `unzip`、Studio/SDK 检测链全按 macOS（`mdfind`、`~/Library`）。产出可直接进 plan 的平台化方案选型。与前报告的 B1（rename 重试）、A4（windowsHide）等结论配合使用。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] Windows 版 cmdline-tools / Temurin JRE 的钉版下载源与目录布局？→ §2（官方 zip 真实 URL 与 Windows 布局已确认）
- [x] `.bat`/`.cmd` 在 Node 里怎么合法 spawn？→ §2（Node 官方文档有专节：`cmd.exe /c` 或 exec）
- [x] `unzip` 在 Windows 换什么？→ §3（系统 tar.exe 官方支持 zip；Expand-Archive 官方确认 2GB 上限，排除）
- [x] 大 zip（>2GB 条目）纯 JS 有什么备选？→ §3（yauzl/zip.js 均支持 ZIP64）
- [x] Windows 上 Studio 装在哪、配置目录在哪、默认 SDK 在哪？→ §4（`Program Files`、`%APPDATA%\Google\AndroidStudio*`、`%LOCALAPPDATA%\Android\Sdk`，官方文档确认）
- [x] `mdfind` 的 Windows 替代？→ §4（无 Spotlight 等价物；注册表卸载键 / 固定目录扫描）

### 1.3 拆分判断

拆 3 个单元：F 引导平台化（下载源 + 布局 + 路径后缀 + .bat 规则，互相同处一个文件群，合为一单元）、G 解压选型（独立决策点，且 F 依赖它落地）、H 检测链（独立模块 `studioDetect.ts`）。顺序：G → F → H（G 的结论被 F 引用）。

## 2. 调研单元 F：SDK 引导平台化

### 2.1 该部分要做什么

`bootstrapSdk`（`src/main/emulator/sdk.ts:372`）在 Windows 上可用：按平台选下载源、按平台归位目录布局、`sdkPaths` 补 `.exe`/`.bat`、`.bat` 合法执行。不做什么：检测链（H 单元）、解压实现（G 单元）。

### 2.2 项目现状

- `sdk.ts:12-17`：钉版源只有 macOS——Temurin `aarch64_mac` tar.gz、`commandlinetools-mac_arm64-16111833_latest.zip`。
- `sdk.ts:33-55`：`sdkPaths` 全按 mac 布局——`jre/Contents/Home/bin/java`、`cmdline-tools/latest/bin/sdkmanager`（无后缀）、`platform-tools/adb`、`emulator/emulator`。
- `sdk.ts:407-413`：JRE 归位假设 `<version>-jre/Contents` 结构（mac 专属 bundle）。
- `sdk.ts:325` / `downloader.ts`：直接 `spawn(paths.sdkmanagerBin, …)`——Windows 上 sdkmanager 是 `.bat`，Node ≥18.20/20.12 起直接 spawn `.bat` 抛 EINVAL（安全修复行为）。
- `avd.ts:63-66`：`avdmanager` 同样无后缀；`JAVA_HOME` 指向 mac JRE 布局。

### 2.3 候选方案

**方案 F1：按平台钉版双源 + 布局归位平台分支（采用官方产物，手写平台分支）**

- 原理：官方 cmdline-tools 每个平台各出一个 zip（命名 `commandlinetools-<os>-<build>_latest.zip`），Windows 版不带架构段；Temurin 21 JRE 各平台独立产物，Windows x64 提供 zip（免安装 MSI 之外另有 zip 供手动部署），解压后布局是 `jdk-21.x+x-jre/bin/java.exe`——没有 mac 的 `Contents/Home` 层。实现上：`PINNED_SOURCES` 变成按 `process.platform` 选择的两套常量；JRE 归位逻辑平台分支（win 直接 `rename(tmp/<top>, root/jre)`，javaBin 指向 `root/jre/bin/java.exe`）；`sdkPaths` 的 javaBin/sdkmanager/avdmanager/adb/emulator 五条路径加 `.exe`/`.bat`。
- 来源：Windows cmdline-tools 真实下载地址（dl.google.com 直链，已在检索结果中确认存在）<https://dl.google.com/android/repository/commandlinetools-win-15859902_latest.zip>；命名规则 <https://github.com/codepath/android_guides/wiki/installing-android-sdk-tools>；Temurin Windows x64 JRE 下载页 <https://adoptium.net/temurin/releases/?os=windows&package=jre&arch=x64&version=21>；zip 手动部署口径 <https://adoptium.net/installation>
- 适配点：`sdk.ts` 常量区与 `sdkPaths`、`bootstrapSdk` 的 JRE/cmdline-tools 归位段。**钉版纪律不变**（代码注释既定口径：「升级 = 显式改这里 + 重跑真机集成」），Windows 版 build 号与 sha1 校验值换源时显式更新。

**方案 F2：`.bat` 经 `cmd.exe /c` 执行（采用 Node 官方口径）**

- 原理：Node 官方文档专节「Spawning .bat and .cmd files on Windows」：要么 `exec('my.bat', …)`，要么 `spawn('cmd.exe', ['/c', 'my.bat'])`；含空格路径要整体加引号。`sdkmanager`/`avdmanager` 在 Windows 上是 `.bat` 启动脚本。
- 来源：Node 官方文档 <https://nodejs.org/api/child_process.html#spawning-bat-and-cmd-files-on-windows>
- 适配点：封装一个「平台执行器」小工具（win32 下 `.bat` → `cmd.exe /c` 包装、`.exe` 直接 spawn；同时收口前报告 A4 的 `windowsHide`），`sdk.ts`/`avd.ts` 的 spawn 调用点统一换用。进度行解析（`parseSdkManagerPercent`）不动——`cmd.exe` 包装不影响 stdout 内容。

**看过不选**：`shell: true` 传给 spawn——官方段落里 exec 与 cmd.exe 直呼均可，`shell: true` 会被 Node 文档提示注入风险（路径含空格/特殊字符时引号语义漂移），显式 `cmd.exe /c` 更可控。

### 2.4 可行性分析

| 维度 | F1 双源平台分支 | F2 cmd.exe /c 执行器 |
| --- | --- | --- |
| 技术匹配 | 官方产物各平台齐全；布局差异已逐条核实 | Node 官方推荐路径； EINVAL 行为有官方背景 |
| 规则冲突 | 无；钉版纪律（注释既定）保持 | 无 |
| 成本 | `sdk.ts` 约 5 处分支；新增一套 Windows 校验值 | 一个 ~30 行工具 + 调用点替换 |

### 2.5 结论与实施建议

- 结论：**采用现成方案**（官方各平台产物 + Node 官方 .bat 执行口径），工程上体现为**手写平台分支**。
- 落地路径：① `sdk.ts` 常量区改双源结构体；② `sdkPaths` 加后缀平台分支；③ JRE 归位平台分支；④ 新增 `platformExec` 工具（含 windowsHide），替换 `sdk.ts`/`avd.ts`/`cameras.ts`/`adb.ts` 的裸 spawn；⑤ Windows 校验值以真机下载实测填入（sha1/sha256 不能抄网页猜）。

## 3. 调研单元 G：解压方案选型

### 3.1 该部分要做什么

镜像下载（2GB+ zip，含 ≥2GB 的 system.img 条目）与 bootstrap 解压在 Windows 的实现选型，替代 mac 上的系统 `unzip`（`downloader.ts:99`）与「mac 自带 tar 即 bsdtar」假设（`sdk.ts:194-222`）。

### 3.2 项目现状

- `downloader.ts:92-104`：`execFile('unzip', ['-q', zip, '-d', dir])`——注释记录 adm-zip 撞 2^31 上限（真机实测 android-21 的 system.img 即 2147483648 字节）才改系统命令。
- `sdk.ts:194-222`：bootstrap 解压用 `spawn('tar', …)`（macOS 自带 tar 即 bsdtar，zip/tar.gz 通吃）。
- 皮肤导入用 AdmZip（`skins.ts:292`，小文件场景，无问题，不在本单元）。

### 3.3 候选方案

**方案 G1：Windows 复用 `tar.exe`（采用系统自带，与 mac 同命令）**

- 原理：微软官方文档明确 Windows 内置 tar「create and extract .tar, .tar.gz, **and .zip** archives」；该 tar.exe 即 bsdtar（libarchive），自 Windows 10 1803（build 17063）起内置 `System32\tar.exe`——与 macOS 自带 tar 同源同语义，zip64 与大条目原生支持。本报告基线 Win10 1809+ 满足。实现上 `downloader.ts`/`sdk.ts` 的解压命令做平台分支：win32 用 `tar.exe -xf`（同一命令，只是 Windows 上必须写 `tar.exe` 明确后缀），mac 维持 `unzip`/`tar` 现状不动。
- 来源：微软官方 tar 文档 <https://learn.microsoft.com/en-us/windows/tar/>；bsdtar 自 1803 内置 <https://ss64.com/nt/tar.html>；libarchive 同源佐证 <https://libarchive.org/>
- 局限（如实记录）：`tar -xf` 无逐条目进度回调（与 mac 现状同病），Defender 扫描期间进度条假死问题仍靠前报告 C2 的排除引导缓解。

**方案 G2：PowerShell Expand-Archive——排除**

- 原理与否决理由：**官方文档明确底层 System.IO.Compression「limits the maximum file size to 2GB」**——恰好撞死 system.img 的 2GB+ 条目；且社区实测性能差（比 7zip 慢约 6 倍）。不候选。
- 来源：官方文档 <https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.archive/expand-archive>；性能 issue <https://github.com/PowerShell/PowerShell/issues/3355>

**方案 G3：纯 JS 流式解压（yauzl / zip.js）——备选，不首选**

- 原理：yauzl 支持 ZIP64（<8PiB）；zip.js（gildas-lormeau）支持 zip64/多核/流式。优点：跨平台统一实现、逐条目进度回调（可解「解压假死」感知问题）；缺点：新依赖 + 主进程流式解 2GB 的 CPU 占用需要挪 worker/线程，且 yauzl 2026-03 有 DoS CVE 报道（选型要锁新版本）、流式解压库的取舍有已知争议（yauzl README 自述两类妥协）。
- 来源：yauzl <https://github.com/thejoshwolfe/yauzl>；zip.js <https://gildas-lormeau.github.io/zip.js/>；yauzl CVE 报道 <https://codeant.ai/security-research/yauzl-denial-of-service-zip-file-crash>
- 看过不选原因：G1 零依赖即可达成正确性；逐条目进度属于体验增强，等真机验证确有痛点再引入。

### 3.4 可行性分析

| 维度 | G1 tar.exe | G3 纯 JS 流式 |
| --- | --- | --- |
| 技术匹配 | 官方确认支持 zip；zip64 原生；与 mac 分支同命令 | zip64 支持但要防 CVE 版本；2GB 解压需挪线程 |
| 规则冲突 | 无 | 引新依赖，与「不引入新抽象」的家规相悖，需 plan 显式批准 |
| 成本 | 平台分支 ~5 行 | 新依赖 + worker 化 + 版本跟踪 |

### 3.5 结论与实施建议

- 结论：**采用现成方案**（G1 系统 tar.exe）；G3 记为后备，触发条件是「真机验证解压感知慢成为主要投诉」。
- 落地路径：`downloader.ts` 的 `extractZip` 默认实现与 `sdk.ts` 的 `defaultUnpacker` 各加 win32 分支（命令 `tar`→`tar.exe`、`unzip`→`tar.exe -xf`），取消逻辑（AbortSignal kill）复用现有结构。

## 4. 调研单元 H：Windows Studio / SDK 检测链

### 4.1 该部分要做什么

`detectStudioAndSdk`（`studioDetect.ts:140`）的候选链在 Windows 全部失效或部分失效的问题：默认路径、Studio 本体扫描、`mdfind`、PATH 反推四条分支的 Windows 等价实现。

### 4.2 项目现状（四条分支逐一对位）

- 分支 1（Studio 配置文件）：`configRoot = ~/Library/Application Support/Google`（`studioDetect.ts:174`）；提取候选后 `value.startsWith('/')` 过滤（`:136`）——Windows 路径是盘符开头且大小写不定，两处都要改。
- 分支 2（环境变量）：`ANDROID_SDK_ROOT`/`ANDROID_HOME`——平台无关，Windows 通用，无需改。
- 分支 3（平台默认目录）：`~/Library/Android/sdk`（`:146`）——Windows 默认是 `%LOCALAPPDATA%\Android\Sdk`。
- 分支 4（PATH 反推）：PATH 按 `:` 分隔（`:79`）、找 `adb` 无后缀（`:81`）——Windows 按 `;` 分隔、找 `adb.exe`。
- Studio 本体：`/Applications` 扫 `Android Studio*.app`（`:95-112`）+ `mdfind` 兜底（`:57`）——Windows 均不适用；jbr 按 `Contents/jbr/Contents/Home`（`:162`）——Windows 布局不同。
- SDK 根核验 `looksLikeSdkRoot` 找 `platform-tools/adb`（`:92`）——Windows 需 `adb.exe`。

### 4.3 候选方案

**方案 H1：配置文件分支平移 + 布局常量平台化（采用官方事实，手写分支）**

- 原理：Android Studio 的配置目录在各平台**同构**，官方 troubleshooting 页明确：Windows 是 `%APPDATA%\Google\AndroidStudio<VERSION>`（`%APPDATA%` 即 `AppData\Roaming`），macOS 是 `~/Library/Application Support/Google/AndroidStudio<VERSION>`——即分支 1 的「读 options/*.xml 提取 SDK 路径」逻辑**主体可复用**，只需换 configRoot、放宽路径形状过滤（盘符开头 + 反斜杠）、比较大小的规范化（前报告 B2）。默认 SDK 目录与 jbr 布局同理平台化。
- 来源：官方目录表 <https://developer.android.com/studio/troubleshoot>（Directories 节，idea.config.path 逐平台路径）；默认 SDK 路径 <https://developer.android.com/tools/variables> 与社区多源一致的 `%LOCALAPPDATA%\Android\Sdk`；Windows jbr 布局（`C:\Program Files\Android\Android Studio\jbr`，直接 bin/java.exe）<https://developer.android.com/build/jdks> 与实践文 <https://medium.com/@rahulchaurasia3592/understanding-multiple-jdk-installations-a-practical-guide-for-android-java-developers-d60c18b30516>

**方案 H2：Studio 本体检测——固定目录扫描为主，注册表卸载键降级为可选增强（手写，替代 mdfind）**

- 原理：Windows 无 Spotlight 等价命令；第一步只用零注册表的两条路径：① 扫安装器默认目录 `C:\Program Files\Android\Android Studio`（覆盖大多数用户）；② 配置目录 `%APPDATA%\Google\AndroidStudio*` 的存在性（证明装过并跑过 Studio，支撑 studioFound 信号）。jbr 就在 `<studio>/jbr`，`bin/java.exe` 在场即 jbrReady；找不到 jbr 时共享模式的 Java 走应用自管 JRE 兜底，功能不缺失。注册表查询（`HKLM\...\Uninstall\Android Studio` 的 InstallLocation，`reg.exe` 只读查询）作为将来的可选增强，覆盖「用户自选目录安装」的场景——**有真机后实测再决定是否值得做**（zip 解压安装的用户不会登记卸载键，注册表本就不是完备路径）。
- 来源：安装目录默认值 <https://developer.android.com/build/jdks> 与实践文 <https://medium.com/@rahulchaurasia3592/understanding-multiple-jdk-installations-a-practical-guide-for-android-java-developers-d60c18b30516>；Windows Installer 卸载键机制（官方） <https://learn.microsoft.com/en-us/windows/win32/msi/uninstall-registry-key>；「Studio 不在控制面板」的 zip 安装反例 <https://stackoverflow.com/questions/65105036/how-to-uninstall-android-studio-if-it-is-not-visible-in-control-panel-and-also-u>

**方案 H3：PATH 反推修正（手写，几行）**

- 原理：分隔符 `;`、找 `adb.exe`、`looksLikeSdkRoot` 核验 `platform-tools/adb.exe`。env 分支（分支 2）天然跨平台不动。
- 来源：Windows PATH 语义为平台事实；与 Node `path.delimiter` 提供的平台常量对应 <https://nodejs.org/api/path.html>

### 4.4 可行性分析

| 维度 | H1 配置平移 | H2 注册表+目录扫描 | H3 PATH 修正 |
| --- | --- | --- | --- |
| 技术匹配 | 官方目录表逐平台确认；解析逻辑复用率高 | 注册表卸载键标准行为；具体键值需真机实测 | 平台事实，`path.delimiter` 官方常量 |
| 规则冲突 | 无 | 无（只读查询） | 无 |
| 成本 | configRoot/过滤/比较三处分支 | reg 查询小模块 + 测试桩 | 几行 |

### 4.5 结论与实施建议

- 结论：三个子项均**手写平台分支**（依据官方目录事实）；H2 的注册表细节留待真机验证后固化。
- 落地路径：`studioDetect.ts` 的 `Deps` 接缝已支持注入（listDir/readFile/env…），新增 `regQuery` 接缝供单测；检测顺序维持「配置文件 → 环境变量 → 默认目录 → PATH 反推」不变（与 mac 同构，行为可对照回归）。`i18n` 的 `defaultSdkPath` 展示与设置页「共享 Studio SDK」禁用态逻辑（studioFound 驱动）自动受益，无需单独动。

## 5. 风险与开放问题

- **Windows 版钉版校验值必须真机取**：cmdline-tools win zip 的 sha1、Temurin win JRE zip 的 sha256，报告只确认了产物存在与 URL 形态，哈希值以真机下载实测为准，不可抄录。
- **注册表卸载键细节未实测**（H2）：InstallLocation 是否稳定存在、HKLM/HKCU 双视图（32/64 位重定向）行为，实现时先写探针脚本在真机跑一遍再固化。
- **`cmd.exe /c` 包装对进程管道的影响**：进度行解析、stdout 缓冲行为理论不变，但需集成测试覆盖（sdkmanager 输出经 cmd 转发后的行分隔符一致性）。
- **Temurin win JRE zip 的版本对齐**：与 mac 侧钉的 21.0.12 同大版本，避免两个平台的 Java 行为差异（avdmanager 对 Java 版本敏感）。

## 6. 待确认假设（2026-10-22 依用户追问修订）

- [x] 假设 1：Windows 引导只支持 x64，**Windows on ARM（WoA）不一起做**——**已批复（2026-10-22）**。成本评估（2026-10-22 补）：核心障碍是模拟器本体——官方 release notes 的 ARM64 host 支持目前只有 Linux 方向，WoA 上跑 Android 模拟器依赖 x64 转译、不是受支持场景（社区实证 <https://montemagno.com/developing-android-apps-on-windows-arm/>），意味着 WoA 上本工具的核心功能（多开模拟器）本身就不可靠，适配无意义；而 JRE 层无障碍（Temurin 官方支持 Windows aarch64，<https://adoptium.net/supported-platforms>）。**缓解**：实现时把钉版源做成按平台查表的常量结构（本报告 F1 已如此设计），将来 WoA 成熟后加支持＝加一套常量＋真机验证，不需重构。
