## 1. 需求理解

### 1.1 功能目标

用户转无线或手动连接失败后，应用提供有依据的诊断和可执行的恢复入口，减少终端排障。成功以无线 transport 为 `device` 且命令可执行为准，不能只看 connect 文案。

Step 0 范围：覆盖无线连接失败分类、诊断信息、用户主动修复；不更换共享 5037 架构、不持久化无线设备、不增加断线后台找回、不调整手机网络或系统权限。全局重启的授权方式由用户本次裁决。

本次实测：USB 在线；手机 TCP 5555 监听；Mac 普通 TCP 探测成功，但共享 ADB 的 connect 返回 `No route to host`；共享服务 PID 85663 自 11 月 3 日运行，未随应用重启；重启共享服务后连接成功，无线 shell 返回 SM-A155F。

这证明重启服务是本次有效的恢复措施，尚未证明旧进程失效的底层原因，也没有统计证据判断发生频率。权限、网络过滤或进程状态仍是候选原因，不能将“服务运行较久”作为故障判据。

### 1.2 未知点清单

- [x] 为什么应用重启无效？共享服务独立存续，启动时仅核对服务协议并复用，见 2.2。
- [x] 能否识别手机可达但 ADB 连接异常？可组合独立探测与 ADB 结果，提供疑似分类；无法仅凭一个错误码确诊权限，见 2.5。
- [x] 能否只修复目标设备？定向重连可覆盖部分 transport 故障，无法保证解决服务进程异常；全局重启影响所有客户端，见 2.3。
- [x] 是否需要新依赖？不需要，复用 Node 网络 API 与 ADB CLI，见 2.5。

### 1.3 拆分判断

作为一个调研单元：诊断结果决定恢复入口，二者属于同一故障处理流程。

## 2. 调研单元：无线连接失败后的诊断与恢复

### 2.1 该部分要做什么

连接失败后自动收集有限诊断，区分网络不通、未授权、切换尚未完成与疑似共享服务异常；允许用户执行一次恢复并查看实际结果。

### 2.2 项目现状

- `src/main/devices/external.ts`：promote 先读 wlan0 IP，再执行 tcpip 5555，再 connect；TCP 失败已有 500ms/1s/2s 退避，不能用“增加重试”单独解决本次问题。tcpip 的返回状态尚未单独分类，实施时需校验 code/stdout/stderr。
- 同文件 connect 将 TCP 失败按本机 /24 前缀归成 unreachable 或 cross-subnet，没有保留原始错误类别给界面；网段前缀只能作提示，不能证明实际路由不可达。
- 同文件 probeAdb 是扫描用 CNXN 探测，仅接受 CNXN；诊断场景需区分 TCP 可达、ADB 应答和授权挑战，不能把现有 false 直接解释成手机不可达。官方 TLS 配对端口也不能套用经典明文探测。
- `src/main/emulator/adb.ts`：ensureSharedServer 仅探测 5037 与协议，不检测远端连接健康；明确禁止为换成自己的服务而 kill-server。
- `src/main/devices/external.ts` 的 track 客户端已有退避重连和会话代次递增，可复用，但需验证全局重启时 USB、无线、模拟器及录屏如何结算。
- `src/shared/types.ts` 的 WirelessConnectOutcome 与 `src/renderer/src/components/wirelessOutcome.ts` 目前只支持通用失败原因；DeviceListPane.tsx 和 WirelessConnector.tsx 共用文案映射。
- `book/docs/PRD.md` F 节与运行环境表要求共享 5037，防止影响 IDE；`book/plans/2026-10-15-real-device-wireless.md` 明确“只 start 不 kill”和不持久化、不自动找回。
- `electron-builder.yml` 尚无 NSLocalNetworkUsageDescription；`scripts/adhoc-sign-mac.cjs` 已有稳定签名优先、失败退回 ad-hoc 的策略，不能宣称补一条权限文案就解决旧服务异常。
- `package.json` 使用 Electron ^39.2.6、React ^19.2.1；诊断在 main，renderer 通过 preload 获取结果。

### 2.3 候选方案

| 方案 | 原理与适配 | 收益与代价 |
| --- | --- | --- |
| A：诊断与指引 | 自动分类失败，显示证据、权限指引及复制诊断；保持现有服务生命周期 | 改动小，不影响其他客户端；恢复仍需用户自行处理 |
| B：自动诊断 + 用户触发修复（推荐） | A 基础上提供“重启 ADB 并重试”；执行前说明全局影响，单次重启并重试本次目标 | 覆盖本次实际故障；需处理任务互斥、连接恢复和全局中断 |
| C：自动诊断 + 自动重启 | 检测到疑似服务异常后自动执行 B 的重启 | 操作最少，但判断可能误报，无法可靠知道 IDE、脚本是否正在使用共享服务 |

官方依据：

- [ADB 命令手册](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md)：connect/disconnect 可针对地址；reconnect 操作现有连接；kill-server 停止共享服务；server-status 可提供二进制路径、后端、日志位置。按本机支持情况使用 server-status，不支持时降级，不阻断诊断。
- [Android ADB 文档](https://developer.android.com/tools/adb)：客户端通过 5037 使用后台 server，由 server 管理设备通信。这支持将连接诊断与服务健康分开。
- [Apple TN3179](https://developer.apple.com/documentation/Technotes/tn3179-understanding-local-network-privacy?changes=_2_6_8)：macOS 15 起存在局域网隐私控制；子工具的网络行为可能归属启动它的应用。因此终端探测成功不能证明应用启动的 ADB 一定拥有相同访问条件；权限文案与打包身份应核验。

独立 ADB 端口方案看过但不选：违背共享 5037 的产品约定，也增加 IDE 发现设备与 USB 占用的复杂度。

### 2.4 可行性分析

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 技术匹配 | Node + 现有 CLI | 同 A，加协调服务重启 | 同 B，但误判无法消除 |
| 规则冲突 | 无 | 需用户批准“显式修复可重启共享服务”的例外 | 需放宽默认不 kill 的边界，外部使用情况不可可靠判断 |
| 成本 | 低，无新增依赖 | 中，涉及录屏/安装/迁移门与会话恢复 | 高，需额外自动化策略，仍无法保证不影响外部客户端 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**，推荐 B。复用官方 CLI 与项目网络能力，按现有共享服务约束组织诊断和显式恢复。

建议行为：

1. 保留现有有限重试；失败后自动诊断一次，每次有超时与取消边界，不做常驻扫描。
2. 记录失败阶段、退出码、stdout/stderr、目标地址、transport 状态、ADB 路径/版本及可得的 server-status；复制前剔除配对码、密钥和无关日志。
3. 分类：手机无 Wi-Fi → 手机联网指引；unauthorized → 手机授权；refused → 无线端口尚未就绪或未监听；timeout/no-route → 网络或访问受阻。独立探测可达而共享 ADB 持续失败时，提示“手机端口可达，疑似 ADB 服务异常”。其他情况保留“原因未确定”，不能仅凭 /24、TCP 成功或进程年龄判定根因。
4. 失败反馈提供“重试”“修复连接”“复制诊断”。“修复连接”的确认文案明确：“将重启共享 ADB，所有设备连接和 Android Studio 调试会短暂中断。”需保留取消入口；已知录屏/安装/迁移等任务进行中时禁用修复并指出任务，不自动终止任务。
5. 修复采用主进程全局互斥与临时门：重新核对迁移/任务状态 → 暂停本应用会自行拉起服务的入口与后台重连 → kill/start → 协议与服务复验 → 恢复跟踪 → 仅重试本次用户目标 → 用 transport 与轻量 shell 验证；失败也必须释放门并给出结果。单次操作最多重启一次，无循环重启。
6. 不持久化地址、不恢复全部历史无线设备。本次操作上下文可暂存目标，结束即释放。其他无线连接可能需要用户重新连接；不承诺外部 IDE 调试和端口转发自动恢复。
7. macOS 补局域网使用说明，核验正式包权限归属与签名升级行为；权限明确拒绝时指向系统设置。权限问题与共享服务异常分别提示，重启不能替代用户授权。

落点：external.ts 与 emulator/adb.ts 承担诊断及受控服务操作；shared/types.ts 扩结果/诊断契约，ipc-channels 与 preload 加修复入口；DeviceListPane、WirelessConnector、wirelessOutcome 和三语文案承接反馈。任务状态从 recording/安装/迁移的事实源读取，必要时在装配层注入，不由界面猜测。更新 PRD 与无线 plan 中的生命周期例外；实施界面时使用 impeccable 技能。

验收应覆盖：本次“独立端口可达而 ADB connect 失败”的替身与真机复验；真实网络不通不误判；未授权不重启；取消无副作用；任务中禁止修复；并发请求仅一次重启；恢复失败仍释放门；USB/无线/模拟器会话重建；权限拒绝与 server-status 不支持时正确降级。

## 3. 风险与开放问题

- 外部 IDE/脚本是否有在途任务无法完整获知，不能将“应用内无任务”等同于全局空闲。
- 从应用启动的新 ADB 可能触发或受制于 macOS 权限，终端重启成功不保证应用内一定成功；正式包真机验收必须覆盖这一点。
- 旧服务的故障原因未定；下次发生时应先保留诊断再修复，不以“进程太旧”掩盖底层问题。
- 全局重启对端口转发、外部调试与无线连接的影响需要明示。恢复能力以实测为准，不承诺无感。
