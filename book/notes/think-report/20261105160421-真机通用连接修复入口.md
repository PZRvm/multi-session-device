# 真机通用连接修复入口功能调研报告

> 创建时间：2026-11-05 16:04:21（Asia/Shanghai）
> 需求来源：用户确认基础验收完成，并澄清需要处理 USB 有线连接偶发断开，询问能否从其他地方重启 ADB。
> 调研单元：1 个
> 状态：用户决定暂缓（2026-11-05），未改实现

## 1. 需求理解

### 1.1 功能目标

用户在 USB 设备异常或从列表消失时，仍能主动检查连接并尝试修复。修复不要求先失败一次无线连接，也不要求知道手机 IP。

本轮是对既有 B 方案的范围补充：原计划覆盖转无线/手动无线连接，当前新增 USB 和设备列表空态。USB 断开的底层原因未确认，不能预设重启 ADB 可以解决每次断开。

### 1.2 未知点清单

- [x] 重启是否仅影响无线？不是，共享 5037 server 管理所有 ADB 客户端与设备；现有入口/验证才是无线专用，见 2.2。
- [x] USB 设备消失时能否使用现有按钮？不能，现有修复必须持有窗口绑定的无线失败 attempt 和 host:port，见 2.2。
- [x] 是否需要新依赖？不需要，保留现有恢复门、原生确认及任务保护，调整入口和恢复后的验证方式，见 2.5。

### 1.3 拆分判断

作为一个调研单元：入口、诊断和恢复后判据共同服务同一连接修复流程。

## 2. 调研单元：真机区通用诊断与显式修复

### 2.1 该部分要做什么

真机区常驻“连接诊断”入口，无 USB 设备或列表为空时仍可进入；提供低影响的检查与用户确认后的全局重启。保留无线失败位置的快捷入口；不自动对每次 USB 拔插重启服务。

### 2.2 项目现状

- `src/main/devices/external.ts`：track 监听共享 server 的设备列表；设备移出或非 device 时销毁会话，恢复 device 后新代次重建。该能力覆盖热插拔，但没有围绕 USB 异常的主动诊断入口。
- `src/renderer/src/components/DeviceListPane.tsx`：真机组头常驻无线入口；修复组件只在 promote 失败且存在 attemptId 时出现。设备完全消失时不能从它发起首次修复。
- `src/main/devices/wirelessRecovery.ts`：repair 必须取得有 target 的失败 Entry；重启后执行 connect(host:port) 与 shell。将按钮搬到组头并不能直接支持 USB。
- `src/main/emulator/adbRecovery.ts`、`src/main/ipc/index.ts`：已有全局互斥、任务二检、CLI 门、暂停/恢复会话，可复用。不得用通用入口绕过原生确认或任务保护。
- 用户完成上一轮六项交互验收；这些结果不证明 USB 偶发断开的原因已经定位。

### 2.3 候选方案

| 方案 | 原理与适配 | 局限 |
| --- | --- | --- |
| A：设置中提供重启 ADB | 用户在设置触发全局确认和现有恢复流程，重启后重新枚举 | 操作入口远，缺少 USB/投屏故障区分，仍容易把所有掉线归为 ADB |
| B：真机区常驻连接诊断（推荐） | 设备有无均可检查；区分 ADB 可见性、授权和投屏状态；用户可确认重启，再按 USB/无线各自验证 | 需解除执行恢复与无线 target 的绑定，增加通用服务结果和 USB 判据 |
| C：每次 USB 消失后自动重启 | track 发现 USB 消失即重启服务 | 正常拔线也会触发，反复中断其他设备，且无法证明是服务异常；不采用 |

来源：[ADB 官方文档](https://developer.android.com/tools/adb)说明 client/server/设备 daemon 与共享 5037；[ADB 命令手册](https://android.googlesource.com/platform/packages/modules/adb/+/refs/heads/main/docs/user/adb.1.md)区分 devices、connect、reconnect 与 kill/start-server。USB 枚举与 TCP connect 的恢复判据须分别设计，不能将无线 connect 成功套给 USB。

### 2.4 可行性分析

| 维度 | A | B | C |
| --- | --- | --- | --- |
| 技术匹配 | 可复用重启门 | 可复用门、任务查询、track 与会话桥 | 可触发，但故障判断不足 |
| 规则冲突 | 显式确认符合 B 裁决 | 显式确认符合 B 裁决；新增 USB 范围需确认 | 违反显式修复边界，且正常拔线也有副作用 |
| 成本 | 低，无新增依赖 | 中，无新增依赖，主要是流程分离和测试 | 自动化误判代价高 |

### 2.5 结论与实施建议

结论：**借鉴思路手写**，推荐 B。

1. 真机组头增加“连接诊断”，无设备时仍常驻；USB 行可有同一入口的快捷动作。实现时使用 impeccable，沿用现有 UI。
2. 诊断分别报告：设备是否在 ADB 列表、device/offline/unauthorized、可否执行轻量 shell、应用投屏会话是否正常。ADB 正常而只有投屏失效时，优先重建该投屏会话，不重启全部 ADB。
3. 设备未在 ADB 列表时显示“未检测到 USB 设备，原因未确定”；提示检查线材、接口和手机授权，同时保留主动重启服务的入口。单凭消失事件不能区分拔线、线材、主机枚举或手机侧原因。
4. 用户可选择“重启 ADB 服务”，原生确认说明全局影响；沿用录屏/安装/SDK/启停保护与单次执行门。此操作不再要求先生成无线失败 attempt，也不接受任意命令。
5. 解开无线专用编排：保留一套共享服务重启/会话恢复执行路径；无线按本次 host:port 重连验证；USB 等待有界枚举，按已知 serial 验证 device + shell。无目标时只报告服务重启和枚举结果，不将“服务启动成功”显示为“USB 已恢复”。
6. 重启后 USB 仍消失或未授权，要保留原因未确定/手机授权引导；不循环重启，不自动切无线，不自动停止录屏。
7. 在当前 worktree 继续实现。修改 shared 契约、preload 白名单、恢复编排与 DeviceListPane；补测试：列表为空仍可进入、USB offline/unauthorized/消失、投屏单独失效、服务重启成功但 USB 未恢复、任务保护和无线既有行为。

## 3. 风险与开放问题

USB 偶发断开尚无当时证据。下次发生先比较系统 USB 枚举、adb devices 和应用列表/画面，才能区分实体连接、ADB transport、track 缓存或投屏会话。重启只是恢复手段，不能作为根因已修复的证明。
