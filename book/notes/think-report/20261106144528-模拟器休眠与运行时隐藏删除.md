# 模拟器休眠与运行时隐藏删除调研报告

> 创建时间：2026-11-06 14:45:28（Asia/Shanghai）
> 需求来源：闲置模拟器希望保留桌面与应用、释放资源，避免每次冷启动；运行时隐藏删除按钮。
> 调研单元：2 个
> 状态：用户已确认全部边界；当前只编写开发计划，尚未实施

## 1. 需求理解

### 1.1 功能目标

用户已明确选择“休眠后释放内存，恢复可以稍慢，但希望回到原来的桌面和应用”。因此目标是保存虚拟机状态后释放模拟器进程，再从该状态恢复；仅冻结 CPU 或暂停投屏不满足需求。

第二项原话“模拟器允许的时候”暂按“模拟器运行的时候”理解：运行时不显示删除按钮，减少误操作。以下研究只针对本工具管理的 Android 模拟器，USB/Wi-Fi 手机不提供休眠或删除设备数据的能力。

### 1.2 未知点清单

- [x] 模拟器是否支持暂停？支持，本机命令帮助确认 pause/resume，见 2.3；但不能据此承诺释放内存。
- [x] 如何保留状态并释放内存？官方快照保存后退出进程，见 2.3—2.5。
- [x] 能否直接复用现有启动/停止？有可复用部分，但冷启动参数、强制终止、状态持久化和会话恢复均需调整，见 2.2。
- [x] 哪些内容可能恢复不了？外部网络连接、调试器和摄像头等外部资源不由 VM 快照保证；版本/配置变更会使快照失效，见第 4 节。
- [x] 删除按钮目前为何能在运行中显示？行组件允许 running 删除，后端会先停止再删除，见 3.2。

### 1.3 拆分判断

两个单元：①休眠/恢复及资源释放；②删除入口与操作约束。第二项可以单独落地，不必等待休眠完成，但新增休眠状态时需统一动作矩阵。后续实现预计属于 L：跨设备生命周期、共享 IPC 契约及持久状态。

## 2. 调研单元：释放内存的休眠与恢复

### 2.1 该部分要做什么

运行设备可以显式休眠，之后显示为“已休眠”；恢复时回到保存的桌面和应用状态。休眠期间该实例不再保有 QEMU 进程、投屏与日志连接。记录必须跨应用重启保留。第一版不做闲置计时、自动休眠、批量休眠、真机休眠或快照版本管理界面。

### 2.2 项目现状

| 事实源 | 已核实的现状与影响 |
| --- | --- |
| `src/shared/types.ts` 的 DeviceStatus | 只有 creating/stopped/starting/running/stopping/deleting，没有暂停或休眠；运行态重启不入盘 |
| `src/main/devices/state.ts` | 主进程是状态唯一事实源；投屏桥按 running 建流、stopped/beforeKill 释放，不能只在 renderer 加一个暂停图标 |
| `src/main/emulator/runner.ts` | 持有子进程、runId、端口和清理 Promise；POSIX 走 SIGTERM→超时 SIGKILL，Windows 走 taskkill /T /F，不能把当前 stop 当成可靠的快照保存事务 |
| `src/shared/settings-contract.ts` | Cold 模式传 `-no-snapshot`，会覆盖启动时指定的 `-snapshot`；恢复必须走专用参数路径 |
| `src/main/emulator/settings.ts` | `quickBootAvailable: false`，启动模式选择禁用；不能把已有代码等同于可交付能力 |
| `src/main/devices/lifecycle.ts` | Quick 停止后以 default_boot 目录内容及 mtime 核验保存；这是旧 Quick 路径，缺少休眠提交标记和恢复兼容性清单 |
| `book/plans/2026-10-05-emulator-wizard.md` | Quick 连续十次、双机各五次及异常场景稳定性门槛尚未完成；历史快照原生崩溃尚需用当前环境复验 |
| `src/main/devices/queries.ts`、`src/main/ipc/index.ts` | 截图、投屏、日志及恢复编排依赖 running/serial/runId；恢复应创建新 runId，不复活旧 sender/图片会话 |
| `src/main/apkInstall/index.ts`、录屏域 | 已有任务忙态；休眠需互斥并等待/拒绝在途任务，不能突然中断安装或仍处暂停态的录屏任务 |
| `src/main/devices/startup.ts`、`src/main/emulator/sdkSourceSwitch.ts` | SDK 迁移检查 runner 活动实例数；休眠中实例仍占资源，已休眠实例则另需检查快照兼容性 |
| `src/preload/api/devices.ts`、`src/shared/ipc-channels.ts` | 只有 start/stop/cancel 等接口，没有 hibernate/resume |

产品现行状态机和删除确认语义在 `book/docs/PRD.md`；新状态需要明确扩展。技术栈为 Electron 39、React 19、styled-components、zustand，本地三进程编排，无须新增服务或虚拟机库。research-feature 中残留的浏览器 partition/antd 假设与本仓库无关，不作为本需求约束。

本机只读核查：Android Emulator 36.1.9 的 `adb -s emulator-5554 emu help avd` 列出 pause/resume 和 snapshot；单项帮助确认 pause 用于暂时不用时节省资源，snapshot save 保存运行时状态。未发送 pause/resume/save/load/kill，未中断用户实例，也未测量实际保存或恢复耗时。

### 2.3 候选方案

**方案 A：虚拟机原地暂停/继续**

- 原理：调用模拟器现有 pause/resume（或 stop/start 执行控制）；虚拟机不继续执行，进程仍在。
- 来源：[官方发布说明](https://developer.android.com/studio/releases/emulator)将 pause/resume 描述为暂停 vCPU；[官方控制台](https://developer.android.com/studio/run/emulator-console)列出虚拟设备执行控制。本机帮助也确认命令存在。
- 适配：控制台命令可以复用现有 ADB 执行器。但没有本机内存回收实测，也没有依据将其承诺为卸载 guest RAM；本方案不满足用户“释放内存”的明确目标。

**方案 B：状态快照 + 退出模拟器进程（推荐）**

- 原理：保存官方 VM 快照，确认成功后退出 QEMU；恢复时启动同一 AVD 并加载指定快照。官方快照保存 OS、应用和用户数据状态，适合继续此前测试场景。
- 来源：[官方快照说明](https://developer.android.com/studio/run/emulator-snapshots)、[控制台 snapshot 命令](https://developer.android.com/studio/run/emulator-console)、[命令行快照参数](https://developer.android.com/studio/run/emulator-commandline)。
- 两种接法：Quick Boot 的退出自动保存可复用已有结构，但受正常退出与当前禁用门槛影响；专用命名快照能明确区分“休眠”和“普通停止”，便于独立核验及避免误加载旧状态。建议先验证专用命名快照保存→退出→启动加载，再复用已有启动准备、端口、流桥和错误处理。
- 限制：进程退出后，实例的进程内存及 GPU/连接资源可释放；系统文件缓存不保证立即消失，不能宣传宿主总内存必定下降固定数值。快照占磁盘、保存/加载需要内存与 IO，未实测前不承诺几秒恢复。

**方案 C：操作系统冻结进程，或关闭投屏**

- SIGSTOP/SIGCONT 是 POSIX 进程执行控制，Windows 需要另一套机制；来源：[Apple kill 手册](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/kill.2.html)。关闭投屏则只影响媒体链路，项目现有活动视图切换已有类似职责。
- 不采用：两者都不等于把运行状态保存后退出 QEMU；内存、锁、端口和退出回收仍需处理。OS 冻结还会阻塞正常停止，不能代替可恢复的休眠事务。

### 2.4 可行性分析

| 维度 | A：原地暂停 | B：快照后退出 | C：OS 冻结/关投屏 |
| --- | --- | --- | --- |
| 目标匹配 | 快速继续，不能保证释放内存 | 满足释放进程内存并恢复场景的目标 | 不满足释放内存目标 |
| 规则与兼容 | 新增状态、维护存活进程 | 需补持久清单、兼容验证、异常恢复和会话重建 | 平台分叉且退出更复杂 |
| 成本 | 较低，但不符合用户选择 | 较高，沿用官方能力，无新增库 | 收益不足，不做 |
| 当前可信度 | 命令存在；未测资源变化 | 官方能力存在；项目稳定性未验证 | 未在用户实例上执行 |

### 2.5 结论与实施建议

结论：**采用现成方案**——使用官方快照实现“休眠”，由现有主进程生命周期编排；不自己序列化虚拟机内存。

先做隔离 PoC：新建可丢弃的测试 AVD，不动用户实例；在 hardware host 后端验证单机十轮、双机各五轮的保存、退出、恢复，记录 CPU/RSS、宿主可用内存、磁盘增量及恢复到可操控画面的耗时。检查应用停留页、Android 状态、投屏/输入和独立设备归属。覆盖当前 Mac；Windows 发布前必须独立测，不能从 Mac 推断。软件渲染配置不通过验证时，应明确禁用或说明原因，不能自动更改用户 GPU 设置。

PoC 特别核实：当前 `-no-snapshot` 禁的是自动保存/加载，并不等于控制台完全不能手动保存；官方源文件 [main-common.c](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/android-emu/android/main-common.c)明确区分。启动恢复时则必须去掉覆盖 `-snapshot` 的参数。以本机版本实测决定最终调用顺序，不凭历史实现开放开关。

建议事务：

1. 主进程验证设备、当前代次和任务忙态，进入“正在休眠”，拒绝新输入/安装/截图。已有输入先释放；在途副作用有界排空。录屏（包括暂停录制）存在时提示用户先结束；媒体生成任务是否占用该实例需区分。
2. 停止并排空该设备投屏/日志/剪贴板会话，避免快照带回旧 scrcpy 连接。保存应用专用命名快照，核实保存完成与清单一致。不能只凭目录 mtime 宣称可恢复。
3. 原子记录快照清单和退出待完成标记，再退出对应进程树；确认没有残留后释放端口并提交“已休眠”。保存失败保留运行实例并尝试恢复媒体连接；进程退出失败保持真实资源占用状态，不能显示已释放内存。
4. 恢复时验证 SDK/emulator、镜像、GPU、AVD 配置指纹及快照有效性，创建新运行代次，分配可用端口、加载快照。ADB/boot 就绪后重新建立投屏/输入/日志。确认成功才消费旧休眠标记，避免下次启动回滚到同一旧快照。
5. 恢复失败保留快照和解释；提供重试或用户明确选择“放弃休眠状态并冷启动”。不要静默冷启动并宣称恢复成功；加载旧快照具有回滚语义，普通启动也不能误用它。

状态建议：`running → hibernating → hibernated → resuming → running`；失败按实际进程及保存结果留在可恢复状态。休眠清单需持久化，内存状态与恢复阶段要在应用重启后重建；现有“重启全部 stopped”的逻辑不能直接沿用。

落地涉及：`shared/types.ts` 与通道/文案契约、`preload/api/devices.ts`、devices 生命周期/状态/启动/IPC/存储、emulator runner 与新增快照适配模块、IPC 装配及媒体任务守卫、deviceStore、DeviceRow 和主画面占位。SDK 切换、编辑配置、退出和恢复对账需接入快照失效策略；不改变普通停止的产品语义。实现界面时使用 impeccable 技能。

## 3. 调研单元：运行时隐藏删除入口

### 3.1 该部分要做什么

模拟器运行时不显示垃圾桶。研究同时区分“入口隐藏”与“禁止运行中删除”：后者需要主进程守卫，不能仅靠按钮实现。第一版不改真机的断开按钮。

### 3.2 项目现状

- `src/renderer/src/components/DeviceRow.tsx` 无条件渲染 Trash2；deleteDisabled 明确允许 stopped 和 running，其余状态只禁用而不隐藏。
- `src/renderer/src/App.tsx` 的 handleDelete 根据 running 显示“先停止再删除”的确认细节。
- `src/main/devices/ipc.ts` 校验主窗 sender 与 id 后调用 deleteDevice。
- `src/main/devices/lifecycle.ts` 会取消 starting，或停止 running/stopping，然后删除 AVD。内部 SDK 清理也复用删除流程，不能把所有内部调用一刀切拒绝。
- PRD 要求破坏性删除必须确认并说明 AVD 永久删除后果；新按钮策略不能取消停止态确认。

### 3.3 候选方案

**方案 A：仅隐藏 running 按钮**

在 DeviceRow 条件渲染，其他状态保留当前行为；对照 [React 官方条件渲染](https://react.dev/learn/conditional-rendering)。成本低，字面满足“运行时不显示”，但旧确认框或直接 IPC 仍能先停后删。

**方案 B：停止态才展示；用户删除入口同步校验（推荐）**

使用现有 stopped 状态作为按钮显示条件；主进程用户删除入口在当前状态非 stopped 时拒绝。主窗确认前后均以最新状态核验，避免确认期间设备启动后仍被删除。来源：同一 React 官方条件渲染机制，以及 [Electron IPC 官方文档](https://www.electronjs.org/docs/latest/tutorial/ipc)；项目具体状态和守卫依据为 3.2 所列真实代码。

这里的 UI 变化无需新库。内部已确认的 SDK 清理流程保持独立授权路径与既有停止/删除能力，不能被用户按钮策略意外阻断。新休眠态建议暂不展示删除，另提供明确的“放弃休眠状态”动作后回到 stopped；该产品建议已由用户确认。

### 3.4 可行性分析

| 维度 | A：只隐藏 running | B：停止态展示 + 用户入口守卫 |
| --- | --- | --- |
| 覆盖 | 直接满足按钮需求 | 同时覆盖过渡态和确认窗口竞态 |
| 兼容 | 后端行为完全不变 | 必须区分用户删除与内部清理，不改内部级联语义 |
| 成本 | 单个组件及测试 | 组件、主窗交互、IPC 守卫及测试；无需新依赖 |

### 3.5 结论与实施建议

结论：**借鉴思路手写**——在既有状态与组件中补条件渲染和用户操作守卫。

建议动作矩阵：stopped 保留启动/编辑/删除；running 显示停止/休眠，隐藏删除；starting/stopping/hibernating/resuming 隐藏删除；hibernated 显示恢复，删除策略见待确认假设。冻结库、跨来源桶等原有删除限制仍然有效，不能因 stopped 而绕过。

改动点：DeviceRow 的条件渲染、App 的删除确认与最新状态处理、devices IPC 的用户删除状态守卫；视必要调整 lifecycle 的用户入口与内部清理区分。测试覆盖鼠标、键盘焦点、不同状态无删除入口、确认期间状态变化，以及内部 SDK 清理回归。使用 impeccable 技能对齐当前图标动作布局，避免新增按钮挤压设备名。

## 4. 风险与开放问题

- 快照稳定性是首要门槛。旧 Quick 验收尚未完成；上轮 GPU 排查确认当前实例曾使用软件渲染，而官方快照文档提示软件渲染下可靠性较差。不可直接给所有镜像开放休眠。
- 快照保存的是虚拟设备状态，不保证远端 TCP、登录令牌有效期、IDE 调试连接或真实摄像头会话继续有效。恢复后可能要重连，不能承诺“所有任务无感续跑”。
- 配置、系统镜像、emulator 升级或 GPU 后端变化可能使快照失效。编辑和 SDK 切换必须提前提示；不要悄悄删除仍可能用于恢复的快照。
- 休眠会增加磁盘使用；低磁盘或宿主内存不足时保存/恢复可能慢或失败。实际空间、延迟和峰值只能由 PoC 给出。
- 应用退出、电脑关机、保存中崩溃、两个实例同时休眠和恢复命令重复到达，需要有界回收、持久记录和幂等保护。保存完成并不等于进程已退。
- 本轮只读查询命令帮助与状态，没有对用户实例执行暂停、保存、加载或退出。因此技术能力已确认，当前产品上的端到端可交付性尚待 PoC。
