# 应用内更新调研报告

> 创建时间：2026-11-23 15:21:07（Asia/Shanghai）
>
> 需求来源：参考多会话测试浏览器，为多开模拟器调研并编写开发计划
>
> 调研单元：3 个
>
> 状态：调研完成，待确认实施前提，未实施

## 1. 需求理解

### 1.1 功能目标

用户在已安装的多开模拟器里发现新版本、查看版本日志、下载并选择何时重启安装。启动检查可以静默运行。录屏、APK 安装、SDK 维护或设备状态变化期间，安装应让当前任务先完成。当前交付为本报告和[开发计划](../../plans/2026-11-23-in-app-update.md)。

### 1.2 调研问题

- [x] 浏览器实际用什么引擎，用户何时授权下载与安装？见第 2 节。
- [x] 模拟器现在能否直接使用浏览器的更新源布局？见第 3 节。
- [x] 哪些安装准备逻辑必须按模拟器的生命周期重写？见第 4 节。

### 1.3 调研范围

先核对运行时引擎和交互，再核对各引擎所需的发布资产，最后核对引擎获得安装许可前的准备动作。参考源码为本地 `multi-session-browser` 的 `ccf53f0`，目标源码为本地 `multi-session-device` 的 `62bc5e9`。公开发布状态于 2026-11-23 通过 GitHub API 只读核对。

## 2. 运行时引擎与交互

### 2.1 该部分要做什么

在安装版启动时检查稳定版，也支持手动检查。发现更新后给出版本、日志和下载进度。下载与重启安装分别由用户授权。

### 2.2 两个项目的现状

| 环节 | 多会话测试浏览器的现行实现 |
| --- | --- |
| 入口 | 主窗和独立窗 TabStrip 右端显示候选入口，设置「关于」提供手动检查，macOS 应用菜单「设置…」下方也能检查。菜单发现候选会打开版本日志，已最新或失败走原生反馈。见 [UpdateEntry.tsx](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/renderer/src/components/UpdateEntry.tsx) 和 [main/index.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/index.ts)。 |
| 状态 | 主进程持有单例控制器，检查、下载和安装互斥。主窗、独立窗、设置窗的顶层 frame 才可调用更新 IPC。renderer 用 `revision` 镜像状态，版本日志的动作再次核对候选版本。开发态和 Linux 不初始化引擎，两项入口同时隐藏时也不联网。见 [updates.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/updates.ts) 和 [updateController.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/updateController.ts)。 |
| macOS | 官方 Sparkle 2.10.1，经 Objective-C / Node-API 桥接。检查后保留 Sparkle 的候选回复，等用户点击下载。下载就绪保留安装回复，只有用户确认且安装准备通过才授权。选择「稍后」可在本进程继续安装。正常退出先等 Sparkle 确认取消，下次打开需要重新下载。见 [macSparkle.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/updates/macSparkle.ts)、[bridge.m](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/native/sparkle/bridge.m) 和 [浏览器 ADR-005](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/book/docs/decisions/ADR-005-macos-sparkle-update.md)。 |
| Windows | `electron-updater 6.8.9` 搭配 NSIS 及 GitHub provider，关闭自动下载、退出自动安装、预发行和降级。下载结束后出现一次原生「稍后 / 重启安装」确认，安装准备通过后调用 `quitAndInstall(false, true)`。见 [updates.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/updates.ts)。 |

模拟器还没有应用更新调用链，`electron-builder.yml` 的 generic publish URL 是示例地址。现有 `BoardHead`、设置「关于」、受限 preload 与三语主题系统可作为接入点。锁文件中模拟器用 Electron `39.8.10`、electron-builder `26.15.3`，浏览器用 Electron `45.3.0` 和同版 builder。浏览器桥接构建脚本把 Electron 版本和头文件 SHA-256 设为硬校验，直接复制其配置会在模拟器构建时失败。见 [模拟器 package-lock.json](../../../package-lock.json)、[打包配置](../../../electron-builder.yml)、[BoardHead](../../../src/renderer/src/components/BoardHead.tsx)、[关于页](../../../src/renderer/src/components/settings/PaneAbout.tsx) 和 [浏览器 build-sparkle.mjs](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/scripts/build-sparkle.mjs)。

### 2.3 候选方案

- **A. 复用浏览器双引擎。** macOS 用 Sparkle 2.10.1 与现有 Node-API 桥接思路，Windows 锁定 electron-updater 6.8.9。目标主进程复用控制器模式，窗口和 preload 采用模拟器自己的入口。 [Sparkle 2.10.1](https://github.com/sparkle-project/Sparkle/releases/tag/2.10.1) · [electron-builder v26 自动更新](https://www.electron.build/v26/docs/features/auto-update/)
- **B. 用 electron-updater 统一两端。** Windows 仍用 NSIS，Mac 回到 Squirrel.Mac，需要兼容的应用代码签名身份及 ZIP 更新资源。浏览器早期 ad-hoc 包在该路线交接验签失败。 [Electron autoUpdater 的 macOS 要求](https://www.electronjs.org/docs/latest/api/auto-updater#macos) · [浏览器迁移决定](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/book/docs/decisions/ADR-005-macos-sparkle-update.md)

### 2.4 可行性

| 维度 | A. 双引擎 | B. 单库 |
| --- | --- | --- |
| 技术匹配 | Windows 继续用现有打包目标。Mac 需在目标 Electron 上编译并用两个真实安装包验证。 | Windows 匹配。Mac 的签名和更新包需要另立路线。 |
| 产品约束 | 适配现有 ad-hoc 分发，保留显式下载安装和普通退出取消。 | 继续使用 ad-hoc 时，无法以包内结构校验推定跨版本安装可用。 |
| 成本 | 多一个原生构建和签名链，由参考实现降低移植量。 | 控制器接线较少，Mac 分发与证书维护成本另计。 |

### 2.5 结论与实施建议

**采用现成方案 A。** 使用同一套平台引擎和用户流程。将原生桥接绑定到目标 Electron 头文件、目标 CPU 及实测最低 macOS 版本。可复用控制器、日志清洗与桥接的通用部分，核对 MIT 许可和归属。用模拟器板头、关于页和 macOS 应用菜单承载入口，窗口布局走 impeccable。

## 3. 发布资产与更新源

### 3.1 该部分要做什么

发布可检查、可下载、可验证的完整版本。安装包、平台清单和用户看到的日志各自绑定到同一版本。

### 3.2 两个项目的现状

- 浏览器的 Mac 构建把 `SUPublicEDKey` 和 `SUFeedURL` 写进 app，用 Sparkle 私钥给 ZIP 签 EdDSA。arm64 / x64 各有 DMG、ZIP 和 appcast。appcast 从本架构的 Latest 地址获取，归档和日志链接指向准确的版本 Tag；Windows 从 GitHub Release 读取 `latest.yml`、NSIS EXE 和可选 blockmap。单份版本 Markdown 生成 Mac 日志附件、Windows `latest.yml.releaseNotes` 和 Release 正文。CI 核对资产后才公开草稿并设为 Latest。 [浏览器发布手册](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/.github/RELEASING.md)
- 模拟器的合并触发条件已具备。当前 `dev → main` 合并后构建 macOS arm64 DMG 与 Windows x64 EXE，发布两个安装包和 `SHA256SUMS`。`.github/release-notes.md` 内含当前版本说明，尚无共享给客户端的清单与日志生成。公开 API 对 `v1.0.1` 返回 `prerelease=true`、`draft=false`，`releases/latest` 返回 404。GitHub Latest 排除预发行和草稿；照搬 Latest 地址时，目前取不到稳定更新。 [模拟器发布工作流](../../../.github/workflows/release.yml) · [v1.0.1 Preview](https://github.com/PZRvm/multi-session-device/releases/tag/v1.0.1) · [GitHub Latest 规则](https://docs.github.com/en/rest/releases/releases#get-the-latest-release)

### 3.3 候选方案

- **A. GitHub 稳定版渠道。** 沿用浏览器的固定 Latest feed 和同版本专属附件，维护者首次授权时发布带更新器的稳定版；后续稳定版沿用同一入口。 [浏览器发布手册](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/.github/RELEASING.md)
- **B. 独立预览渠道。** 若仍希望预览版应用内自更新，另设固定预览清单地址和显式预览客户端策略。Mac 与 Windows 均需验证稳定包与预览包互不串流。 [Sparkle 渠道配置](https://sparkle-project.org/documentation/publishing/) · [electron-builder v26 渠道文档](https://www.electron.build/v26/docs/tutorials/release-using-channels/)

### 3.4 可行性

| 维度 | A. 稳定渠道 | B. 独立预览渠道 |
| --- | --- | --- |
| 技术匹配 | 复用参考项目的 feed 规则，要求仓库出现合格的稳定 Latest。 | 可继续分发 GitHub Preview，但需要额外的固定索引和两端渠道判定。 |
| 产品约束 | 保留已有 Preview 和发布 PR 触发条件，首次启用涉及发布决策。 | 支持预览用户连续升级，交互及信任边界需另行设计。 |
| 成本 | 单渠道、单发布清单，首版要建立本项目的签名与升级基线。 | 需要维护两组版本选择、资产测试与故障恢复。 |

### 3.5 结论与实施建议

**采用现成方案 A，作为待确认的发布设计。** 维护者确认前，正式更新源保持关闭，可用两组隔离版本验收。以后仅在稳定版构建生成 Mac arm64 ZIP / appcast、Windows x64 `latest.yml` 及所引用资产，保留原 DMG / EXE 名称和合并触发条件。版本日志用独立版本文件供发布工具读取，路径建议 `.github/release-notes/v<version>.md`，项目开发记录继续使用 git log。已有 `v1.0.1` 用户需手动覆盖安装首个带更新器的稳定版，此后才能在应用内更新。

## 4. 安装与设备任务保护

### 4.1 该部分要做什么

重启安装前让影响用户数据或设备状态的任务到达安全边界。下载失败、保存失败、设备未停干净或用户选择稍后时，旧版继续可用。

### 4.2 两个项目的现状

- 浏览器在确认后检查录屏忙态，冻结写入口、等在途写入、严格保存浏览器恢复集与历史，最后授权平台引擎。参考项目曾出现冷缓存恢复集覆盖问题，后有独立修复和真实联动回归。模拟器应保留这套顺序，持久化对象按本项目重新核对。 [浏览器 updatePreparation.ts](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/src/main/updatePreparation.ts) · [恢复集修复记录](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/book/plans/2026-11-15-修复更新准备恢复集R1.md)
- 模拟器正常退出可以询问保存或丢弃录制，随后停自有 AVD、等待设备写队列尾部、销毁投屏和日志流。有残留时可以选择强退；留下时恢复命令接纳和真机会话。配置写入已有设备队列、跨文件事务日志和存储只读保护。队列到尾只证明任务结算，无法替代失败结果核对。 [退出编排](../../../src/main/index.ts) · [设备清理](../../../src/main/devices/lifecycle.ts) · [设备持久化](../../../src/main/devices/persistence.ts) · [录制退出](../../../src/main/recording/index.ts)

### 4.3 候选方案

- **A. 借鉴浏览器顺序，编写模拟器的安装准备。** 使用现有录制、SDK、设备和投屏生命周期接口，在安装入口按目标产品语义设置忙态和写入屏障。 [浏览器 ADR-004](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/book/docs/decisions/ADR-004-app-update-ownership.md)
- **B. 直接走模拟器普通退出链。** 可重用的部分是 AVD 停机和流资源释放；普通退出的丢弃录制、强退与容错继续规则无法作为安装许可。 [模拟器退出编排](../../../src/main/index.ts)

### 4.4 可行性

| 维度 | A. 独立安装准备 | B. 普通退出复用 |
| --- | --- | --- |
| 技术匹配 | 在调用引擎前就能确认保存和停机结果，适配两端异步交接。 | 依赖关窗或退出回调时序，难以保证在引擎启动前已经完成。 |
| 产品约束 | 可明确拦住录屏处理、APK、SDK 移动或设备状态迁移，保持共享 SDK 与真机边界。 | 允许强退或丢弃数据，和本功能的安装保护目标冲突。 |
| 成本 | 复用已有域接口，新增一个主进程协调器和关键竞态测试。 | 接线更短，仍要重写退出分支和失败回退才能满足安装验收。 |

### 4.5 结论与实施建议

**借鉴顺序，由模拟器实现安装准备。** 用户确认后冻结冲突操作，再复核忙态、持久化和设备停机结果，全部成功才授权引擎。安装失败只恢复可安全恢复的能力，不把已关闭的 AVD 显示为仍在运行。已有真机保持设备连接，仅处理本应用管理的流和跟踪。普通退出用现有清理规则，Mac 在进入该链前先结算 Sparkle 的取消。

## 5. 风险与待验证事项

- **Mac 验签与宿主权限。** Sparkle EdDSA 验证更新归档；应用仍用 ad-hoc 签名，首次手动安装可能受 Gatekeeper 约束，升级后摄像头、麦克风、局域网权限可能重新询问。App bundle、Sparkle framework 和 helper 要先完整组装并最终签名，再归档与签署 ZIP。 [Sparkle 发布说明](https://sparkle-project.org/documentation/publishing/) · [现有 ad-hoc 签名钩子](../../../scripts/adhoc-sign-mac.cjs)
- **Windows 分发信任。** 现有 NSIS 未做代码签名。参考实现依赖 GitHub HTTPS 与清单哈希，只有配置发布者身份时才有对应的发布者验证。首版需确认是否沿用无签名分发，并实测 SmartScreen、安装范围和重启。 [electron-updater v26 文档](https://www.electron.build/v26/docs/features/auto-update/) · [模拟器现有发布说明](../../../.github/release-notes.md)
- **平台证据。** 浏览器已有 Mac arm64 和 Rosetta x64 的隔离升级证据，原迁移计划仍把 Windows x64 真实升级列为待测。这些结果只确定参考路线。目标项目需要在自己的 Electron、安装包和用户数据夹具上重新验收。 [浏览器迁移计划](https://github.com/PZRvm/multi-session-browser/blob/ccf53f0/book/plans/2026-11-14-macOS更新迁移Sparkle.md)

## 6. 待确认假设

- 首期沿用正在发布的 macOS Apple Silicon 与 Windows x64，不扩到 Intel Mac、Linux 或 Windows ARM。
- 面向稳定版开放更新，保留已公开 Preview；首个稳定版的发布时点、版本号及正式密钥配置由维护者确定。
- 接受参考体验：Mac 选「稍后」可以本次进程内继续安装，普通退出后需要重新下载。自有空闲运行中的 AVD 可在明确提示后正常停机，存在保护任务时延后安装。
