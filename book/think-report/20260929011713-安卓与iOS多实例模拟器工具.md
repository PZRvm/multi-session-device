# 安卓与 iOS 多实例模拟器工具 可行性调研报告

> 创建时间：2026-09-29 01:17（Asia/Shanghai，与文件名 14 位时间戳一致）
> 需求来源：用户原话要点——"再做两个同系列的软件，一个安卓一个 iOS，新建会话就是新建模拟器，可以同时开启多个模拟器，以 tab 方式切换，调研技术可行性"
> 调研单元：5 个（安卓实例管理 / 安卓画面嵌入 / iOS 实例管理 / iOS 画面嵌入 / 架构复用与合规）
> 状态：已确认（2026-09-29 用户批复，见第 8 节；执行顺序：先安卓、后 iOS；未实施）

## 1. 需求理解

### 1.1 功能目标

在"多会话测试浏览器"产品思路之上再做两款同系列桌面工具，面向软件测试人员：

- **安卓版**：左侧会话栏管理多个完全隔离的 Android 模拟器实例（AVD），"新建会话"即创建一台全新的模拟器实例（登录态、应用数据、存储互不影响）；可同时启动多台并行运行；右侧内容区以 **tab 方式切换**当前显示与操控的实例，画面嵌入在应用窗口内。
- **iOS 版**：同样形态，实例换成 Apple iOS Simulator 设备。

两款均为独立仓库、独立产品（系列交互语言一致），不改动本仓 `multi-session-browser`。预期效果：测试人员在单一应用内并行维护 N 套互不污染的移动端测试环境，点击 tab 即切换到对应设备画面并直接操控。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 安卓模拟器能否官方支持多实例并发？——能。官方 emulator CLI 文档 `-port` 条目：控制台端口范围 5554–5682，"允许 64 台虚拟设备并发"（见 2.3 方案 A）
- [x] "会话隔离"在模拟器上怎么落地？——安卓：每会话独立 AVD（克隆/Duplicate，各自独立数据目录），`-read-only` 多实例会丢写入不可用；iOS：每台设备天然独立 data container，`simctl clone` / `erase`（见 2、4 章）
- [x] 安卓模拟器能否无头运行（不弹模拟器自己窗口）？——能，`-no-window` 官方支持，经 adb 访问（见 2.3）
- [x] 模拟器画面能否真正嵌入 Electron 窗口内（而非摆窗口）？——安卓可以：scrcpy 协议视频流 + WebCodecs 解码（Tango 全链路 MIT）；iOS 无公开帧流 API，只能 ScreenCaptureKit 窗口采集（见 3、5 章）
- [x] 触摸/操控能否从嵌入画面反向注入？——安卓：scrcpy 控制协议原生支持；iOS：idb/FBSimulatorControl 经逆向的 Indigo/dtuhidd 通道注入，无需窗口聚焦（见 3.3、5.3）
- [x] iOS 多模拟器并发的资源量级？——Apple Silicon 16GB 实测每台约 1.3GB RAM、约 150 进程 + 3000 文件描述符，10 台最优、14 台可达（需调系统上限）（见 4.3）
- [x] iOS 版的 macOS/Xcode 依赖与合规边界？——iOS Simulator 仅随 Xcode 运行于 macOS，runtime 不可随第三方 App 再分发，只能检测/引导安装（见 6.3）
- [x] 依赖库的许可证是否干净？——Tango/scrcpy-server(Apache-2.0)/ws-scrcpy/idb 均 MIT 或 Apache-2.0（见各章）
- [x] 本仓哪些资产可直接平移到两个新 App？——Electron 壳层全套（会话栏/tab 条/视图编排/IPC 纪律/i18n 机制）（见 6.2）
- [x] 竞品有没有已经做成这个形态的？——Genymotion 多开（商业）、Corellium 云端虚拟化（商业）、RocketSim（Xcode 内增强）；无"会话隔离为一等公民"的免费桌面产品，差异化成立（见 6.3）

### 1.3 拆分判断

拆为 5 个调研单元。理由：两个目标平台（Android SDK 体系 / Apple Xcode 体系）互不相关，且每个平台的"实例生命周期管理"与"画面嵌入操控"是两个独立能力点（后者决定产品体验上限，风险集中于此）；另设跨切单元收敛架构复用、合规与资源结论。依赖顺序：单元 A/B（安卓）与 C/D（iOS）相互独立；单元 E 依赖前四者结论。

## 2. 调研单元 A：安卓版——多模拟器实例生命周期管理

### 2.1 该部分要做什么

新建会话 = 创建一台数据隔离的 AVD 并可启动；会话可关闭/销毁/重置；多台同时运行；监控其运行状态。不含画面渲染（单元 B）。

### 2.2 项目现状

新 App 为独立仓库，本仓无模拟器相关代码。可平移的是壳层与服务组织模式：

- `src/main/sessions.ts`：本仓会话生命周期服务（partition 隔离）——新 App 的"模拟器会话服务"照此模式重写（子进程管理替代 partition）
- `src/shared/sessions.ts`：跨进程会话类型与 IPC 通道常量——同构平移
- `src/main/index.ts` + `src/preload/index.ts` + `src/preload/index.d.ts`：Electron 三进程纪律（本仓 AGENTS.md 分层规则），新 App 沿用
- 红线映射：本仓"每会话独立 partition 禁止共享"→ 新 App 对应"每会话独立 AVD 数据目录禁止共享"，语义等价

### 2.3 候选方案

**方案 A：Android SDK 官方 CLI 全托管（avdmanager / sdkmanager / emulator 子进程）**

- 原理：App 检测/引导安装 cmdline-tools + emulator + system image + platform-tools，以子进程方式调 `avdmanager create avd` 建会话、`emulator @<avd> -no-window -port <n>` 无头启动、`adb -s emulator-<n>` 寻址。
- 来源（均已实际读取核实）：
  - emulator 官方命令行文档：`-no-window`"禁用模拟器图形窗口……可通过 adb 或 console 访问"；`-port`"范围 5554 到 5682，允许 64 台虚拟设备并发"；`-gpu swiftshader_indirect` 示例；`-data` 可指定独立用户数据镜像文件；`-snapshot` 从快照恢复"通常远快于完整启动"（https://developer.android.com/studio/run/emulator-commandline）
  - AVD 官方文档：每个 AVD 有专用存储区（用户数据 + 模拟 SD 卡），Device Manager 提供 Duplicate 复制 AVD（https://developer.android.com/studio/run/managing-avds）
  - 旧版官方工具文档：多实例并发、各实例独立 user data/SD card 存储区（http://docs.52im.net/extend/docs/api/android-50/tools/devices/emulator.html）
- 与本项目的适配点：主进程 Node 子进程管理，无新原生依赖；adb 寻址天然区分实例。

**方案 B：Genymotion Desktop**

- 原理：商业 Android 模拟器（自有 VirtualBox/QEMU 栈），官方支持多开。
- 来源：https://www.genymotion.com/ ；官方支持页"数量无上限，但不建议同时超过两台"（https://support.genymotion.com/hc/en-us/articles/15006454206877-How-many-devices-can-I-run-simultaneously）
- 看过、不选：商业订阅、非 AVD 体系（会话数据格式私有）、不可程序化深度控制；其"不建议同时 >2 台"也提示多开资源代价。

**方案 C：云端虚拟化（Corellium / Genymotion Cloud）**

- 来源：https://www.corellium.com/ ；2020-12 美国联邦法院裁定其 iOS 虚拟化构成 fair use（https://appsecsanta.com/corellium）
- 看过、不选：本地 Android 模拟器完全可行，无需云依赖与订阅；作为"iOS 真虚拟化"备选见单元 D。

### 2.4 可行性分析

| 维度     | 方案 A（SDK CLI 托管）                                                                                                             | 方案 B（Genymotion）                 |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------ |
| 技术匹配 | 多实例并发官方明文支持（64 台端口空间）；每 AVD 独立存储区 = 隔离语义成立；`-no-window` + `-gpu swiftshader_indirect` 满足无头嵌入 | 多开支持但会话数据不可自定义路径体系 |
| 规则冲突 | 无；与"会话隔离"红线语义对齐                                                                                                       | 数据格式私有，隔离粒度不可控         |
| 成本     | 全免费；需引导用户接受 Android SDK 许可（`sdkmanager --licenses`）；每实例磁盘 2GB+                                                | 商业订阅                             |

资源量级旁证：Android Q+ 系统镜像模拟器最小 RAM 提至 2GB（https://developer.android.com/studio/releases/emulator）；多实例同机竞争共享资源是已知不稳定源（https://www.qawolf.com/blog/5-strategies-to-address-android-emulator-instability-during-automated-testing）。Apple Silicon 需 arm64-v8a 系统镜像（Google 官方过渡仓库 https://github.com/google/android-emulator-m1-preview ；https://dev.to/mochafreddo/setting-up-and-managing-android-emulators-on-macos-with-homebrew-3fg0）——本机为 darwin arm64，满足。

### 2.5 结论与实施建议

- 结论：**采用现成方案**（Android SDK 官方 CLI 子进程托管），隔离落地为"每会话一个克隆 AVD"。注意：`-read-only` 虽允许同一 AVD 多实例并发，但写入不持久化，不满足"会话状态保留"，故不用；如后续想省磁盘可 PoC"模板 AVD + `-data` 独立镜像"方案（同 AVD 并发的目录锁行为未核实，列入风险）。
- 落地路径（新仓库）：`src/main/emulator/sdk.ts`（检测/引导安装 SDK 组件；cmdline-tools 的 avdmanager/sdkmanager 是 Java 程序，需随 App 附带 JRE 或检测系统 JDK；SDK 许可经应用内确认后写入 licenses 哈希文件，等效 `sdkmanager --licenses`）→ `src/main/emulator/avd.ts`（create/delete/duplicate/erase，对应本仓 `src/main/sessions.ts` 模式）→ `src/main/emulator/runner.ts`（`-no-window -port <n> -gpu swiftshader_indirect` 子进程池 + 崩溃重启）→ `src/shared/sessions.ts` 同构类型（状态机增加"创建中/启动中/运行中/停止"，模拟器冷启动 20-60s 必须异步化）→ IPC 通道照本仓 preload 纪律。`-snapshot` 用作会话快速恢复选项。依赖面：**不需要 Android Studio**——仅 cmdline-tools + emulator + system image + platform-tools 四件，可由 App 引导下载到独立 SDK 目录，或复用用户已有 `ANDROID_HOME`（含 Android Studio 装的）。
- 界面涉及新建会话弹层/列表的，实现时走 impeccable 技能。

## 3. 调研单元 B：安卓版——模拟器画面嵌入与操控

### 3.1 该部分要做什么

右侧内容区把每台运行中实例的画面渲染进应用窗口内（真嵌入，不是摆外部窗口），tab 切换显示目标；鼠标/键盘从画面反向操控设备。

### 3.2 项目现状

- 本仓右侧内容区为 `WebContentsView` 嵌入（`src/main/browser/manager.ts` / `src/main/browser/registry.ts` / `src/main/browser/windows.ts` 编排），tab 条为 `src/renderer/src/components/browser/TabStrip.tsx`——新 App 的内容区从"原生视图嵌入"换成"视频流画布嵌入"，编排模式（registry + 激活切换）可平移。
- 本仓 F12 DevTools per session（`docs/PRD.md` 3.3/4.3）在新 App 的对应物待产品定义（候选：logcat 面板、WebView 调试经 adb forward 接 chrome://inspect 协议）。

### 3.3 候选方案

**方案 A：Tango（@yume-chan/adb 全家桶）+ scrcpy-server + WebCodecs（推荐）**

- 原理：Tango 是 TypeScript 重写的 ADB 客户端，主进程经 TCP 连 adb server/模拟器 adbd，push scrcpy-server 到设备并启动，H.264 视频流送 renderer 用 WebCodecs 硬解渲染 canvas，触摸/按键走 scrcpy 控制协议反向注入。
- 来源（已实际读取核实）：
  - 仓库 README 原文："Tango is a TypeScript re-implementation of ADB client that **works in Chromium-based browsers (including Chrome for Android), Node.js, and Electron**"，MIT 许可，3.2k stars / 1243 commits（https://github.com/yume-chan/ya-webadb ，文档 https://tangoadb.dev/ ）
  - WebCodecs 解码器独立包 `@yume-chan/scrcpy-decoder-webcodecs` 在 npm 持续发布（2026-03，https://www.npmjs.com/package/@yume-chan/scrcpy-decoder-webcodecs ）
  - scrcpy 本体 Apache-2.0（https://github.com/Genymobile/scrcpy ），server 端二进制可随 App 分发
  - scrcpy 多实例寻址 `-s <serial>`（https://github.com/Genymobile/scrcpy/issues/485 ）
- 适配点：主进程持 ADB 连接（renderer 无 Node 的纪律不破），编码流经 IPC 送 renderer 解码；Electron 39 的 Chromium 带 WebCodecs。

**方案 B：ws-scrcpy 整栈内嵌**

- 原理：Node 服务 + 浏览器前端，产品形态就是"多设备列表 + 多窗口/tab 镜像操控"，与目标形态几乎重合。
- 来源：MIT（https://github.com/NetrisTV/ws-scrcpy ，LICENSE https://github.com/NetrisTV/ws-scrcpy/blob/master/LICENSE ）
- 看过、作备选：自带 Web 栈（自有 server + 前端）与 Electron 壳层重复，需大改才能融入本系列交互；维护活跃度一般（镜像更新 2024-11，https://sourceforge.net/projects/ws-scrcpy.mirror/ ）。其设备列表/多窗产品形态值得借鉴。

**方案 C：scrcpy 桌面进程 + 窗口采集**

- 原理：每实例 spawn 一个 scrcpy SDL 窗口，再用 ScreenCaptureKit 采窗口。
- 看过、不选：绕远路（视频已经解码渲染又被采集重编码），延迟与清晰度双损，且 macOS 上无法窗口 reparent。

### 3.4 可行性分析

| 维度     | 方案 A（Tango 组合）                                                                                   | 方案 B（ws-scrcpy）                    |
| -------- | ------------------------------------------------------------------------------------------------------ | -------------------------------------- |
| 技术匹配 | 像素级真嵌入 canvas、tab 即流切换、控制协议原生，覆盖需求与边界（多实例、低延迟）                      | 形态匹配但栈重复、嵌入 Electron 需改造 |
| 规则冲突 | 无（MIT/Apache-2.0，主进程 Node、renderer 纯 JS）                                                      | 无                                     |
| 成本     | 依赖轻（npm 包 + 一个 scrcpy-server 二进制）；风险点是与 scrcpy 协议版本的耦合（Tango 按版本发布适配） | 引入整套服务端栈，耦合深               |

### 3.5 结论与实施建议

- 结论：**采用现成方案**（Tango + scrcpy-server + WebCodecs 组合），无需自研协议栈。
- 落地路径：新仓库 `src/main/scrcpy/stream.ts`（Tango ADB 连接池、scrcpy server 生命周期）→ 流经 IPC（或 MessagePort 直通）送 `src/renderer/src/components/device/DeviceCanvas.tsx`（WebCodecs 解码 + canvas 渲染 + 指针事件转 scrcpy 控制消息）→ tab 切换即流的启停/挂起（复用本仓 `TabStrip.tsx` + registry 激活模式）。tab 内容布局与视觉实现时走 impeccable 技能。
- 先做 1-2 天 PoC：单台 AVD 无头启动 + Tango 取流 + canvas 操控，验证延迟与帧率。

## 4. 调研单元 C：iOS 版——多模拟器实例生命周期管理

### 4.1 该部分要做什么

同单元 A，实例换成 iOS Simulator：新建会话 = 创建一台全新模拟器设备；隔离、并行、重置、销毁。

### 4.2 项目现状

同单元 A（本仓无可复用模拟器代码，平移壳层与会话服务模式）。平台约束：iOS 版仅 macOS、依赖 Xcode 安装（见单元 E）。

### 4.3 候选方案

**方案 A：xcrun simctl CLI 子进程（推荐主路径）**

- 原理：`simctl create <name> <devicetype> <runtime>` 建设备（stdout 返回 UDID）、`clone` 克隆（需先 shutdown 源设备）、`boot`/`shutdown`/`erase`/`delete`/`rename` 管生命周期，`bootstatus -b` 阻塞等启动完成，`privacy`/`status_bar`/`io`/`install`/`launch` 等辅助。
- 来源（已实际读取核实的全量子命令清单与用法）：https://suelan.github.io/2020/02/05/iOS-Simulator-from-the-Command-Line/ （其引用官方 WWDC19/418 https://developer.apple.com/videos/play/wwdc2019/418/ ）
- 隔离依据：每台设备独立数据容器（`get_app_container ... data` 输出 `~/Library/Developer/CoreSimulator/Devices/<UDID>/data/...`），`erase` 重置。

**方案 B：FBSimulatorControl 框架直嵌**

- 原理：Meta 的 Swift 框架（idb 仓库内），官方描述原文："**Boots multiple Simulators concurrently on the same host, isolated in custom 'Device Sets'**"。
- 来源：https://fbidb.io/docs/idb/fbsimulatorcontrol/ ；仓库 MIT（https://github.com/facebook/idb ，5.3k stars，构建前置 macOS 15+ / Xcode 26+，活跃维护）
- 定位：本单元用不到其全量能力（simctl 已够），但它是单元 D 触摸注入的载体。

**方案 C：idb companion（gRPC 服务）**

- 来源：https://github.com/facebook/idb （`brew install facebook/fb/idb`）
- 看过、备选：多一层 companion 进程，一期 CLI 即可；自动化深水区再引入。

并发资源量级（已核实）：Apple Silicon M1 16GB 实测每台模拟器约 **1.3GB RAM、150 进程、3000 文件描述符**，10 台最优、14 台可达，超过 5-9 台需调 `launchctl limit maxproc` / `sysctl kern.maxfiles`（Apple Simulator 团队 WWDC lab 背书的调参，https://blog.nihongo-app.com/running-14-ios-simulators-in-parallel/ ）。多实例并行为 Xcode 官方日常工作流（https://rafellk.medium.com/deploy-to-multiple-ios-simulators-with-one-single-build-a3292d204f48 ）。

### 4.4 可行性分析

| 维度     | 方案 A（simctl CLI）                                                      | 方案 B（FBSimulatorControl）                            |
| -------- | ------------------------------------------------------------------------- | ------------------------------------------------------- |
| 技术匹配 | 全生命周期命令齐备；每设备独立 data container 天然隔离；并发实证 10-14 台 | 同能力 + Device Set 隔离更细，但引入 Swift 产物集成成本 |
| 规则冲突 | 无                                                                        | 无（MIT）                                               |
| 成本     | 零依赖（macOS + Xcode 自带）                                              | 需打包/构建 Swift 框架或独立 helper 进程                |

### 4.5 结论与实施建议

- 结论：**采用现成方案**（simctl CLI 子进程托管），会话 = 独立模拟器设备，隔离零成本。
- 落地路径：与单元 A 同构——新仓库 `src/main/simulator/device.ts`（create/clone/erase/delete）+ `src/main/simulator/runner.ts`（boot + `bootstatus -b` 轮询 + shutdown）+ 共享类型状态机。App 内提供"运行实例数上限"设置与资源提醒（16GB 建议 ≤6 台）。UI 走 impeccable。

## 5. 调研单元 D：iOS 版——模拟器画面嵌入与操控（风险集中区）

### 5.1 该部分要做什么

同单元 B：画面嵌入应用窗口、tab 切换、反向操控。iOS 侧的难点：Apple 没有公开的"模拟器帧流"API。

### 5.2 项目现状

同单元 B（复用 TabStrip/registry 编排与内容区框架）。macOS 权限约束：ScreenCaptureKit 需"屏幕录制"授权、CGEvent 注入需"辅助功能"授权（与本仓 dev 态 TCC 坑点同类的系统层问题，见 `AGENTS.md` 坑点节）。

### 5.3 候选方案

**方案 A：Simulator.app 多窗口 + ScreenCaptureKit 单窗采集 + idb/FBSimulatorControl 注入（推荐）**

- 原理：每会话 `boot` 后用 `open -a Simulator --args -CurrentDeviceUDID <UDID>` 为该设备开一个 Simulator 窗口（多设备各一窗口，Xcode 官方多模拟器工作流形态）；App 内 tab 激活时用 ScreenCaptureKit 只采该设备窗口，画面渲染进 Electron；触摸注入不经窗口，走 idb companion 的 `ui tap/text`（底层 Indigo/dtuhidd）。
- 来源（已实际读取核实）：
  - ScreenCaptureKit 官方文档：SCContentFilter 支持"捕捉单个窗口或整个显示器"，WWDC22 明示 `desktopIndependentWindow` 类型过滤器（https://developer.apple.com/cn/documentation/screencapturekit/capturing-screen-content-in-macos 、https://developer.apple.com/kr/videos/play/wwdc2022/10155/ ）
  - FBSimulatorControl 官方文档原文："This service is how clicking on the UI of the Simulator.app translates into touches within the iOS Simulator"——Indigo（逆向 mach IPC）/dtuhidd（XPC）双传输已抽象（https://fbidb.io/docs/idb/fbsimulatorcontrol/ ）
  - `open -a Simulator --args -CurrentDeviceUDID` 定向开窗的成熟用法（https://itnext.io/you-dont-need-gui-or-how-to-control-ios-simulator-from-command-line-bf5cfa60aed2 、https://developernote.com/2024/05/launching-the-ios-simulator-from-terminal/ ）
  - 多设备同时开窗为社区常规操作（https://www.reddit.com/r/reactnative/comments/qgs42w/open_two_simulators_iphone_and_ipad_simultaneously/ ）
- 适配点：采集端需一个 Swift/Rust 原生模块或 helper 进程（Electron 主进程没有 SCK 绑定）；注入端经 idb companion gRPC/CLI。

**方案 B：sim-video / FBSimulatorControl 视频能力直取**

- 原理：idb 构建产物含 `sim-video`（官方目录注释"the simulator video recorder"，`Tools/VideoRecorder`）。
- 来源：https://github.com/facebook/idb （Build/Distribution 清单）
- 看过、待 PoC：若其能以流式输出帧则可摆脱"依赖 Simulator 窗口存在"，但公开文档未承诺帧率/延迟，列为 PoC 项而非主路径。

**方案 C：`simctl io recordVideo` 当直播流**

- 已核实不可行：recordVideo 为文件录制、SIGINT 时才写完索引（moov），格式非流式；官方 FAQ 仅支持"多台并行各写各文件"（https://www.screenify.studio/blog/2026-08-13-simctl-recordvideo-ios-simulator 、https://suelan.github.io/2020/02/05/iOS-Simulator-from-the-Command-Line/ ）。适用于"会话录屏取证"功能，不适用于实时画面。

**方案 D：Corellium 云端（看过、不选）**

- 唯一能"真虚拟化 iOS 并浏览器投屏"的商用路径，但云端订阅 + 数据出内网，定位不同（https://www.corellium.com/ ；fair use 判例背景 https://appsecsanta.com/corellium ）。

### 5.4 可行性分析

| 维度     | 方案 A（SCK 采集 + idb 注入）                                                                                           | 方案 B（sim-video）               |
| -------- | ----------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| 技术匹配 | 60fps 级窗口采集 + 无聚焦注入，覆盖"嵌入 + tab 切换 + 操控"；但非像素级嵌入——依赖 Simulator 窗口存在与摆位（屏外/缩小） | 理论上更干净，帧率/延迟无公开承诺 |
| 规则冲突 | 需屏幕录制 + 辅助功能两授权（桌面直发可接受）；私有 API 风险由 idb 抹平                                                 | 同左                              |
| 成本     | 一个原生 helper（Swift 进程或模块）+ idb 依赖；工程量为两 App 中最大                                                    | 若 PoC 通过可省掉窗口管理复杂度   |

### 5.5 结论与实施建议

- 结论：**借鉴思路组合手写**（官方 ScreenCaptureKit 采集 + 开源 idb 注入 + 自研窗口编排），无单一现成方案；iOS 版整体判定为**有条件可行**——生命周期侧完全官方成熟，嵌入侧体验上限低于安卓版（窗口采集 vs 像素流），需 PoC 定版。
- 落地路径：`src/main/capture/sck-helper`（Swift helper 进程：枚举 Simulator 窗口 → SCStream 采单窗 → H.264 输出管道 → 主进程转发 renderer 解码渲染）→ `src/main/inject/idb.ts`（idb companion 生命周期 + `ui tap/text/key` 封装）→ 窗口管家（把各 Simulator 窗口按 UDID 绑定、置于屏外或缩微，tab 激活时切换采集目标；窗口管理用 Accessibility API，需辅助功能授权）→ 录屏取证用 `recordVideo`（方案 C 的正确用途）。UI 走 impeccable。
- 先做 3-5 天 PoC：两台设备并跑 + 双 tab 采集切换 + idb 注入点击，量化延迟/帧率/切 tab 恢复速度；同时 PoC sim-video 是否可流式。

## 7. 风险与开放问题

- **iOS 嵌入体验**（最高风险）：ScreenCaptureKit 路线依赖 Simulator 窗口存在；切 tab 时窗口隐藏/缩微后的采集行为、多显示器摆位、用户手动关窗等边界需 PoC 验证。
- **Xcode 26/27 Simulator 形态变动**：Apple 论坛已有"DeviceSet 启动的模拟器不进 DeviceHub、呈 headless"的讨论（https://developer.apple.com/forums/tags/simulator ），`-CurrentDeviceUDID` 开窗在新版 Xcode 的行为需在目标 Xcode 版本上锁定验证。
- **安卓同 AVD 多实例锁**：本报告推荐的"克隆 AVD"路线不受影响；若日后改走"模板 AVD + `-data` 独立镜像"省磁盘方案，需先验证 AVD 目录锁是否允许并发。
- **scrcpy 协议版本耦合**：Tango 与 scrcpy-server 版本需配套锁定（随 App 分发固定版本可解）。
- **多开资源竞争**：安卓多实例同机资源竞争是已知不稳定源（QA Wolf 文，见 2.4）；需实例数上限 + 启动排队 + 内存水位提醒。
- **macOS 权限摩擦**：iOS 版需屏幕录制 + 辅助功能两项授权，首次体验要设计引导（专业用户向，不做手把手引导，但授权状态检测必须做）。
- **IDE 联调干扰面**：本工具须与 Android Studio 共用 adb server（5037），adb 版本不一致会触发 server 重启闪断 IDE 连接；iOS 侧禁用自定义 Device Set 否则设备对 Xcode 隐身（详见第 9 节）。
- **模拟器冷启动耗时**：安卓 20-60s、iOS 亦不快，会话状态机与 UI 必须全异步（快照/克隆可缓解）。

## 9. 追答（2026-09-29）：Android Studio / Xcode 能否部署调试到本工具的实例上

结论：**两端都可以**。这是"标准本地栈"路线的直接收益——本工具创建/启动的实例在 IDE 眼中就是普通设备，中间没有私有虚拟化层。

**安卓侧**

- 实例即标准 adb 设备（`emulator-5554` / `emulator-5556`…），Android Studio 设备下拉、`./gradlew installDebug`、`flutter run`、JDWP 断点调试、Logcat、Profiler 全部照常（多实例时 IDE/命令经 adb 以 serial 寻址，官方文档要求多实例场景显式 `-s`，见 2.3 方案 A 出处）。
- 设计要求：本工具必须与 Android Studio **共用同一 adb server（默认端口 5037）**，不得另起隔离 server；优先复用用户已有 platform-tools 的 adb，避免 adb client/server 版本不一致引发的 server 自动重启（会把 IDE 的连接一并闪断）。会话设备命名带会话标识（如 `MST-03 · Pixel 8`），便于在 IDE 设备下拉里辨认。

**iOS 侧**

- 会话设备注册在 CoreSimulator **默认设备集**（`~/Library/Developer/CoreSimulator/Devices`），Xcode 运行目标下拉、`xcodebuild test -destination 'platform=iOS Simulator,...'`、`flutter run` 都能选到并部署，lldb 调试照常——设备由谁 boot 不影响 IDE 交互（`simctl create` 建的设备进 Xcode 目标列表是 CI 常规用法，见 4.3 / 5.3 出处）。

- 待 PoC：Xcode 26+ 向已 boot 设备部署时的 Device Hub / Simulator 窗口行为，与本工具窗口管家的协调（已列入第 7 节风险）。

**生命周期协调**

会话"擦除/销毁"是破坏性操作，需检测目标设备上是否有活跃的 IDE 调试进程并二次确认（对齐本仓 PRD 4.10 破坏性确认框惯例）。

## 10. 追答（2026-09-29）：SDK / 运行时引导下载有没有可直接调用的接口

**安卓侧：有官方接口，就是 `sdkmanager` 子进程本身。**

- 官方文档定义其为"查看、安装、更新、卸载 Android SDK 包"的命令行工具，支持 `--sdk_root`、`--channel`、`--package_file`（https://developer.android.com/tools/sdkmanager ）。一条命令即完成下载、校验、解压、依赖解析：`sdkmanager --sdk_root=<dir> "platform-tools" "emulator" "system-images;android-35;google_apis;arm64-v8a"`；进度解析 stdout 百分比输出即可。
- 引导的引导：cmdline-tools 本体是 dl.google.com 固定 URL 的 zip（`commandlinetools-mac-<build>_latest.zip`），App 内置版本号直接下载解压；包仓库清单（repository2 XML）也公开可解析，但无需自拼。
- 许可：应用内确认后写 `licenses/android-sdk-license` 哈希文件（CI 惯例，等效 `sdkmanager --licenses`）。
- 结论：安卓侧引导下载全程无浏览器、无手工，可完全 App 内闭环（前提：随 App 附带或检测 JRE，见 2.5）。

**iOS 侧：分两段，只有"装 Xcode"这一步没有官方接口。**

- Xcode 本体：Apple 未提供命令行下载渠道（Mac App Store / developer.apple.com/downloads 需 Apple ID 网页会话）。App 只能做版本检测 + 跳转引导；可选集成第三方 `xcodes`（https://github.com/XcodesOrg/xcodes ，可编程下载安装多版本 Xcode，走 XCODES_USERNAME/XCODES_PASSWORD 环境变量认证）——涉及把 Apple ID 凭据交给工具，属安全决策，默认不集成、对目标用户（开发/测试机多有 Xcode）以检测为主。
- Xcode 装好之后全部有官方命令（Apple 官方文档 https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components ）：
  - `xcodebuild -runFirstLaunch`：首启安装所需系统组件；
  - `xcodebuild -downloadPlatform iOS`：下载指定平台模拟器 runtime；`-downloadAllPlatforms` 下载全部；
  - `xcrun simctl runtime add <dmg>`：从 dmg 安装 runtime（社区实证用法，见 https://www.reddit.com/r/iOSProgramming/comments/16miit0/ ）；历史版本 dmg 可经第三方 `ipsw` CLI 下载（https://testableapple.com/install-ios-simulator-runtimes/ ）；
  - 检测面：`xcodebuild -version`、`xcrun simctl list runtimes`。

## 11. 追答（2026-09-29）：桌面框架选型——是否继续用 Electron

**结论：维持 Electron（与本仓同栈），不换框架。**

依据三条：

1. **核心链路形状**：安卓侧风险最低的路线（Tango ADB + scrcpy 客户端 + WebCodecs 硬解 + canvas）是 TypeScript + Chromium 形状——Tango 官方只承诺 Chromium 系浏览器 / Node.js / Electron（见 3.3）。换框架 = 用其它语言重写 ADB 与 scrcpy 协议栈，无同等成熟度的替代生态。
2. **壳层复用是成本底线**：会话栏 / TabStrip / antd 6 / zustand / i18n / IPC 纪律约八成直接平移（见 6.2），且是系列产品识别度本身。
3. **Electron 的短板在本产品不致命**：壳内存约 300–500MB，对每台安卓实例 2.5–3GB 不构成瓶颈（8GB 最低档的约束在模拟器不在壳，见第 8 节假设 5 批复）；iOS 侧原生能力（ScreenCaptureKit、idb）本就以外置 helper 进程承担（见 5.5），换框架不能省掉这块。

对照结论：Tauri（省内存但核心链路需 Rust 重写 + WKWebView 解码未验证，不采用）；Qt（视频管线全自建，Genymotion 级工程量，不采用）；SwiftUI 原生（仅 iOS-only 场景成立，双端合一下出局）；Flutter（Dart 无成熟 ADB/scrcpy 生态，各项不占优）。

**重新选型的触发条件**（任一成立再评估）：产品收缩为 iOS-only；转向大众市场、安装包体积成硬指标；团队整体 Rust 化。
