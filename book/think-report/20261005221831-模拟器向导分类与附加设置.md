# 模拟器向导分类与附加设置功能调研报告

> 创建时间：2026-10-05 22:18:31（Asia/Shanghai，与文件名一致）
> 需求来源：设备画像按 Phone、Tablet、Wear OS 等分类；系统 API 选择与附加设置布局参考 Android Studio。
> 调研单元：3 个，覆盖用户后两项需求。
> 状态：调研完成，范围已确认（未实施）；SD 卡暂不开发，跨架构放到二期。

## 1. 需求理解

### 1.1 功能目标

测试人员在应用内创建 AVD 时，先按设备形态找到画像，再按 API、服务类型和兼容性选择系统镜像，最后配置设备参数。布局参考用户截图 3、4 及最后两张附加设置截图：左侧形态导航、中央表格；配置页左侧「设备 / 附加设置」标签，右侧固定设备与镜像摘要。

预期效果包括快速搜索画像、看见屏幕与兼容 API 信息、明确镜像是否安装及下载大小，以及修改参数后在实际 AVD 中生效。截图中的数值是参考界面当前选择，不直接作为本产品默认值。

2026-10-05 用户确认：SD 卡暂不开发，其余已讨论能力纳入开发范围，包括第 3 项的环境/镜像列表规则、第 6 项的具体机型皮肤导入/下载/显示和真实摄像头接入。跨架构仍按此前决定放到二期。本期不开发 SD 卡的 Custom、Existing image、None 配置、文件导入、镜像创建/挂载及对应 IPC；内部存储配置仍需开发。其余此前已确认的边界继续有效：仅配置新建设备，不扩展到已有设备编辑、XR 或硬件画像新建/导入。

前三项已有独立计划：[动作图标对齐](../plans/2026-10-05-device-action-icon-alignment.md)、[清单加载反馈](../plans/2026-10-05-wizard-catalog-loading.md)、[工作台与设备外框](../plans/2026-10-05-device-frame-and-canvas.md)。本报告不为这三项另做可行性调研。

调研采用项目源码、Android 官方文档/源码、官方镜像 manifest，以及本机 SDK/Studio 的画像资源交叉核实。当前会话没有 anysearch MCP 工具，网络检索使用内置 web；部分 Gitiles 页面不能经 web 打开，使用官方 `?format=TEXT` 读取。未创建/启动 AVD、下载系统镜像或改动源码。报告沿用仓库已有 `book/think-report/` 分类（见其 [README](README.md)），不新增另一套调研目录。

### 1.2 未知点清单（本次调研要回答的问题）

- [x] 画像是否有正式分类与屏幕信息，还是只能按名字猜？官方定义有标签和硬件元数据，可借鉴 Studio 分类规则；详见 2.2、2.5。
- [x] 能否列出 Wear OS 等类别，是否有当前 arm64 可用镜像？官方源存在对应资源；应用需要扩展目录和匹配规则，完整运行与操控仍需实测；详见 2.5、3.5。
- [x] 截图中的 API 37.2、16 KB 和 SDK 扩展能否表示？官方 manifest 有这些条目，现有整数 API 与三变体模型会丢失它们；详见 3.2、3.5。
- [x] 可否直接复用 Android Studio 的模态框？其 UI 依赖 Java/Swing/IDE；推荐在现有 React 窗口重建布局；详见 3.3。
- [x] 附加设置改哪些配置才能生效？需同时覆盖创建配置、启动参数及资源能力；详见 4.5。
- [x] 是否所有截图设置都能自由配置？本期开发除 SD 卡外的已确认设置；Quick Boot 需单独验证，跨架构放到二期。SD 卡的平台限制保留作调研依据，不再作为本期功能；详见 4.5、5。

### 1.3 拆分判断

| 单元                       | 对应需求        | 依赖                                                   |
| -------------------------- | --------------- | ------------------------------------------------------ |
| 画像元数据与形态分类       | 用户第 4 项     | 可先独立完成数据与分类布局                             |

## 2. 调研单元：画像元数据与形态分类

### 2.1 该部分要做什么

参考截图 3：左侧提供手机（Phone）、平板（Tablet）、Wear OS、桌面、电视、车载分类；右侧搜索与单选表格，列名称、Play 支持、支持 API、宽、高、密度。分类依据真实画像，切换类别后清除不属于当前类的选中项；列表为空、加载和错误均明确可见。

已确认不纳入 XR、新建/导入硬件画像；截图中的分类导航与已有画像选择仍按本单元开发。

### 2.2 项目现状

- [profiles.ts](../../src/main/emulator/profiles.ts) 运行 `avdmanager list device`，提取 id/name，并直接排除带 `Tag :` 的条目；因此 Wear、TV、Automotive、Desktop 被过滤，手机和平板混列。
- [types.ts](../../src/shared/types.ts) 的 DeviceProfile 仅有 id/name，无法支持截图中的列、预览和兼容性判断。[SDK IPC](../../src/main/emulator/index.ts) 缓存 5min，可扩充返回契约，保持 renderer 只经 [preload](../../src/preload/api/sdk.ts) 访问。
- [DeviceWizard](../../src/renderer/src/components/DeviceWizard.tsx) 是纵向按钮列表；[原生向导窗](../../src/main/window/wizard.ts) 为不可缩放的 440×560，需要改尺寸与内容布局。
- [PRD B](../docs/PRD.md) 要求画像来自 avdmanager；[此前计划的变更记录](../plans/2026-10-04-avd-create-delete.md) 已确认恢复官方 create/list 路径，不宜退回手写设备名目录。

本机只读核实的资源：

| 事实源                                                                                                                          | 实际读到的内容                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/Users/pangzerui/Library/Application Support/multi-session-device/AndroidSDK/cmdline-tools/latest/lib/sdklib/tools.sdklib.jar` | `com/android/sdklib/devices/` 下 devices、nexus、wear、tv、desktop、automotive、xr XML；其中 devices/nexus 为 25/46 个定义，符合当前手机/平板 71 条的口径 |
| `/Applications/Android Studio.app/Contents/plugins/android/lib/sdklib.jar`                                                      | 同类 XML，但 devices/nexus 为 24/41，wear 为 4；应用 SDK 的 wear 为 5，说明两个工具版本的目录并不完全一致                                                 |
| 上述 SDK 的 nexus.xml                                                                                                           | Pixel 9a：1080×2424、6.24 英寸、420dpi、API 35 起、Play=true；Pixel Tablet：2560×1600、10.95 英寸、API 33 起；Pixel Fold：7.58 英寸且有折叠描述           |

这些路径是本次样本环境，不能写死在产品中。画像可从安装的 cmdline-tools JAR、镜像附带定义等来源补元数据；官方 [DeviceManager 源码](https://android.googlesource.com/platform/tools/base/+/studio-master-dev/sdklib/src/main/java/com/android/sdklib/devices/DeviceManager.java) 说明了定义的资源来源，此旧分支仅用于来源机制参考，实际格式以当前 SDK 为准。

### 2.3 候选方案

**方案 A：官方 XML 元数据 + Studio 分类规则，应用自己渲染**

- 原理：main 从当前 SDK 的画像 XML 提取元数据，与 avdmanager 输出按 id/厂商核对。分类借鉴 [Category.java](https://android.googlesource.com/platform/tools/adt/idea/+/refs/heads/mirror-goog-studio-main/android/src/com/android/tools/idea/avdmanager/ui/Category.java) 和 [Device.java](https://android.googlesource.com/platform/tools/base/+/refs/heads/mirror-goog-studio-main/sdklib/src/main/java/com/android/sdklib/devices/Device.java)，renderer 渲染导航与表格。
- 适配点：现有 profiles 模块与 sdk:profiles 返回值；不要求安装 Studio。官方源码为 Apache 2.0，若移植逻辑/代码需保留对应许可与来源。

**方案 B：小型 Java 辅助程序调用 sdklib，输出 JSON**

- 原理：利用现有 JRE 与 cmdline-tools 的 sdklib 读取 Device，对外返回结构化字段和分类，减少自行解释 XML 的工作。依据同一 [Device API](https://android.googlesource.com/platform/tools/base/+/refs/heads/mirror-goog-studio-main/sdklib/src/main/java/com/android/sdklib/devices/Device.java)。
- 适配点：main 子进程；Java 已有，但还需辅助程序编译/分发、classpath 与 SDK 版本适配，SDK 内部 API 不等于稳定公共接口。

**方案 C：只用列表名称、id 前缀和少量手写映射**

- 原理：保留现有文本解析，再按 Pixel Tablet 等已知名称归类；[avdmanager 文档](https://developer.android.com/tools/avdmanager) 的 list 命令可提供设备清单。
- 适配点：改动最少；无法可靠获得完整屏幕信息、API 约束、折叠标记与自定义设备类别，后续镜像匹配仍要补数据。

### 2.4 可行性分析

| 维度     | 方案 A                                                                  | 方案 B                                               | 方案 C                               |
| -------- | ----------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------ |
| 技术匹配 | 覆盖分类、表格和摘要；需处理 XML 版本/单位/缺字段及来源合并             | 能借用官方语义；需适配所装 sdklib                    | 仅适合极少画像，无法满足完整布局信息 |
| 规则冲突 | main 读资源、renderer 走 IPC；保留 avdmanager 创建画像事实源            | 同样可遵守分层，不能加载/写用户 IDE 目录作为必需条件 | 名称推断不符合真实画像与兼容性要求   |
| 成本     | 增画像读取和缓存；JAR 解包可借用 SDK bootstrap 的提取思路，解析成本可控 | 增辅助产物和 Java API 耦合，维护成本较高             | 起步低、后续误分类与补数据成本高     |

方案 A、B 都可行，A 更适合现有 Electron 产品。不要直接把 xdpi/ydpi 当 UI 的 density：它们是物理像素密度；截图中的 Android 逻辑 dpi 应从 pixel-density 及官方映射得到。

### 2.5 结论与实施建议

结论：**借鉴思路手写（方案 A）**。复用官方定义，自己实现结构化适配与 React 分类表格。

官方 Device 规则已实际读取：无特殊 tag 的设备，默认屏幕至少 7 英寸且不是 foldable 才归 Tablet；其余归 Phone。因此 Pixel Fold 即使展开超过 7 英寸仍是手机。Wear/TV/Desktop/Automotive 按 tag 判断，车载 Play 标签需规范化；弃用标记独立处理。未知标签保留为未知类别，不直接当手机。来源：[Device.java](https://android.googlesource.com/platform/tools/base/+/refs/heads/mirror-goog-studio-main/sdklib/src/main/java/com/android/sdklib/devices/Device.java)、[DeviceProfileTags.java](https://android.googlesource.com/platform/tools/adt/idea/+/refs/heads/mirror-goog-studio-main/android/src/com/android/tools/idea/avdmanager/ui/DeviceProfileTags.java)。

实施建议：

1. 新增 main `emulator/profileMetadata.ts`，仅从应用选定 SDK 受控资源读取；按画像 id、manufacturer 合并元数据，按 SDK 根/版本使缓存失效。未能关联的条目显示缺失字段，禁止伪造 API/Play 兼容信息。
2. 扩展 DeviceProfile：formFactor、manufacturer、tag、屏幕 width/height/diagonal/density、foldable/round、软件 API 范围、playStoreSupported、deprecated、默认 RAM/朝向和摄像头能力。保留 id/name，并使 create 仍采用 avdmanager 能识别的 id。
3. 停止排除所有 Tag 条目，改为保留标签再按获准类别展示。取消 UI 上不存在的默认选中项；键盘支持单选表格与搜索，中文导航、设备专有名称保持原名。
4. 向导外壳改为约 900×680 的原生模态窗，可缩放，最小尺寸以真实屏幕验证；左分类栏约 180px，右侧表格填充，搜索/表头/页脚固定、列表独立滚动。实施时使用 impeccable 技能，保留本项目亮暗、橙色选中和无阴影规则。
5. 对每个新类别验证「画像 → 对应镜像 → 创建 → 启停 → 投屏 → 必要输入」。Wear 圆屏、TV D-pad、车载/桌面输入不能以现有手机触控可用代替验收；类别能展示不代表完整操控已获验证。

## 3. 调研单元：API/服务筛选与系统镜像选择

### 3.1 该部分要做什么

参考截图 4，把名称、API 与服务筛选、镜像表格放在「设备」标签；右侧展示设备轮廓及硬件/系统摘要，未安装时显示实际下载大小。名称沿用默认画像名 + API，可修改。

系统镜像以完整包为选择对象。API 版本、SDK 扩展、16 KB 页大小、服务类型和 ABI 都是包属性，不能把一行简化成「API × Google Play」。

### 3.2 项目现状

- [catalog.ts](../../src/main/emulator/catalog.ts) 直读三份 sys-img2-3 manifest，筛 stable、arm64 和最近 5 个整数 API。正则 `<api-level>(\d+)</api-level>` 无法解析 37.2 或 36x；tag 白名单也会排除 ps16k 等变体。
- [ImageEntry/CreateDeviceInput](../../src/shared/types.ts) 没有 API minor、extension、displayName、image tag 等信息；向导使用 API+variant 作行 key。[devices.create](../../src/main/devices/index.ts) 再按整数 API+variant 反推 packageName，不能精确创建截图中的镜像。
- [SDK 下载守卫](../../src/main/emulator/index.ts) 只接受 `android-\d+`、三种 tag 与 arm64；[store.ts](../../src/main/store.ts) 同样把 ImageVariant 视为三值闭集。单改镜像 UI 会导致下载/创建/重启读取失败。
- [package.json](../../package.json) 实际为 Electron ^39.2.6、React ^19.2.1、styled-components ^6.5.3、zustand ^5.0.15，无 antd。[PRD 决策](../docs/PRD.md) 已否决 antd；技能中 antd 的旧技术栈描述不能用于本任务。

2026-10-05 实际读取的官方目录证据：

| 官方来源                                                                                                                                                                                                                           | 观察结果                                                                                                                                                                                                   |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [Google Play manifest](https://dl.google.com/android/repository/sys-img/google_apis_playstore/sys-img2-3.xml)                                                                                                                      | 包 `system-images;android-37.2;google_apis_playstore_ps16k;arm64-v8a`；api-level=37.2、extension-level=24、base-extension=true，名称含 16 KB Page Size。另有 36-ext19，api-level=36x、base-extension=false |
| [SDK 源目录](https://dl.google.com/android/repository/addons_list-6.xml)                                                                                                                                                           | 登记 wear、tv、desktop、automotive 和 tablet 专用镜像等 sys-img2-4 源；源目录名与包内 tag 不总是相同                                                                                                       |
| [Wear manifest](https://dl.google.com/android/repository/sys-img/android-wear/sys-img2-4.xml)、[TV manifest](https://dl.google.com/android/repository/sys-img/android-tv/sys-img2-4.xml)                                           | 均读到 arm64-v8a 包，例如 Wear API 35、TV API 36；尚未在本产品中安装运行                                                                                                                                   |
| [Desktop manifest](https://dl.google.com/android/repository/sys-img/android-desktop/sys-img2-4.xml)、[Automotive manifest](https://dl.google.com/android/repository/sys-img/android-automotive/sys-img2-4.xml)                     | 均有 arm64-v8a 条目；车载包含扩展 API 与多种 tag                                                                                                                                                           |
| [Tablet Google APIs manifest](https://dl.google.com/android/repository/sys-img/google_apis_tablet/sys-img2-4.xml)、[Tablet Play manifest](https://dl.google.com/android/repository/sys-img/google_playstore_tablet/sys-img2-4.xml) | 存在平板专用包；Play 源内出现 google_apis_playstore_tablet 等 tag，不能由源目录名直接反推                                                                                                                  |

这是目录存在性证据，不代表所有条目都是 stable、适配当前宿主或可以通过现有 scrcpy 启动。实现必须逐包读 channel、ABI 和类型属性。

### 3.3 候选方案

**方案 A：现有 manifest + 本地安装目录，重建 React 配置布局**

- 原理：扩展现有 catalog 成结构化镜像目录，按画像兼容信息筛选；复用 sdkmanager 下载，以完整 packageName 创建。[官方 SDK 源目录](https://dl.google.com/android/repository/addons_list-6.xml)、[sdkmanager 文档](https://developer.android.com/tools/sdkmanager) 提供包来源和安装机制。
- 适配点：catalog、SDK IPC、shared 类型、devices/create、AVD、store、DeviceWizard；不替换 SDK 工具链。

**方案 B：sdkmanager 清单/小型 sdklib 辅助程序作为统一仓库服务**

- 原理：由官方工具库负责仓库解析，再输出完整包元数据；renderer 仍手写布局。来源：[sdkmanager 文档](https://developer.android.com/tools/sdkmanager)、[DeviceSystemImageMatcher](https://android.googlesource.com/platform/tools/base/+/refs/heads/mirror-goog-studio-main/sdklib/src/main/java/com/android/sdklib/DeviceSystemImageMatcher.java)。
- 适配点：main；普通 `sdkmanager --list` 文本不能独自提供截图所需全部字段，若引 sdklib 辅助程序则需额外分发与版本维护。

**方案 C：直接集成 Android Studio 的选择 UI**

- 原理：复用 Studio 的 Java/IDE 向导组件。已读取的 [ConfigureDeviceOptionsStep.java](https://android.googlesource.com/platform/tools/adt/idea/+/refs/heads/mirror-goog-studio-main/android/src/com/android/tools/idea/avdmanager/ui/ConfigureDeviceOptionsStep.java) 依赖 Swing 与 IDE 控件，不能作为 React 组件装入现有 BrowserWindow。
- 适配点：需额外 JVM/IDE UI 集成、生命周期与主题桥接；会增加 Studio 依赖或大规模移植，不选。

### 3.4 可行性分析

| 维度     | 方案 A                                                     | 方案 B                                                | 方案 C                                      |
| -------- | ---------------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------- |
| 技术匹配 | 覆盖下载大小、筛选、摘要和离线已装数据；需升级当前正则解析 | 官方仓库语义较全，但 CLI 文本不足，辅助程序需验证 API | Java/Swing 与 Electron 页面不是同一组件体系 |
| 规则冲突 | 保留现有 SDK/AVD 隔离、中文文案、styled-components         | 可守住隔离，但不能静默写宿主 SDK/用户 Android 配置    | 把 Studio 当必需前提违背独立 SDK 产品目标   |
| 成本     | 在已有链路扩展，耦合集中；需维护 schema、缓存和元数据迁移  | 少写仓库解析，多维护 Java 产物与版本适配              | 最高，主题和原生窗口集成成本不划算          |

### 3.5 结论与实施建议

结论：**借鉴思路手写（方案 A）**。窗口布局和筛选逻辑在 React 实现，继续采用官方 manifest/sdkmanager/avdmanager。

建议的数据与接口：

- ImageEntry 保留完整 packageName 作为主键；增加显示名、结构化 API（major/minor、原始标记、预览信息）、extension/baseExtension、服务类型、image tags、ABI、channel、revision、下载大小和安装状态。minor 不能用浮点数比较；API 字面值、平台包段和 SDK extension 也不能互相等同。
- 兼容性输出为 `supported/unsupported/unknown` 与中文原因。借鉴已实际读取的 [DeviceSystemImageMatcher](https://android.googlesource.com/platform/tools/base/+/refs/heads/mirror-goog-studio-main/sdklib/src/main/java/com/android/sdklib/DeviceSystemImageMatcher.java)：画像软件 API 范围、Play 支持、形态标签、tablet 专用标签；再叠加本应用宿主 ABI 与工具版本能力。不能只比较最低 API 或一律要求 tag 字符串相等。
- CreateDeviceInput 增 imagePackageName；main 从可信目录/本地已装包核验其存在、安装完整与画像兼容，传给 `avdmanager -k`。用户提供的 tag/路径不直接拼成命令；sdk 下载从目录 allowlist 选完整包，不放宽成任意 shell 参数。
- DeviceMeta 增确切镜像身份与必要显示元数据，调整 store 校验并提供向后兼容读取。旧设备仅在缺字段时按旧映射读取/派生，不重建 AVD、重命名或删除旧记录；AVD config 继续是硬件/实际镜像事实源。
- 已装检测改为按完整包定位、核对 package.xml/source.properties 与关键镜像文件，不能继续按 API/三变体构造路径或以非空目录算完整安装。离线可显示本地已装包和上次缓存；在线目录失效与本地不可用分别表达。

建议步骤与布局：

1. 升级 catalog 的 XML 解析和包模型；按官方源发现/受控登记新形态源，合并已装包，API 窗口先保留推荐视图，完整列表由筛选开关控制。
2. 在设备页将名称、API、服务筛选与镜像表格合并，右侧约 210px 摘要固定；增加「显示 SDK 扩展镜像」「显示不支持的镜像」。不支持项可查看原因，创建禁用；未知兼容性不以支持处理。
3. 「设备 / 附加设置」切换保存表单；返回画像页或改镜像后重新检查兼容性与高级参数。根据尚未安装的选中镜像显示下载按钮/进度；下载并核验成功后才允许完成创建，保留现有单下载互斥。
4. 需要匹配截图的两页流程时，将命名合入配置页；这会替代 PRD 现有三步顺序，应先同步 PRD/plan，不能直接在代码中改变流程。颜色和主题继续本项目设计系统，实施使用 impeccable 技能。
5. 修改 `shared/types.ts`、`preload/api/sdk.ts`、`preload/index.d.ts`、`main/emulator/{catalog,index,avd}.ts`、`main/{devices/index,store}.ts` 和 renderer 向导。尽量复用通道；新增参数/能力时同步 shared IPC 白名单。

验证需含整数/小版本/extension/16KB/预览、同 API 多个包不覆盖、离线、未装/半装、无兼容镜像、错误重试、旧元数据兼容，以及每获准类别至少一个真实 AVD 的创建/下载/启停。稳定镜像默认可用，预览和不支持项不能通过勾选自动绕过 main 守卫。

## 4. 调研单元：附加设置布局与实际配置

### 4.1 该部分要做什么

参考最后两张图，按设备皮肤、摄像头、网络、启动、存储、模拟性能分组，支持修改并实际应用。右侧摘要和页脚固定，表单主体独立滚动，单位可选、错误定位到字段，关键限制在字段旁解释。

本期包含具体机型皮肤导入/下载/显示、模拟/虚拟场景及真实摄像头、网络速度/延迟、朝向、启动方式、内部存储、CPU/GPU/RAM/VM heap 和 arm64/Optimal ABI 选择。SD 卡分组及其全部配置/导入能力暂不开发；跨架构属于二期。

设置默认值沿用已明确的画像与 PRD 约束，实施计划再细化各字段的可用范围与验证顺序；不把截图中的 Quick、4 核、2GB RAM、228MB heap 等视作授权默认值。Quick Boot 属于本期开发范围，通过恢复稳定性验证后才开放。

### 4.2 项目现状

- [CreateDeviceInput/DeviceMeta](../../src/shared/types.ts) 与 [devices.create](../../src/main/devices/index.ts) 没有高级参数。[avd.ts](../../src/main/emulator/avd.ts) 仅 `avdmanager create avd -n/-k/-d`，没有创建后的 config 覆写步骤。
- [runner.ts](../../src/main/emulator/runner.ts) 启动固定 `-no-window -no-snapshot -gpu host`。即使表单或 config 选择 Quick/Automatic，目前仍会被启动参数覆盖。
- [PRD B](../docs/PRD.md) 已提出朝向、RAM、内部存储、SD 卡，其中 RAM 随画像、内部存储默认 6GB 且创建后不扩容；当前尚未实现。[快照问题](../notes/issue/2026-10/2026-10-04-emulator-snapshot-resume-crash.md) 记录的是旧版本/手写 AVD 的 SIGABRT，官方创建路径恢复后尚不能宣称问题已消失。
- 本机 SDK 的 `/Users/pangzerui/Library/Application Support/multi-session-device/AndroidSDK/emulator/lib/hardware-properties.ini` 已读到 `hw.cpu.ncore`、`hw.ramSize`、`vm.heapSize`、`disk.dataPartition.size`、`hw.initialOrientation`、`hw.camera.front/back`、`hw.gpu.mode`、`hw.sdCard.path`、`fastboot.forceColdBoot`。其中 RAM/heap 单位为 MB，GPU enum 为 auto/host/software；产品读取以所装工具版本为准。
- 原生 dialog 白名单当前只是 MessageBox；选文件和宿主摄像头枚举需新增受控能力，不能在 renderer 直接读路径或启动工具。

### 4.3 候选方案

**方案 A：avdmanager 创建 + config.ini 白名单覆写 + runner 参数适配**

- 原理：先由官方工具生成 AVD，再应用被验证的高级字段；运行时选项由 runner 构造 argv。硬件字段参考 [官方 hardware-properties.ini](https://android.googlesource.com/platform/prebuilts/android-emulator/+/refs/heads/main/darwin-x86_64/lib/hardware-properties.ini)，并以本机 SDK schema 复核。
- 适配点：avd、runner、devices、store 和 shared；需保留未知 config 键、受控路径、创建回滚与旧设备默认行为。

**方案 B：把设置全部变成 emulator 启动参数**

- 原理：使用 [emulator 命令行](https://developer.android.com/studio/run/emulator-commandline) 覆盖 RAM、GPU、摄像头、网络等，创建 AVD 不改。
- 适配点：主要是 runner；不能覆盖所有创建时存储和 UI skin 语义，也容易让磁盘配置、元数据与实际参数不一致，只适合 A 的运行时部分。

**方案 C：手写完整 AVD / 移植 Studio 的 AVD 构建器**

- 原理：从头生成全部 config 或引入 sdklib 构建 API。项目 [手写 AVD 经验](../notes/learn/2026-10/2026-10-04-avd-config-handwrite.md) 曾验证最小冷启动，但已因官方创建恢复可用而退为备用；[Studio 配置组件](https://android.googlesource.com/platform/tools/adt/idea/+/refs/heads/mirror-goog-studio-main/android/src/com/android/tools/idea/avdmanager/ui/ConfigureDeviceOptionsStep.java) 不是可直接嵌入的 Web 表单。
- 适配点：需要重新承担设备默认键、兼容性、快照与资源生成责任；不选。

### 4.4 可行性分析

| 维度     | 方案 A                                                    | 方案 B                                   | 方案 C                            |
| -------- | --------------------------------------------------------- | ---------------------------------------- | --------------------------------- |
| 技术匹配 | 覆盖大多数截图字段，分别接入创建/启动；仍有平台与版本限制 | 部分运行选项够用，存储/皮肤/完整配置不足 | 理论覆盖广，缺键及版本行为难验证  |
| 规则冲突 | 保留官方画像、SDK/AVD 隔离与失败回滚                      | 会覆盖已有配置，需定义参数优先级         | 放弃现有官方创建路径，扩大故障面  |
| 成本     | 中等；字段验证、单位换算与启动生效验证是主要工作          | 单项成本低，完整需求仍需 A               | 最大；Java 构建依赖或完整自研维护 |

4. runner 用同一份经验证的设置构造 argv，定义配置优先级，移除对获准字段的固定覆盖；legacy 设备缺字段继续按现有冷启动/host 路径，变更默认值另行确认。AVD config 仍为硬件事实源，JSON 记录创建意图与需要的启动参数。

修改范围：`shared/types.ts`，preload 与共享通道，`main/emulator/{profiles,avd,runner,index}.ts`，新增皮肤资源读取/解析与摄像头能力模块，`main/{devices/index,store,dialog/index}.ts`，以及 DeviceWizard、配置表单/摘要和投屏外观组件。测试覆盖单位/边界/非法 IPC、失败回滚、重启读取、选项真正传到 argv/config、两设备配置互不串台、旧设备兼容；内部存储容量、朝向与摄像头取景需真 AVD 验收。皮肤需验证导入/下载失败、素材缺失、屏幕尺寸不匹配、横竖布局、缩放和触控坐标；不能只检查 config 有键。

## 5. 风险与开放问题

1. **布局可行，完整能力需分项验收。** 无需安装 Studio 来显示分类与配置布局；Wear/TV/Desktop/Automotive 的目录和 arm64 包存在，但本轮没有启动实测。TV D-pad/Wear 形状/车载多屏可能要求扩充既有输入和显示契约。
2. **精确复刻目录会受工具版本影响。** 本机 Studio 与 SDK 画像数量不同；以应用 SDK 能创建的资源为事实源，缺字段明确显示未知。schema、deprecated、API minor/extension/preview、source 与 tag 变化都需真实 fixture，不能继续堆正则补丁。
3. **已有硬限制不能用表单掩盖。** SD 卡已由用户排除本期，平台限制保留为调研事实；Quick Boot 纳入本期开发，但仍须解决已知恢复问题并通过稳定性验收；GPU 降级性能与多实例 RAM 超配必须验证。本期字段的可编辑范围必须与能力一致。
4. **PRD 需要跟进。** 已确认的两页向导、更多设备类型/镜像、完整附加设置（除 SD）、机型皮肤、真实摄像头及 Quick Boot 扩展现有范围；实施前同步 PRD 与 plan，并更新 SD 暂缓、跨架构二期和原 Quick Boot v1.1 候选口径。stage 由人定，建议步骤只能用 suggested。用户本轮要求更新调研文件，本轮交付仍为文档，不直接进入实现。
5. **源码与资源许可不同。** 本报告借鉴的 AOSP 源码文件为 Apache 2.0；实际下载 SDK/镜像继续使用既有许可流程。截图作布局参考，不把 Studio 图标/皮肤资产直接打包为应用资源。
6. **AVD 对账并行草案需协调契约。** 当前 [对账计划](../plans/2026-10-05-avd-reconciliation.md) 尚为 draft/suggested；本报告建议的 metadata 扩展需与其读取诊断协调，不能在迁移失败时当空库覆盖，也不借本次调研修复该问题。

本期建议交付顺序为分类元数据和页面 → 精确镜像模型/选择/创建 → 基础与运行附加设置 → 机型皮肤/真实摄像头/Quick Boot 及新类别逐项验收启用。这些是同一期内的开发批次，不以拆批次为由遗漏已确认能力。前三份视觉/加载计划可以先实施，其中通用外框是后续具体机型皮肤显示的基础，无须等待整个新向导。SD 暂缓，跨架构二期。
