# 机型皮肤与宿主摄像头调研

> 创建时间：2026-10-06 22:36:36（Asia/Shanghai）
> 需求来源：选了皮肤仍显示通用外框、Mac 摄像头不可选，希望新建机型直接匹配并获取官方皮肤。
> 调研单元：3 个
> 状态：三项建议均已于 2026-10-07 确认，实施见 [施工图](../plans/2026-10-07-skin-camera-integration.md)

## 1. 需求理解

### 1.1 功能目标

背景：向导已保存皮肤和摄像头设置，但所选机型外观没有进入投屏显示，真实摄像头列表为空。用户希望减少逐个寻找、导入 zip 的操作。

范围：皮肤解析、受控素材读取、投屏几何与装饰、摄像头枚举与权限反馈、官方皮肤目录与按机型获取。沿用 Electron 39、React 19、styled-components 和现有 scrcpy 链路。

排除项：不改视频采集协议，不重建用户 AVD，不修改 Android Studio 文件，不替用户重置系统权限；镜像 package.xml 修复、Quick Boot、SD 卡和折叠多屏不并入这轮。

预期行为：已有设备的明确皮肤选择能在应用内显示，显示和触控共用屏幕矩形；MacBook 摄像头能在向导识别并进入 Android 相机取景验证；新建设备按官方画像 id 精确找皮肤，首次获取后留在应用库，后续设备复用。

### 1.2 未知点清单

- [x] 为何写入 skin.path 仍看不到皮肤？投屏组件没消费 skinRef，见 2.2。
- [x] 原有 layout 能否直接用于触控？不能；Pixel 7 屏幕偏移解析错误，平板横屏首布局也会被拒，见 2.2。
- [x] Mac 摄像头是否完全没有枚举出来？本轮宿主 CLI 已列出 MacBook Pro相机，旧正则解析结果仍为 0，见 3.2。
- [x] 是否有官方独立皮肤来源？有；Studio 官方源码仓库的 device-art-resources，已实取 Pixel 7 归档，见 4.2。
- [x] 是否每台设备都要重新导入？已有应用皮肤库可复用；缺的是官方来源接入、机型匹配和默认策略，见 4.5。

### 1.3 拆分判断

分为投屏皮肤、宿主摄像头、官方皮肤获取三个单元。摄像头可独立开发；自动获取依赖皮肤校验和显示接通，避免下载成功仍无外观。既有向导 plan 第 6、7 节已覆盖显示与权限要求，本报告补充实测根因和可用来源。

## 2. 调研单元：让所选皮肤进入投屏

### 2.1 该部分要做什么

把设备保存的 skinRef 解析为布局和受控素材，在工作台绘制真实边框；视频保持完整，输入映射使用同一屏幕矩形。覆盖已有选择、缩放、设备切换和横竖变化。

### 2.2 项目现状

- [DeviceCanvas](../../src/renderer/src/components/DeviceCanvas.tsx) 只读取 frameKind，调用 [computeLayout](../../src/renderer/src/screen/geometry.ts)，绘制 FrameShell、听筒和摄像头圆点；没有读取 advancedSettings.skinRef。当前实现是 styled DOM 通用装饰，用户看到的通用边框与此一致。
- [runner](../../src/main/emulator/runner.ts) 固定 `-no-window`。写 AVD skin 配置不会让 scrcpy 视频自动带外框；需要应用自行合成。
- [创建事务](../../src/main/devices/index.ts) 已保存 advancedSettings，并给导入皮肤写绝对 skin.path。[皮肤摘要](../../src/shared/types.ts) 只有尺寸，没有屏幕偏移、素材层或受控 URL，现有 [SDK IPC](../../src/main/emulator/index.ts) 也未提供素材读取能力。
- [parseSkinLayout](../../src/main/emulator/skins.ts) 从首个 part 取屏幕位置。Pixel 7 的 part1 是外框，part2 才是 device；[真实 fixture](../../src/main/emulator/__tests__/fixtures/skins/pixel_7-layout) 和本机官方文件都给出屏幕位置 `(59,58)`，现有 [测试](../../src/main/emulator/__tests__/skins.test.ts) 错断言 `(0,0)`。
- 本机官方 Pixel Tablet layout 只有 layouts.landscape，当前解析要求 portrait，因而跳过该皮肤。旧机型布局可见 `rotation 3`；[官方 skin 规格](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/docs/ANDROID-SKIN-FILES.TXT) 定义 rotation 为 0–3 的四分之一圈，当前注释和构造测试以 90 度解释，不能直接据此做旋转。
- 当前导入的 `b32a0f89-5dd6-4c73-9339-e86bd0239b17` 是验收占位素材。读取 back.webp 实际为 1200×2541 的纯灰 PNG；它只能验证导入与 config，不能作为真实 Pixel 外观验收素材。

### 2.3 候选方案

**方案 A：应用内合成官方位图和视频。** 解析 part 名称、摆位和素材层；把外框、屏幕映射到现有几何接口。来源：[Android 皮肤说明](https://developer.android.com/studio/run/managing-avds#create_an_emulator_skin)、[skin 规格](https://android.googlesource.com/platform/external/qemu/+/emu-master-dev/android/docs/ANDROID-SKIN-FILES.TXT)、现有 geometry/DeviceCanvas。

**方案 B：显示 emulator 原生窗口。** 原生窗口自行渲染皮肤。来源：上述 skin 规格和现有 runner 的 `-no-window`。若改成原生窗，会改变单工作台投屏与多会话编排，超出需求范围。

### 2.4 可行性分析

| 维度     | A：应用内合成                                 | B：原生窗口                          |
| -------- | --------------------------------------------- | ------------------------------------ |
| 技术匹配 | 沿用视频和输入接口，WebP/PNG 由 Chromium 显示 | 外框可见，但需改变当前嵌入链路       |
| 规则冲突 | 可遵守 renderer 白名单、完整画面和同源几何    | 与本轮保留工作台和 scrcpy 的范围冲突 |
| 成本     | 补布局解析、资源接口和几何，无新依赖          | 窗口编排与控制需要另做方案           |

### 2.5 结论与实施建议

结论：**借鉴思路手写**，采用 A，沿用官方 layout 的数据与现有投屏几何。

落地到 `skins.ts`、`shared/types.ts`、`shared/ipc-channels.ts`、`preload/api/sdk.ts`、SDK IPC、`DeviceCanvas.tsx`、`screen/geometry.ts`；界面实施走 impeccable。

1. 解析真正含 display 的 part，保留位图对应的 part、偏移和旋转；接受横屏首布局。对不支持的多屏明确报错。Pixel 7 的原始屏幕矩形锁为 `(59,58,1080,2400)`，外框为 `1200×2541`。
2. 新增受控的设备皮肤显示接口：renderer 只传 deviceId；main 从保存的 skinRef 解析库内资源，返回显示布局与只读素材句柄。禁止接收任意文件路径，守卫主窗来源并核验资源归属。
3. 让图像装饰、视频和输入共用缩放后的 screenRect。素材放屏幕之外；mask/cutout 按既有 plan 的完整画面要求处理，不能遮掉视频像素。缺方向时按基础布局旋转，比例不匹配则给出原因，避免拉伸。
4. 切设备和方向时释放旧手势，忽略迟到素材响应，回收 URL。明确选了皮肤但资源坏时显示诊断；旧设备或未选皮肤继续通用外框。

验证：真实官方 Pixel 7/Pixel Tablet 的截图；屏幕四角和中心触控、外框拒收触控、缩放/方向切换；坏图片、缺文件、路径越界和 IPC 来源拒绝。现有占位 zip 不用于外观判定。

## 3. 调研单元：Mac 摄像头可枚举、可恢复、可取景

### 3.1 该部分要做什么

在向导显示真实 Mac 摄像头及其权限/可用状态，正确配置 Android 前后摄像头。权限申请由用户操作触发；列出设备时不打开取景。

### 3.2 项目现状

- [cameras.ts](../../src/main/emulator/cameras.ts) 只接受 `Camera 'webcam0' is connected to device '…'`。现有 [测试样本](../../src/main/emulator/__tests__/cameras.test.ts) 来自 emulator 36.1.9。
- 本轮在应用 SDK 的 emulator **37.2.12.0** 实跑 `-avd __webcam_probe__ -webcam-list`，exit 0，stdout 为：

  `Camera 'MacBook Pro相机' can be specified by label as 'webcam0' or by id as '…' and will use pixel format 'NV12'`

  同一 stdout 含 MacBook 摄像头和 webcam0，但用生产正则解析得到 **0 项**。这是权限之外的确定解析缺口。

- [能力富化](../../src/main/emulator/settings.ts) 把枚举错误吞成空列表；[表单](../../src/renderer/src/components/wizard/SettingsForm.tsx) 只展示真实摄像头 webcamN，不能区分未授权、无硬件和探针错误。
- main 没有 getMediaAccessStatus/askForMediaAccess 接线。开发 Electron 的 Info.plist 已有 NSCameraUsageDescription；签名读取结果为 ad-hoc、TeamIdentifier 未设置。`electron-builder.yml` 有用途说明，`build/entitlements.mac.plist` 没有 camera 权限项；需核验签名后的应用与子进程权限，不能只看配置。
- [此前现场记录](../notes/issue/2026-10/2026-10-06-real-machine-acceptance-findings.md) 曾在 Electron 身份下取得无 Camera 行的 stdout。该证据保留，但尚未证明修复格式解析后正式应用仍不能枚举；TCC 和责任链需在真实 app 身份下复测。

### 3.3 候选方案

**方案 A：修正 emulator 输出解析，接 Electron 权限 API。** 兼容新旧格式，保留友好名称、宿主稳定 id 和 webcam 参数。来源：[Electron systemPreferences](https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos)、本轮 emulator 输出及现有 cameras 模块。

**方案 B：新增原生 AVFoundation 枚举助手。** 原生接口读取宿主摄像头，再关联 emulator 参数。来源：[Apple 媒体授权文档](https://developer.apple.com/documentation/avfoundation/requesting-authorization-to-capture-and-save-media)。仍需解决 TCC 与 emulator id 对应，助手身份并不会自动替宿主或取流进程取得授权。

### 3.4 可行性分析

| 维度     | A：修现有枚举并接权限                            | B：原生助手                                 |
| -------- | ------------------------------------------------ | ------------------------------------------- |
| 技术匹配 | 保留 emulator 权威参数；Electron 39 已有权限 API | 可拿宿主信息，但还需关联 emulator 名称/序号 |
| 规则冲突 | main 处理平台能力，renderer 仅经白名单           | 可遵守边界，但要新增编译、签名与分发链      |
| 成本     | 两种输出 fixture、权限状态和入口                 | 增加原生构建，未证实可解决现有责任链问题    |

### 3.5 结论与实施建议

结论：**采用现成方案**，先用 A。输出格式修复可直接证明；权限恢复和取景需要真实应用验证。

落地到 `cameras.ts`、`settings.ts`、SDK IPC、shared/preload、`SettingsForm.tsx` 与 mac 打包配置；复用创建/启动重核验。

1. 新旧格式兼容解析，显示“MacBook Pro相机（webcam0）”；保留真实宿主 id，避免把序号当稳定设备身份。先兼容现有保存的 webcamN，枚举排序变化时不得静默换到另一台相机。
2. 返回权限状态与枚举诊断。macOS 状态未知时由“允许访问摄像头”按钮申请；拒绝时给系统设置恢复入口，授权后刷新。受限、无硬件、超时和已授权但探针空各给实际原因。
3. 用 getMediaAccessStatus/askForMediaAccess；[Electron 文档](https://www.electronjs.org/docs/latest/api/system-preferences#systempreferencesaskformediaaccessmediatype-macos) 说明拒绝后不能反复弹申请，系统设置改授权后需重启应用。不要自动执行 tccutil reset。
4. 核验 NSCameraUsageDescription 与需要的 camera entitlement；开发版和签名构建各留结果。实际 emulator 子进程能枚举/取景才算通过，Electron 返回 granted 不能单独作为通过证据。

验证：37.2.12 新输出与 36.1.9 旧输出、中文名称、空/异常输出、权限状态、刷新并发、热插拔/占用；真 AVD 前后摄像头配置和 Android 相机真实取景。拒绝时不静默改为模拟画面。

## 4. 调研单元：官方皮肤自动匹配与缓存

### 4.1 该部分要做什么

新建画像时识别官方是否有对应皮肤，让首次获取与后续复用成为正常路径；保留手选导入皮肤和通用外框。

### 4.2 项目现状与来源实测

- [SKIN_DOWNLOAD_SOURCES](../../src/main/emulator/skins.ts) 为空，UI“下载官方皮肤”仍要求手填名字。现有 scanImportedSkins 已从应用 `device-skins` 库恢复导入/下载资源，皮肤不需要每个 AVD 再导入一次。
- 之前只检查 platform/sdk 的 emulator/skins，漏掉 Studio artwork 目录。真实官方来源是 [platform/tools/adt/idea 的 device-art-resources](https://android.googlesource.com/platform/tools/adt/idea/+/c500183b708aedf521b05e304e0e7f8d771d22b1/artwork/resources/device-art-resources/)，目录包含 pixel_7、pixel_tablet、wearos、tv、automotive 等；官方存在某目录不等于当前解析器支持该格式。
- 本机 `/Applications/Android Studio.app/Contents/plugins/android/resources/device-art-resources/` 已有 Pixel 7 等完整素材。应用 SDK 没有 skins 目录；这批资源实际属于 Studio，先前 fixture README/skins 注释的“SDK 自带机型皮肤”描述需要更正。
- 固定官方提交 `c500183b708aedf521b05e304e0e7f8d771d22b1` 后实取 [Pixel 7 tar.gz](https://android.googlesource.com/platform/tools/adt/idea/+archive/c500183b708aedf521b05e304e0e7f8d771d22b1/artwork/resources/device-art-resources/pixel_7.tar.gz)：HTTP 200，**176638 字节**，tar 列出 `back.webp`、`layout`、`mask.webp`。归档仅在内存读取检查，未写入用户皮肤库。
- 本次归档 SHA-256 为 `6726b02223f606e74fcdbd23bc9504abca5f989ee8b3c3acb2212ed2ddd60940`，是实测值，不能冒充上游发布的校验值。固定树里各文件的 Git blob id 可作为解包内容核验依据：layout `e6886ea2f219336295e2e7f5f6bd3ff267c7f217`，back.webp `326bda11b5489ef2526b8f5fe60b0fa744555b41`，mask.webp `5ccbc40407d71853d1ce33bea65fa07d92a76bd7`。
- 同目录 device-art.xml 有 AOSP/Apache-2.0 头部；位图归档没有独立 LICENSE。按原 plan，来源和许可需保留，不能把 XML 的许可证推定为全部图片可随应用重新打包；本轮方案先采用用户按需获取，不内置位图。

### 4.3 候选方案

**方案 A：从官方固定提交按机型下载，存应用库。** 使用受控目录清单和精确画像映射；原始归档已实测。来源：上述官方仓库/归档。

**方案 B：从用户已装 Android Studio 复制。** 找受控安装位置，校验后复制到应用自有库，来源记录保留路径和版本。来源：本机实际目录及同一官方资源树。可作为缓存缺失时的快捷来源，不能要求用户必须安装 Studio。

### 4.4 可行性分析

| 维度     | A：官方按需获取                            | B：Studio 本地复用                              |
| -------- | ------------------------------------------ | ----------------------------------------------- |
| 技术匹配 | 满足没有 Studio 时也能使用；固定提交可复核 | 本机立即有素材，不需 zip，但安装路径/版本不固定 |
| 规则冲突 | 固定来源白名单、入应用库，符合隔离契约     | 只读后复制，不修改或依赖 Studio 的运行目录      |
| 成本     | 复用 downloadSkin，增加清单/校验/幂等      | 增加受控安装位置发现和来源记录，无新依赖        |

### 4.5 结论与实施建议

结论：**采用现成方案**，使用官方资源；优先应用缓存，可补 Studio 本地复用，缺失时走 A 的官方获取。按机型精确匹配，不相似匹配皮肤。

落地到 `skins.ts`（或专用 `skinSources.ts`）、`settings.ts`、SDK IPC、shared/preload、`DeviceWizard.tsx`、`SettingsForm.tsx`。界面实施走 impeccable。

建议用户流程：选择 Pixel 7 → 显示“Pixel 7 官方皮肤” → 已缓存直接预选，首次确认来源条款后按需获取 → 校验入库并预选 → 创建 → 显示相同皮肤。用户已有明确手选时不覆盖；“通用外框”始终可选。新机型无官方皮肤时显示原因并保留导入入口。

资源与事务设计：

- main 内置固定版本目录清单，画像 id → 官方目录映射；名字不一致的 wear/TV 使用经过核实的显式映射。拒绝任意 URL、未知 skinName 和路径穿越。
- 资源缓存键由来源、固定提交和官方目录构成；同皮肤并发请求复用任务，成功后保存来源名和稳定引用，后续 AVD 共用。导入 zip 保持原有身份，不因自动策略重写旧设备。
- 临时目录获取，解包前检查条目和资源限额；核验路径、实际图片可解码、布局、文件 Git blob 身份后原子入库。失败只清本次临时文件，不删除已有共享皮肤。
- 不在每次开向导时下载，也不随远端主分支自动升级；缓存可离线用。进度、失败和重试入口复用现有 skin-progress；默认选择只在用户尚未手选时生效。
- 精确匹配后仍核对屏幕比例与方向支持，解析失败明确提示。折叠多布局先列为暂不支持，不能因目录存在就开放。

验证：Pixel 7 首次获取、再次新建零重复下载、重启复用、离线缓存、无官方目录、手选不被覆盖、取消/失败/重试、并发幂等、校验失败和条目越界。Pixel Tablet 作为横屏首布局回归。

## 5. 风险与开放问题

- 权限 TCC 责任链与 dev ad-hoc 签名问题需要真实应用复测；本轮没有重置授权或启动用户设备，尚未证明取景可用。先修确定的输出解析，再据授权状态和 stdout 定位。
- 资源目录和下载接口可用已验证；位图随应用分发的许可范围尚未确认。保留官方来源和许可说明，具体条款在实施来源接入时核实，不把源码 Apache 头部当素材重新分发授权。
- 固定提交避免运行时漂移；新机型靠显式更新资源清单。官方资产可得到与应用解析能支持是两道条件。
- [直连镜像 package.xml 的 P1](../notes/issue/2026-10/2026-10-06-real-machine-acceptance-findings.md) 仍是独立创建阻塞；本轮三项修复不能替代镜像修复任务。
